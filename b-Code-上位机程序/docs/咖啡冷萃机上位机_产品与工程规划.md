# 咖啡冷萃机上位机：产品与工程规划

> 文档性质：业务前端与上位机工程规划，不含实现代码  
> 基础工程：AppShell（C# / .NET 8 / WPF / AvalonDock 4.72.1）  
> 版本：v0.1  
> 日期：2026-07-13  
> 当前阶段：GPIO15 / GPIO16 黄灯、蓝灯轮换点亮实验已通过；上位机业务化改造待开始

---

## 1. 项目目标

在已有 AppShell 通用桌面框架上构建咖啡冷萃机专用上位机，使操作者能够：

1. 在中央主窗口直观看到上舱体、电气仓、下舱体及液体转移过程。
2. 在控制面板手动执行上液、降液、停止，并编排循环过程。
3. 在底部表格查看每个 GPIO 的定义、方向、当前电平、逻辑状态和更新时间。
4. 明确区分“待机、上液、降液、暂停、完成、故障、离线”等设备状态。
5. 让所有 UI 操作仍经 AppShell 指令总线执行，在控制台留痕并可复现。
6. 首先完成可离线演示的前端模拟器，再接入真实 ESP32；本规划阶段不修改嵌入式代码。

### 1.1 首版成功标准

- 应用启动后显示咖啡冷萃机专用名称、界面和默认布局，不再显示电机演示内容。
- 点击“上液”时，画面表现液体从下舱体沿密闭管路经过中部区域进入上舱体。
- 点击“降液”时，画面表现液体从上舱体沿密闭管路回到下舱体。
- 上液与降液不能同时处于激活状态，停止指令始终可用。
- GPIO15 / GPIO16 的 UI 状态与中央动画一致。
- 无设备连接时可以使用“模拟模式”完整演示；连接设备后可切换为“设备模式”。
- 断连、超时、非法状态不会被显示成“正常完成”。

### 1.2 本阶段不做

- 不编写或修改 ESP32 固件。
- 不确定最终串口报文细节，只预留清晰的通讯边界和消息模型。
- 不实现真实液位测量、温控、压力控制等尚未确认的硬件能力。
- 不把动画进度伪装成传感器实测液位；没有传感器时必须标注“估算/模拟”。

## 2. 已有基础与复用策略

现有工程已经具备以下可复用能力：

| 现有能力 | 在咖啡机项目中的用途 | 处理方式 |
|---|---|---|
| `ShellConfig.MainContent` | 注入三舱体主模拟画面 | 直接复用注入点 |
| AvalonDock 停靠布局 | 控制面板、GPIO 表、控制台自由停靠 | 保留 |
| 指令总线 | 统一执行上液、降液、停止、编排控制 | 保留并注册 `brew.*` / `device.*` 指令 |
| 声明式控制面板 | 承载基础按钮与参数输入 | 简单控件复用；复杂编排使用专用 WPF View |
| 表窗口 / SQLite | 保存运行记录、编排方案和事件 | 复用数据服务，不直接拿通用可编辑表充当实时 GPIO 看板 |
| 控制台与日志 | 调试通讯、追踪操作和故障 | 保留，默认与 GPIO 表位于底部标签组 |
| 资源窗口 | 管理编排文件、导出日志、参考资料 | 保留，可默认隐藏或缩小 |

### 2.1 改造原则

- `AppShell.Core`、`AppShell.Services` 和通用 Shell 能不改则不改。
- 咖啡机业务组件优先放在派生应用层，避免破坏模板的再次复用能力。
- 实时状态放在内存中的单一状态模型；SQLite 用于历史记录，不作为动画的实时消息总线。
- UI 不直接写串口，也不直接改 GPIO 状态；UI 只发指令，由业务服务决定模拟执行或设备执行。
- 设备回报是“实际状态”，按钮点击只是“控制意图”，两者不能混为一谈。

## 4. 中央三舱体模拟窗口

### 4.1 视觉结构

主画面按真实产品的纵向结构组织：

1. **上舱体**：透明圆柱容器，显示咖啡液填充高度、容量百分比和状态标签。
2. **电气仓**：深色实体仓体，显示泵、阀、ESP32、通讯指示与一段密闭液路示意。
3. **下舱体**：透明圆柱容器，显示咖啡液填充高度、容量百分比和状态标签。

整体外观参考项目已有的产品渲染图，使用深咖啡色液体、暗红机身和玻璃质感。界面不是机械 CAD 图，而是可快速读懂状态的工业监控示意图。

重要表达规则：液体仅沿“密闭管路”穿过电气仓区域，不把整个电气仓填充成液体，避免造成液体与电气元件直接接触的错误理解。

### 4.2 上液动画

上液对应当前原型中的 GPIO15：

1. 下舱体作为液体来源，边框出现黄色脉冲提示。
2. 下舱体液位连续下降，上舱体液位连续上升。
3. 管路中的粒子或流光由下向上运动，穿过电气仓中的密闭液路。
4. 电气仓内“上液执行”指示点亮，使用与黄灯实验一致的黄色语义。
5. 中央状态文字显示：`正在上液 · 下舱 → 上舱`。
6. 完成后动画平滑停止，进入待机或编排中的下一阶段。

### 4.3 降液动画

降液对应当前原型中的 GPIO16：

1. 上舱体作为液体来源，边框出现蓝色脉冲提示。
2. 上舱体液位连续下降，下舱体液位连续上升。
3. 管路流光由上向下运动。
4. 电气仓内“降液执行”指示点亮，使用与蓝灯实验一致的蓝色语义。
5. 中央状态文字显示：`正在降液 · 上舱 → 下舱`。

### 4.4 待机、暂停、故障和离线

| 状态 | 主画面表现 |
|---|---|
| 待机 | 无流光；两个舱体保持当前液位；中性灰/绿色状态标记 |
| 暂停 | 动画冻结；显示琥珀色“已暂停”；保留当前编排位置 |
| 完成 | 短暂绿色完成提示，然后回到待机 |
| 故障 | 红色边框与故障摘要；停止所有流动动画 |
| 离线 | 画面降低饱和度；明确显示“设备未连接”；禁止设备控制按钮 |
| 模拟 | 正常动画，但持续显示“模拟数据”水印，避免误认实机状态 |

### 4.5 液位数据规则

- 状态模型统一使用 `0.0–1.0` 表示液位比例。
- 上、下舱体液量在理想模拟下守恒：`UpperLevel + LowerLevel = Constant`。
- 首版没有真实液位传感器时，液位来自运行时间估算，UI 标记为“估算液位”。
- 一旦后续加入液位传感器，动画以设备遥测值为准，并可显示“目标值”和“实测值”两条信息。
- 在设备模式中，如果只收到 GPIO 状态而没有液位数据，允许显示方向动画，但不得显示伪精确百分比。

## 5. 控制与编排面板

### 5.1 顶部：连接与模式

- 串口选择、刷新端口、连接/断开。
- 模式切换：模拟模式 / 设备模式。
- 连接设备前显示端口、波特率和最后错误。
- 设备模式未连接时，所有会改变设备状态的按钮禁用，但“模拟运行”仍可使用。

### 5.2 手动控制区

按钮：

- `上液`：请求进入上液状态。
- `降液`：请求进入降液状态。
- `停止`：立即结束当前动作，回到安全待机；使用醒目的红色样式。

交互规则：

- 上液和降液互斥，不允许同时激活。
- 再次点击当前动作不重复下发；UI 显示“已在执行”。
- 从上液直接切到降液，或从降液直接切到上液时，必须先经过停止/死区阶段。
- “按钮已点击”不等于“动作已生效”；收到设备确认前显示“请求中”。
- 软件停止不能替代真实硬件急停。未来若存在危险运动，硬件必须有独立保护。

### 5.3 编排参数

首版固定为冷萃循环模板，参数包括：

| 参数 | 建议默认值 | 说明 |
|---|---:|---|
| 上液时长 | 60 秒 | 下舱到上舱的运行时间 |
| 上舱停留 | 30 秒 | 上液后浸泡/等待时间 |
| 降液时长 | 60 秒 | 上舱到下舱的运行时间 |
| 下舱停留 | 30 秒 | 降液后等待时间 |
| 循环次数 | 5 次 | 完整“上液→停留→降液→停留”的重复次数 |
| 切向死区 | 500 毫秒 | 两个方向切换之间保持双路关闭 |

参数范围在进入实现前再结合泵、容积和机械测试确认。UI 必须进行最小值、最大值和整数校验。

### 5.4 编排时间线

面板用纵向时间线展示当前方案：

```text
循环 1..N
  ① 上液      GPIO15       60 s
  ② 上舱停留  两路关闭     30 s
  ③ 降液      GPIO16       60 s
  ④ 下舱停留  两路关闭     30 s
```

控制按钮：`启动编排`、`暂停`、`继续`、`停止并复位`。

当前步骤高亮并显示剩余时间；已完成步骤显示勾选；未执行步骤显示灰色。修改参数只影响下一次启动，运行中不允许悄悄改变当前方案。

### 5.5 后续可扩展的自由编排

P1 阶段可将固定模板升级为步骤列表，允许添加、删除、排序：

- 上液
- 降液
- 等待
- 循环开始 / 循环结束
- 条件等待（未来有传感器后）

自由编排必须先做静态校验：禁止相互冲突的输出、零时长无限循环、超范围参数和缺失停止路径。

## 6. 底部 GPIO 状态表

### 6.1 设计选择

新增专用 `PinStatusView`，作为底部首个标签，而不是直接使用通用 SQLite 可编辑表格。原因：GPIO 是实时设备状态，普通可编辑数据库表容易让操作者误以为“改单元格就能改硬件”。

GPIO 表首版为只读监视；需要控制时必须通过右侧控制面板或等价指令完成。

### 6.2 列定义

| 列 | 示例 | 说明 |
|---|---|---|
| GPIO | `15` | ESP32-S3 引脚号 |
| 名称 | `PUMP_UP` | 固件/协议稳定名称 |
| 中文功能 | `上液` | 操作者可读名称 |
| 方向 | `OUTPUT` | INPUT / OUTPUT / PWM / ADC 等 |
| 电平 | `HIGH` | 实际或模拟电平 |
| 有效状态 | `激活` | 根据有效电平换算后的逻辑状态 |
| 设备含义 | `下舱→上舱` | 工艺语义 |
| 指示色 | `黄色` | 与原型灯和主动画一致 |
| 数据来源 | `设备` / `模拟` | 避免混淆 |
| 质量 | `正常` / `过期` / `未知` | 是否收到可信更新 |
| 更新时间 | `21:35:07.184` | 最后变化时间，精确到毫秒 |
| 备注 | `与 GPIO16 互斥` | 安全和接线说明 |

### 6.3 当前已知引脚基线

| GPIO | 稳定名称 | 暂定业务功能 | 当前原型指示 | 有效电平 | 互锁 |
|---:|---|---|---|---|---|
| 15 | `PUMP_UP` | 上液：下舱 → 上舱 | 黄灯 | HIGH | 不得与 GPIO16 同时有效 |
| 16 | `PUMP_DOWN` | 降液：上舱 → 下舱 | 蓝灯 | HIGH | 不得与 GPIO15 同时有效 |

以上颜色映射依据当前实验照片与现有实验程序暂定。接线若与此相反，应只修改引脚配置/映射，不改动画业务含义。

### 6.4 表格告警规则

- GPIO15、GPIO16 同时有效：整行红色，设备状态进入故障，主动画立即停止。
- 设备在线但某引脚长时间没有更新：质量显示“过期”，使用琥珀色。
- 未收到设备快照：电平显示 `—`，不得默认当作 LOW。
- UI 请求状态与设备回报不一致超过超时阈值：显示“指令未确认”。
- GPIO 定义表中未来可继续加入泵、阀、液位、温度、门盖等引脚，不改变表结构。

## 7. 业务状态模型

### 7.1 总状态

```text
Offline
  └─连接成功→ Idle

Idle
  ├─上液请求→ StartingUp → PumpingUp
  ├─降液请求→ StartingDown → Lowering
  └─编排启动→ RunningSequence

PumpingUp / Lowering / RunningSequence
  ├─暂停→ Paused
  ├─停止→ Stopping → Idle
  ├─完成→ Completed → Idle
  └─异常→ Fault

Fault
  └─故障确认且状态安全→ Idle
```

### 7.2 核心状态对象

`MachineState` 至少包含：

- 连接状态与运行模式。
- 当前工艺状态、当前步骤、循环序号和剩余时间。
- 上/下舱液位及其数据来源、数据质量。
- 所有引脚的快照。
- 当前告警列表。
- 最后一次设备消息时间和最后一次命令确认时间。

所有 UI 组件只订阅这一份状态，不各自维护“另一套真相”。这样主动画、GPIO 表、状态栏与控制按钮才能保持一致。

### 7.3 安全不变量

无论模拟模式还是设备模式，都必须满足：

1. `PUMP_UP` 与 `PUMP_DOWN` 不可同时有效。
2. 方向切换必须经过两路关闭的死区。
3. 断开连接、通讯超时或程序退出时，上位机首先请求停止；是否真正安全仍由嵌入式端独立保证。
4. 故障状态不能通过再次点击上液/降液直接覆盖，必须先确认故障原因并复位。
5. UI 动画只能表现状态，不能作为安全反馈或真实液位依据。

## 8. 指令设计

遵守 AppShell“一切操作皆指令”的原则。建议指令域：

| 指令 | 作用 | UI 入口 |
|---|---|---|
| `device.ports` | 刷新并列出串口 | 刷新端口 |
| `device.connect port=COM5 baud=115200` | 连接设备 | 连接 |
| `device.disconnect` | 断开设备 | 断开 |
| `device.mode mode=simulation|hardware` | 切换模式 | 模式选择 |
| `brew.up` | 请求上液 | 上液按钮 |
| `brew.down` | 请求降液 | 降液按钮 |
| `brew.stop` | 停止当前动作 | 停止按钮 |
| `brew.sequence.start ...` | 按参数启动编排 | 启动编排 |
| `brew.sequence.pause` | 暂停编排 | 暂停 |
| `brew.sequence.resume` | 继续编排 | 继续 |
| `brew.sequence.abort` | 终止并进入安全待机 | 停止并复位 |
| `brew.status` | 输出完整状态摘要 | 控制台/诊断 |
| `gpio.list` | 输出所有引脚状态 | GPIO 表刷新/控制台 |

约束：

- 按钮不得直接调用串口服务，必须执行等价指令。
- 指令结果区分“请求已发送”“设备已确认”“动作已完成”。
- 设备控制指令必须异步，不阻塞 WPF UI 线程。
- 每条控制指令写入日志，记录来源、参数、请求时间、确认时间和结果。

## 9. 通讯边界规划（暂不实现嵌入式代码）

### 9.1 分层

```text
WPF View
  → CommandBus
  → BrewController
  → IMachineTransport
       ├─ SimulationTransport
       └─ SerialMachineTransport（后续接 ESP32）
  → MachineStateStore
  → UI 统一刷新
```

接口职责：

- `SimulationTransport`：在无设备时生成确定性的 GPIO、阶段和液位估算数据。
- `SerialMachineTransport`：只负责连接、收发、校验、超时和重连，不包含 UI 逻辑。
- `BrewController`：实施互锁、状态机、编排与命令确认。
- `MachineStateStore`：保存最新可信状态快照并通知 UI。

### 9.2 后续协议最低需求

未来与 ESP32 对接时，无论最终选择 JSON Lines、紧凑文本或二进制协议，都必须支持：

- 协议版本和设备标识。
- 心跳与在线状态。
- 全量 GPIO 快照，不能只依赖边沿变化。
- 当前工艺状态与故障码。
- 命令序号、接收确认和执行结果，避免重复或丢失后无法判断。
- 时间戳或单调递增序号，用于识别旧消息。
- 上电主动上报状态；上位机重连后可请求一次完整快照。

通讯协议应先形成独立文档并冻结字段，再进入嵌入式实现。

## 10. 数据与历史记录

建议 SQLite 业务表：

| 表 | 用途 | 首版 |
|---|---|---|
| `brew_runs` | 每次手动动作或编排的起止、参数、结果 | P1 |
| `brew_steps` | 每次编排中每一步的起止和结果 | P1 |
| `device_events` | 连接、断连、超时、故障、复位 | P1 |
| `gpio_events` | 只记录状态变化，不按 UI 刷新频率无限写入 | P1 |
| `recipes` | 保存命名编排方案 | P1 |

实时 GPIO 表不直接查询 SQLite；运行结束后才通过历史表追溯。日志和数据库都不能在 UI 线程同步进行高频写入。

## 12. 视觉规范

### 12.1 颜色语义

| 颜色 | 语义 |
|---|---|
| 黄色 | 上液 / GPIO15 激活 / 下舱到上舱 |
| 蓝色 | 降液 / GPIO16 激活 / 上舱到下舱 |
| 绿色 | 在线、待机安全、动作完成 |
| 琥珀色 | 请求中、暂停、状态过期、需要注意 |
| 红色 | 停止、故障、互锁冲突、通讯异常 |
| 深咖啡色 | 咖啡液体 |
| 暗红 + 深灰 | 机身与电气仓主色 |

颜色之外必须同时使用文字、方向箭头和图标，不能让色觉差异用户只凭颜色判断状态。

### 12.2 动画原则

- 动画服务于方向和状态识别，不追求复杂 3D。
- 使用 WPF 矢量形状、裁剪区域、渐变和轻量 Storyboard；避免高成本逐帧位图。
- 所有动画由业务状态驱动，窗口隐藏或最小化时降低刷新开销。
- 支持关闭动画/减少动态效果，关闭后仍能通过液位、箭头和文字读懂状态。

## 13. 分阶段实施计划

### M0：业务骨架清理与状态模型

- 应用更名为咖啡冷萃机上位机。
- 移除 `motor.*`、演示 users 表和无关示例入口。
- 建立 Domain、状态存储、指令注册和模拟传输层。
- 配置新的默认停靠布局。

验收：应用能在模拟模式启动；主画面、控制面板、GPIO 表共享同一状态。

### M1：中央三舱体与手动控制

- 实现三段主画面和液位/流向动画。
- 实现上液、降液、停止。
- 实现 GPIO15 / GPIO16 状态表及互锁告警。
- 控制台能用 `brew.up`、`brew.down`、`brew.stop` 完成同样操作。

验收：连续切换 100 次无双路同时有效、无 UI 卡死、动画与表格一致。

### M2：固定循环编排

- 上液、停留、降液、停留和循环次数参数。
- 启动、暂停、继续、终止。
- 时间线进度、当前循环与剩余时间。
- 参数校验和运行中锁定。

验收：多循环运行后步骤数、总时长、最终状态正确；中途停止可安全回待机。

### M3：串口设备接入

- 冻结通讯协议文档。
- 实现串口枚举、连接、心跳、超时、状态快照和命令确认。
- 模拟/设备模式使用同一业务接口。
- 完成 ESP32 联调；此阶段才进入嵌入式代码工作。

验收：拔线、重连、设备复位、重复消息和超时均有明确状态，不能误显示为成功。

### M4：历史、配方与产品化

- 运行记录、GPIO 事件和故障记录。
- 命名配方保存/加载。
- 视觉精修、部署打包、异常恢复和用户操作说明。

状态：0.4.0-M4 已完成。上位机已接入 JSON 持久化的运行历史与命名配方，控制面板提供配方保存/载入/删除和最近记录视图，控制台提供 `recipe.*` 与 `brew.history` 指令，用户操作说明见 `docs/咖啡冷萃机上位机_用户手册.md`。

## 14. 测试与验收清单

### 14.1 UI 与业务

- 上液时只允许 GPIO15 为激活，方向为下到上。
- 降液时只允许 GPIO16 为激活，方向为上到下。
- 停止、等待、待机时两路均关闭。
- 动画、状态栏、GPIO 表、控制按钮四处状态完全一致。
- 快速连续点击不会制造重复命令或非法并发状态。
- 关闭/浮动/恢复工具窗后状态不丢失。

### 14.2 编排

- 单循环和多循环步骤顺序正确。
- 暂停时计时停止，继续后不重复前一步。
- 运行中参数修改被禁止或明确延后生效。
- 中途终止进入停止阶段，并记录未完成原因。
- 应用异常退出后重新启动不得自动恢复危险输出。

### 14.3 通讯（M3）

- 未连接、连接中、在线、超时、断开五种状态可区分。
- 指令发送成功但未确认时不显示为动作已生效。
- 设备重启后上位机以新快照覆盖旧状态。
- 收到 GPIO15 和 GPIO16 同时有效时立即进入故障显示。
- 串口噪声、半包、错误包不会导致 UI 崩溃。

## 15. 已确认事项与待确认事项

### 15.1 已确认

- 上位机基于现有 AppShell 工程继续开发。
- 主窗口采用上舱体、电气仓、下舱体三段结构。
- 上液方向为下舱体到上舱体，降液方向相反。
- 底部需要显示每个引脚状态的表格。
- 控制面板需要上液、降液以及过程编排。
- GPIO15 / GPIO16 原型输出和黄/蓝灯点亮实验已经完成。
- 当前阶段只做上位机规划，不写嵌入式代码。

### 15.2 进入 M1 前需确认

1. GPIO15 是否最终固定对应黄灯/上液，GPIO16 是否固定对应蓝灯/降液。        对的，这事实上和电机接线有关，我们的文档规定GPIO15为上液，16为降液
2. “上液/降液”控制的是两只独立执行器、一个泵的两个控制端，还是泵与阀的组合。  分别是两个继电器连接两个泵（完全解耦）
3. 最终输出是高电平有效还是驱动板低电平有效。                              高电平有效NPN放大电路
4. 上、下舱体的有效容积以及一次完整转移的预计时间。                        时间是可以标定的，我们在控制中要设置一个完整转移时间标定（给文本框我自己输入）
5. 首版控制是点击后定时运行，还是必须按住按钮才运行。                      点击后就运行，按钮相关（后续嵌入式编程再考虑）
6. 是否已经具备液位、温度、门盖、压力等输入引脚；没有则 UI 只显示模拟/估算值。 本身就没有相关传感器，这里我们都是手动标定运行时间的只有电源显示这个后续再做
7. 黄、蓝仅用于开发验证，还是也会成为最终产品的固定状态色。                  可以直接固定，反正产品中不会有这个灯，我们可以再程序中弄一个黄灯和蓝灯（其实也没必要）

这些问题不会阻碍 M0 的业务骨架开发，但会影响设备控制和画面文案，必须在真实设备联调前关闭。

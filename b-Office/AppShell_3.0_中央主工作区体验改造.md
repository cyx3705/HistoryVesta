# AppShell 3.0 中央主工作区体验改造说明

> 状态：已实施；完整流水线、消费方回归和人工功能检测通过，获准随 3.0.0 正式发布；版本冻结延后
> 适用范围：AppShell 3.0 冻结前的 Shell 布局改造
> 性质：设计、实现与验收依据

## 1. 背景

当前 AppShell 已删除旧的固定主内容和 `page.*` 工作页体系，所有业务界面统一通过
`ToolWindowDescriptor` 注册。这消除了主页面与工具窗口两套生命周期，但现有 Shell 仍保留一个没有内容的
中央布局区域，而且当前没有窗口注册到该区域。

当窗口分别停靠在上方和下方时，二者围绕空中央区排列，形成明显的空白裂痕。它带来三个问题：

1. AppShell 独立启动后主窗口中心为空，看起来不像一个完整、可独立使用的应用框架。
2. 上下窗口在视觉上被无意义的空区隔断，内容关系割裂。
3. 中央区虽已存在 `DockSide.Center` 概念，却没有默认窗口和完整的主工作区呈现规则。

该问题属于 Shell 布局拓扑和窗口语义问题，不应由 OHS、WBall 或模块分别通过边距、背景色、固定高度或删除
布局文件来规避。

## 2. 改造目标

本次改造把中央区域定义为 AppShell 的**中央主工作区**，并以现有“命令集”窗口作为第一个默认中央窗口。

目标体验：

```text
┌──────────────────────────────────────┐
│ 上方工具窗口                         │
├──────────────────────────────────────┤
│                                      │
│ 中央主工作区                         │
│ 默认内容：命令集窗口                 │
│ 始终显示本区页面头与页面选择区域     │
│                                      │
├──────────────────────────────────────┤
│ 下方工具窗口                         │
└──────────────────────────────────────┘
```

改造完成后应满足：

- AppShell 独立启动时，命令集直接填充中央主工作区，不再出现没有承载内容的空白中心。
- 上、下、左、右工具窗口围绕中央主工作区停靠，窗口之间不存在空白裂痕。
- 中央始终显示自己的页面头和页面选择区域；只有命令集时也保留命令集标签，不能以上方工作区代替。
- 中央存在多个窗口时继续使用同一标签组，允许命令集与消费方业务窗口在主工作区切换。
- 中央窗口继续复用统一的注册、owner 回收、布局持久化和命令控制，不恢复旧页面体系。

## 3. 核心设计

### 3.1 命令集是默认中央窗口

当前没有任何页面或窗口注册到中央区。新实现不等待消费方提供业务首页，而是将框架已有的
`StandardWindowIds.Mcp` 命令集窗口默认放置到 `DockSide.Center`。

命令集适合作为默认中央内容，原因如下：

- 它是 AppShell 自身能力，不引入 OHS、WBall 等消费方业务。
- AppShell 独立运行时即可查看命令目录、选择命令并进入指令详情，主窗口具备实际用途。
- 前后端分离模式下，命令集仍可展示服务端权威目录，不需要复制业务页面。
- 消费方以后注册中央业务窗口时，可以与命令集组成同一个中央标签组。

命令集仍通过 `ToolWindowDescriptor` 注册，不恢复公开的 `ShellConfig.MainContent` 属性或第二套页面生命周期；
但在 Shell 内部，`DockSide.Center` 使用 AvalonDock 原生 `LayoutDocumentPane/LayoutDocument` 承载，而不是
`LayoutAnchorablePane` 工具窗。命令集存在时，它是固定主文档，不允许隐藏、浮动或停靠到四边。普通四边
工具页拖入中央时保留 `LayoutAnchorable` 身份，仅把父容器切换为主文档区，因此还能再次拖回四边。

### 3.2 `Center` 从几何位置升级为主工作区语义

`DockSide.Center` 不应只是“放到中间的另一种工具窗位置”，而应具备以下稳定语义：

| 状态 | 呈现规则 |
|---|---|
| 一个中央窗口 | 填满中央主工作区；显示本区页面头和当前页标签 |
| 多个中央窗口 | 共享中央区域；显示单层标签栏；当前窗口填满剩余空间 |
| 中央窗口切换 | 不改变上下左右工具窗尺寸，不重建内容实例 |
| 中央窗口隐藏或释放 | 命令集主文档不可隐藏或浮动；业务中央文档移除后激活其它文档 |
| 四边工具页拖入中央 | 作为中央标签页显示；仍可拖出、浮动或停回四边，owner 与内容实例不变 |
| 没有中央窗口 | 仅在命令集被显式禁用且消费方没有注册中央窗口时允许；显示统一背景，不自动提升侧边工具窗 |

中央窗口属于主工作区，因此不支持自动隐藏。命令集是固定主文档；业务中央文档隐藏、浮动或卸载时不得让
命令集随之离开主区。未启用命令集的消费方（例如以业务舞台为中心的应用）由自己的 `Center` 文档承载主区。

### 3.3 保持单一窗口模型

本改造不得恢复以下旧设计：

- `ShellConfig.MainContent` 或固定业务主页面。
- `page.list/open/activate/close` 等第二套页面命令。
- 与 `ToolWindowDescriptor` 并行的页面描述符、页面注册器和页面 owner 生命周期。
- 为 OHS 或某个模块硬编码中央页面。

中央主工作区只改变内部布局载体。窗口注册、创建、释放、owner 回收、命令寻址和布局保存仍走
`ToolWindowDescriptor` 与 `IDockingService`，消费方不接触 AvalonDock 文档类型。

## 4. 布局规则

### 4.1 初始布局

框架在建立标准窗口描述符时，将命令集作为默认 `Center` 窗口。控制台、资源、指令详情和模块管理仍按各自
描述符停靠；它们不得创建第二个空中央占位区。

默认布局应形成“一个原生文档主区 + 四周工具窗”的单一布局树，而不是“0.01px 空文档区 + 并排中央工具窗”。

### 4.2 中央页面头与选择区

中央工作区拥有独立于上方工具窗的页面头和页面选择区域。即使只有命令集，也显示命令集标签和选中状态；
第二个 `Center` 页面加入后直接出现在同一选择区。中央标签区不得借用上方工作区，也不得因只剩一个页面而
折叠，否则消费方无法确认中央容器边界或发现后续页面入口。

### 4.3 旧布局恢复

旧布局可能只包含上、下、左、右窗口，也可能把命令集保存为顶部窗口、普通标签页，或保存为 3.0 早期候选的
“0.01px 空文档区 + 并排中央工具窗”。恢复时遵循：

1. 若布局中已有合法中央窗口，尊重其中央标签顺序和当前选中项。
2. 若没有中央窗口但命令集可用，将命令集迁入中央主工作区。
3. 若旧布局引用已删除窗口，丢弃无效节点后仍必须建立合法中央主工作区。
4. 不通过删除整个用户布局解决迁移；框架应完成结构自愈并保存新布局。
5. 恢复失败时回到新的默认布局，而不是回到带空白裂痕的旧拓扑。

## 5. 消费方影响

### 5.1 OneHistoryStudio

OHS 当前没有中央注册页面，`overview` 位于顶部，命令集与其它窗口按工具窗方式布局。第一阶段无需先为 OHS
设计新的业务首页：框架升级后，由命令集填充中央主工作区，上方 `overview`、下方控制台及左右工具窗继续
围绕它停靠。

如果 OHS 后续决定让项目总览、继承树或其它业务界面成为中央内容，应显式注册为 `DockSide.Center`，与命令集
组成中央标签组，而不是重新引入 OHS 专属主页面通道。

### 5.2 模块

重型模块界面可选择 `DockSide.Center`，与命令集共享主工作区；属性、日志、资源等辅助窗口继续使用四周停靠。
模块卸载后，框架回收其中央标签并激活命令集，不留下空中央节点。

`DockSide` 是公开枚举。实施本改造时必须显式固定既有枚举数值，避免旧模块编译时的 `Tab` 数值在 3.0 中被
解释为 `Center`。如果决定不保持二进制枚举兼容，则必须要求所有 UI 模块随 3.0 重编译，并在升级手册中列为
阻断项，不能静默改变窗口位置。

## 6. 非目标

本次改造不包含：

- 为 AppShell 制作营销式首页、欢迎页或业务仪表盘。
- 改写命令集本身的业务功能和远端目录协议。
- 替换 AvalonDock 或全面重写停靠系统。
- 自动把任意顶部窗口判断为主窗口并迁移到中央。
- 改变工具窗口 owner、模块热重载或命令注册契约。

## 7. 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| CENTER-01 | AppShell 独立启动 | 命令集填满中央主工作区；不存在空中央裂痕 |
| CENTER-02 | 上下窗口同时可见 | 上方窗口、中央命令集、下方窗口连续排列，分隔条数量和位置合理 |
| CENTER-03 | 单中央窗口 | 显示中央自己的页面头和当前页面标签；缩放窗口时内容连续填充 |
| CENTER-04 | 多中央窗口 | 新页面进入同一中央标签组；切换不重建其它窗口，不改变四周布局 |
| CENTER-05 | 隐藏、浮动、卸载 | 命令集主文档不能离开中央；模块卸载后命令集仍承载中央区 |
| CENTER-06 | 旧布局迁移 | 无中央节点、命令集旧位置、0.01px 并排拓扑和已删除节点均能自愈，不要求用户删布局 |
| CENTER-07 | OHS 消费 | OHS 的顶部总览、中央命令集和底部控制台无空白裂痕；现有命令与窗口可用 |
| CENTER-08 | 模块兼容 | 旧 `DockSide.Tab` 不被误判为 `Center`，或所有受影响模块已明确重编译 |
| CENTER-09 | DPI 与尺寸 | 100%、125%、150%、200% DPI 及最小窗口尺寸下无重叠、裁切和跳动 |
| CENTER-10 | 布局持久化 | 保存、重启、恢复后中央标签顺序、当前项和四周比例保持一致 |
| CENTER-11 | 拖入与拖回 | 四边工具页可拖入中央成为标签页，再拖出或停回四边；保存恢复后位置一致 |

## 8. 收口条件

只有满足全部 `CENTER-*` 验收、AppShell Debug/Release 测试通过、OHS 使用真实 3.0 包完成 GUI 回归后，才能把
本文确定的行为合并进《通用窗口框架需求规划》《模块与 MCP 接入》和升级手册，并将本文从“待评审”改为
实施证据。仅调整颜色、边距或默认布局截图，不算解决中央主工作区问题。

## 9. 当前实施证据

2026-07-29 已将中央承载从 `LayoutAnchorablePane` 改为 `LayoutDocumentPane`：

- 命令集或消费方 `Center` 窗口直接成为主文档，不再与空文档锚点横向争夺宽度；
- 中央页面头与页面选择区始终显示，第二个中央文档加入同一标签组；
- 真实 WPF 视觉树断言主文档宽度超过主窗口 50%，覆盖“命令集缩在左侧”的回归；
- 早期候选的 `0.01px` 并排拓扑恢复后强制归一为 `*` 主文档宽度；
- Debug/Release 当前均为 0 warning / 0 error，含冻结审查整改回归在内的框架测试各 69/69 PASS。

完整候选流水线已通过：AppShell Debug/Release 均为 69/69，隔离 PackageSmoke 通过；OHS 使用候选 3.0 包的
Debug/Release 构建、Contracts 与 11 套 Smoke 均通过。本轮进一步恢复中央区自己的页面头与页面选择区域，
修正中央自愈逻辑抢回命令集焦点的问题，并开放四边工具页拖入中央、再拖回及布局持久化；上方项目视图仍是独立工具窗，不能替代中央页头。中央宽度超过
Shell 50% 由真实 WPF 视觉树测试断言。OHS 真实鼠标验收已完成“侧边页签拖出、浮窗拖入中央、中央页签
再次拖出、浮窗停回右侧”的完整往返，Debug 连续 3 次与 Release 1 次均通过；人工功能检测已通过，获准随 3.0.0
正式发布，tag/push 冻结动作延后。

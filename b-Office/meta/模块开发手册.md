# 模块开发手册

> 适用版本：OneHistoryStudio V2.7.7
> 框架基线：OneHistory.AppShell.* 3.0.0

## 当前架构

V2.4.0 起，模块托管是 AppShell 框架能力。框架的 `ShellWindow` 创建 `ModuleHost`、注册 `module.*` 指令、接管“模块管理”窗口，并在退出时释放文件监听器和加载上下文。派生应用不应再创建第二个模块宿主。

OneHistoryStudio 在框架能力之上增加两项应用集成：

- 项目库中的 `module.manifest.json` 发现、校验、SHA-256 溯源与模块槽同步；
- 模块重载完成后同步面板文件，并通过统一指令总线执行 `panel.reload`。

以上是 AppShell 3.0.0 与当前 OHS 的运行事实。其中“模块槽同步”仍指向应用数据目录的
`Modules\<name>`；下文的 z/Z 级目录直接消费是已经确定但尚未编程实现的下一代合同，不能据此判断
当前版本已经取消复制槽。

`ShellConfig.EnableModules` 默认是 `true`。设置为 `false` 时，框架不创建宿主、不注册 `module.*`，也不接管模块管理窗口。

开发时遵守三条边界：业务能力先注册命令、补齐 Help/MCP 元数据，再连接 UI；AppShell 公共契约、指令语法、
停靠核心和数据格式的改动按 AppShell 演进手册评审；OneHistoryStudio 不复制框架源码，也不为单个工具在
主程序中另建专用执行通道。模块按钮、脚本、控制台和 MCP 最终都应进入同一命令注册表。

跨桌面与 Service 宿主复用的内置命令，元数据只能写在 AppShell.Core 的共享定义中；桌面和 Service
注册点只绑定各自 handler 与宿主能力（例如桌面表窗口的 UI 线程同步）。禁止在两个宿主分别复制摘要、
示例、参数、只读性或确认策略。Help、命令目录、MCP、Web 和命令手册继续只读取最终注册表。

只在桌面执行的框架命令由 `FrontendCommandCatalog` 从真实桌面注册结果筛选，并为 Service 创建保留名称、
摘要、示例、参数、只读性和危险性的前端代理；代理仅把 `ExecutionSite` 标为 frontend，实际调用经前端会话
中继。新增或修改前端命令时不得在 OHS 维护命令名或参数白名单，生产 Service 目录与桌面源描述符必须由
Smoke 逐字段对账。共享内置命令则由 `BuiltinCommandDefinitions` 提供元数据，两个宿主只绑定 handler。

菜单动作也必须通过 `CommandBus.Validate` 对当前注册表做无副作用的命令名、参数和必填校验；菜单字符串
不是第二份命令真值。AppShell 标准窗口使用 `AppShell.Core.Docking.StandardWindowIds` 的常量，OHS
业务窗口 Id 由宿主自行定义，不得把两类身份混用。

## 两层发布与直接消费决策

模块及宿主产品统一采用两层发布模型：

| 层级 | 目录 | 合同 |
|---|---|---|
| 1 | `b-Publish` | 临时构建、发布候选、审核和历史版本归档区；允许按版本保存多个历史产物，不是运行时消费真值 |
| 2 | `z-Package`，或模块项目约定的 z/Z 级正式发布目录 | 正式发布与消费区；只保留最新的已验证正式版本，是后续装载和部署的唯一发布输入 |

OHS 自身的 `b-Publish` 细分为 `current`、`work/OneHistoryStudio`、`history/OneHistoryStudio` 和
`quarantine/OneHistoryStudio`；模块项目可以沿用同样职责命名。仓库根不再建立独立 `stage`。

`C:\OneHistory\OneHistory-Push` 是运行部署位置，不是第三层发布区。OHS 自身部署可以把 `z-Package` 的
正式快照事务替换到 `C:\OneHistory\OneHistory-Push\OneHistoryStudio`，但这个运行副本不产生新的发布
层级，也不得反向成为构建或模块消费来源。

模块的目标链路是：模块源码先在 `b-Publish` 形成候选并保留历史，通过校验与提升后，只把最新正式版本
放入项目的 z/Z 级正式发布目录；OHS 发现并批准该目录后，AppShell 直接把它作为只读模块来源装载。
链路中不再复制到额外的 `Modules\<name>` 注册槽，也不再把复制槽当作模块真值。`tool_registry` 届时只记录
来源、版本、哈希、准入和装载状态，不保存另一份正式模块实体。

该目标需要 AppShell 与 OHS 分工实现，不能只在一侧硬编码：

- AppShell 提供通用的多来源/外部只读模块目录装载合同，继续统一负责目录监听、可回收加载上下文、热重载、
  命令与 UI 注册、卸载和异常隔离。AppShell 不认识 OHS 项目库、worktree、z/Z 命名或 `tool_registry`。
- OHS 继续负责项目库与 worktree 枚举、z/Z 级一级目录发现、`module.manifest.json` 校验、来源冲突、安全准入
  和 MCP 暴露策略，再把通过验证的正式目录交给 AppShell。
- OHS 不创建第二个 `ModuleHost`，不绕过 AppShell 自行装载程序集；AppShell 也不直接扫描 OHS 项目库。

AppShell 3.0 是本仓冻结消费基线，当前 `ModuleHost` 只接受一个模块目录。因此通用装载合同应先在独立
AppShell 项目的下一条公共契约线（计划为 4.0）实现，OHS 再接入 z/Z 级发现结果并取消物理复制。
在该合同完成前，模块开发、注册器、`tool.sync` 和现有模块槽行为均保持不变；本节只形成架构决策，
不授权在 OHS 内临时实现第二套装载器。

## 模块文档与证据归属

模块需求、设计、实现、COM/第三方接口研究、诊断、转换样件结果和模块验收记录，必须保存在所属模块源码的
`b-Code-<Module>/docs`。模块注册元数据可以位于项目约定的 z/Z 级目录，但不得借注册或部署流程把模块文档
复制、汇总或上抛到 OHS 的 `b-Office`。

OHS 只记录由宿主产生的集成事实：发现的模块名称与版本、清单和部署物哈希、同步槽、注册/装载结果、命令或
窗口是否可用。`b-Office/evidence`、`versions` 和 `meta` 不接收模块原始请求、事件、日志、样件输出、实现测试
报告或完整模块文档。一次验收同时产生宿主事实和模块事实时必须拆分保存；OHS 需要追溯模块结论时只记录所属
项目及模块文档路径，不复制正文或附件。

## 模块目录和装载范围

当前 AppShell 3.0.0 的默认模块目录是应用数据目录下的 `Modules`。本地查询、打开、切换和重载：

```text
module.list
module.open
module.dir
module.dir path=C:\path\to\Modules
module.reload
```

模块管理页刷新时必须通过同一个 `CommandBus` 同时读取 `module.list` 与 `command.list`，形成一次不可拆分的
目录快照。所选模块的指令详情只接受 `Source=module` 且 `SourceDetail=<模块名>` 的条目；不得按命令名前缀
推断归属，也不得回退读取前端进程的本地 `CommandRegistry`。模块声明的指令数、目录条目和详情不一致时，
整次刷新失败并清空旧模块及旧详情；重载开始、选择失效或远端返回错误时同样不得保留上一代详情。

`module.dir` 持久化新目录并立即整体重载。宿主扫描两种布局：

```text
Modules/
├─ LegacyModule.dll              根目录平铺，兼容旧模块
├─ LegacyModule.xml
└─ ToolKit/                      一个一级目录就是一个模块槽
   ├─ ToolKit.dll
   ├─ ToolKit.xml
   ├─ ToolKit.panel.json
   └─ Dependency.dll
```

根目录 DLL 共用一个可回收加载上下文；每个一级模块槽使用独立的可回收 `AssemblyLoadContext`，依赖优先在本槽解析。宿主不递归把更深目录当成新模块槽。

清单声明 `"ui": true` 时，模块可实现 AppShell.Core 的 `IUiModule`；需要注册宿主工具窗口时再实现
`IShellUiAware`，宿主会在 `CreateUi()` 前注入 `IShellUiRegistrar`。只有前端宿主创建模块 UI；
服务宿主只扫描业务命令，绝不实例化 View/ViewModel。重载/卸载时框架先调用 `DestroyUi()`，再按
owner 兜底注销全部工具窗口，最后卸载旧上下文。普通命令模块无需改动。

## 内嵌工具窗口

`IShellUiRegistrar` 只提供普通工具窗口注册。窗口可隐藏、拖动、浮动、重新停靠和最大化；中央区是空背景，
不再提供主内容或工作页。Core 契约只使用 `object` 内容工厂，不向模块暴露 AvalonDock 类型。

```csharp
public sealed class ExampleUiModule : IUiModule, IShellUiAware
{
    private IDisposable? _window;
    public IShellUiRegistrar ShellUi { private get; set; } = null!;

    public void CreateUi() => _window = ShellUi.RegisterToolWindow(new ToolWindowDescriptor
    {
        Id = "example",
        Title = "示例窗口",
        DefaultSide = DockSide.Right,
        DefaultRatio = 0.4,
        ContentFactory = static () => new ExampleView(),
    }, "Example");

    public void DestroyUi()
    {
        _window?.Dispose();
        _window = null;
    }
}
```

界面 ID 必须是进程内唯一、稳定的小写地址。模块应保留并释放注册句柄；即使模块漏做，框架也会在 ALC
卸载前执行 owner 清理。工具窗口关闭表示隐藏，内容仍可用 `win.show` 唤回。模块不得自行创建生产顶层 `Window`，也不得
直接使用 `Application.Current.Dispatcher`；跨线程操作统一走 `IShellUiRegistrar.Invoke`。

工具窗口统一允许浮动，使用 Shell 的带点蓝色标题拖动条拖出或重新停靠。双击该蓝色标题条切换最大化/恢复；
不要把双击绑定到上方标签。

窗口管理命令：

```text
win.list
win.show name=example
win.hide name=example
win.float name=example
win.dock name=example side=right
win.max name=example
win.restore
```

## 最小模块契约

宿主按基类完整名称 `BaseVariable.ModuleInfoBase` 识别模块，不要求模块引用某个固定路径的 SDK DLL。模块可把兼容契约类编译进自身，也可以引用独立契约程序集。

```csharp
namespace BaseVariable;

public abstract class ModuleInfoBase
{
    public virtual string ModuleName => GetType().Assembly.GetName().Name ?? "UnknownModule";
    public virtual string Description => "";
    public virtual string Author => "";
    public virtual string Version => "v1.0.0";
    public virtual bool Open => false;
    public virtual Type? MainClassType => null;
    public virtual bool Enabled => true;
}
```

属性语义：

| 属性 | 作用 |
|---|---|
| `ModuleName` | 指令域名，方法最终注册为 `<ModuleName>.<Method>` |
| `Description` / `Author` / `Version` | `module.list` 和模块管理页显示的元数据 |
| `Enabled` | `false` 时整个模块跳过 |
| `Open=false` | 精准暴露，只扫描 `MainClassType` |
| `Open=true` | 全暴露，扫描程序集内全部公共业务类 |

推荐使用精准暴露，明确指定一个无歧义的业务入口类。全暴露会把所有符合条件的公共方法纳入命令面，适合边界清晰的小型模块。

## 方法到指令的映射

宿主收集公共、非泛型、非属性访问器方法，并生成 `<模块名>.<方法名>`。支持：

- 实例方法与静态方法；
- 同步返回值与 `Task` / `Task<T>`；
- 字符串、布尔、整数、浮点、枚举和可空参数；
- 默认参数；
- 原始值直接回显，复杂对象序列化为 JSON。

同一模块内生成同名指令时跳过后项；与框架、应用或其他模块命令重名时拒绝该命令，不覆盖既有注册。模块异常会去掉反射包装后交给统一命令总线记录。

模块每次换血前，`ModuleHost` 从当前注册表中排除旧模块命令，再按命令名第一个点号前的一级域动态计算宿主
保留域。候选模块的任一命令域与宿主域冲突时，该候选域的命令全部拒绝并记录警告；新增宿主命令域会自动
进入保护范围，不得再维护平行的 `BuiltinDomains` 名单。不同模块之间的同名命令仍由注册表逐项拒绝。

建议为项目启用 XML 文档：

```xml
<PropertyGroup>
  <TargetFramework>net8.0</TargetFramework>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
</PropertyGroup>
```

相邻的同名 XML 文件为 Help、命令集和 MCP 提供方法摘要与参数说明。缺少 XML 时指令仍可用，但会回落为通用描述。

## 最小开发流程

1. 创建 `net8.0` 类库。
2. 提供兼容的 `BaseVariable.ModuleInfoBase` 子类。
3. 以 `Open=false` 指向业务入口类。
4. 为公开方法写 XML Summary 和参数说明。
5. Release 构建 DLL 与 XML。
6. 把 DLL、XML 和依赖放入独立模块槽。
7. 用 `module.list`、`help command=<模块.方法>` 和命令集页面验收。

当前随附示例会生成 `DemoModule.dll` 和 `DemoModule.xml`，精准暴露 `Calculator` 的 `Add`、`SayHello`、`Now` 和 `Reverse`。

## 热重载

`ModuleHost` 递归监听模块目录中的 `.dll`、`.xml` 和 `.panel.json`，文件事件静默 800 毫秒后整体重载：

1. 从磁盘构建新模块快照；
2. 在 UI 线程注销旧模块命令并注册新命令；
3. 替换当前快照；
4. 卸载旧的可回收加载上下文；
5. 触发 `ReloadCompleted`。

DLL 和依赖从内存流读取，正常情况下不会长期锁住磁盘文件。复制仍在进行时会短暂重试读取。坏 DLL、缺失依赖或实例化失败只使对应模块下线并记录警告，不应拖垮宿主。

手工更新时优先构建到临时位置，再替换完整模块槽，避免 DLL、XML 和依赖处于不同版本。通常无需执行 `module.reload`；它用于文件监听异常或人工复验。

## 模块面板

模块可附带 `<模块名>.panel.json`。AppShell 启动前会把模块旁面板同步到应用 `panels` 目录，OneHistoryStudio 也会在模块重载后再次同步：

- 已有面板通过 `panel.reload` 原地更新；
- 新面板窗口需要重启后进入停靠布局；
- 模块下线后，只回收 `module-` 前缀的同步副本，不触碰用户手写面板；
- 面板 ID 冲突由现有面板管理器拒绝并告警。

## OneHistoryStudio 工具清单

`module.manifest.json` 不是 AppShell 3.0.0 装载模块的前提，而是 OneHistoryStudio 从项目库发现、同步和追踪工具的应用层清单。清单位于项目的 z/Z 级一级元文件夹中。

示例：

```json
{
  "name": "ToolKit",
  "version": "1.0.0",
  "description": "常用工具",
  "artifact": "z-ToolKit/bin/Release/net8.0/ToolKit.dll",
  "docs": "z-ToolKit/bin/Release/net8.0/ToolKit.xml",
  "panel": "z-ToolKit/ToolKit.panel.json",
  "deps": [],
  "mcpExposure": "readonly",
  "ui": false
}
```

字段规则：

- `name` 和 `artifact` 必填；名称必须匹配 `^[A-Za-z_][A-Za-z0-9_-]{0,63}$`，且不能占用内置指令域。
- `artifact`、`docs`、`panel`、`deps` 必须是所属 worktree 内的相对路径，绝对路径和越界路径拒绝。
- `docs` 省略时会尝试使用 DLL 旁同名 XML。
- `mcpExposure` 只允许 `standard`、`readonly`、`hidden`，默认 `standard`。
- `ui` 缺省 `false`；设为 `true` 时 `tool.sync` 会把清单复制到模块槽，供宿主启用 UI 生命周期。

管理命令：

```text
tool.scan
tool.sync name=ToolKit
tool.sync all=true
tool.list
tool.remove name=ToolKit
```

当前实现中，`tool.sync` 重建 `Modules\<name>\` 槽，复制 DLL、XML、清单、面板和依赖，复核产物 SHA-256，再写入 `tool_registry` 溯源。文件监听器随后自动接手装载。根目录平铺且没有溯源记录的旧模块，MCP 暴露默认按 `standard` 处理。该行为会在 AppShell 的多来源装载合同和 OHS 适配共同完成后，按“两层发布与直接消费决策”迁移；当前版本不得提前删除复制槽。

## MCP 暴露

模块命令先进入统一注册表，再由 MCP 策略解释：

- `standard`：仅在 MCP 的 standard 策略下可见；
- `readonly`：readonly 与 standard 策略均可见；
- `hidden`：始终不对 MCP 暴露；
- 带本地确认的危险命令仍受危险指令规则约束，清单不能绕过；
- 内置硬排除规则优先于模块清单。

OneHistoryStudio 根据指令注册来源 `module:<name>` 查询 `tool_registry` 的暴露档位。Help、命令集与网关使用同一策略真值。

模块热重载后，程序内命令会立即更新；MCP 服务端下一次 `tools/list` 也按新注册表计算。Codex 等客户端可能缓存工具列表，通常需要新建任务才能看到新增或移除的模块命令。

## 验收清单

以下清单验证当前 AppShell 3.0.0 模块槽实现；z/Z 级正式目录直接消费需要在下一代合同落地时另增验收项。

1. `module.list` 显示模块名、版本、精准/全暴露、槽和指令数。
2. `help command=<模块.方法>` 显示 XML 摘要、参数、默认值与示例。
3. 命令集页面显示来源 `module:<模块名>`。
4. `command.show` 与 `mcp.schema` 对同一指令的参数一致。
5. 替换 DLL 后旧命令消失、新命令出现，删除 DLL 后命令下线，过程不需要重启宿主。
6. 坏 DLL、缺失依赖和模块方法异常只下线或终止对应模块调用，不影响宿主与其他模块。
7. 模块命令与内置命令或其他模块重名时拒绝新命令，不覆盖已注册能力。
8. `tool.list` 中的来源、版本、哈希和槽状态正确。
9. 面板更新后已有窗口可刷新；新面板在重启后出现。
10. 新建 Codex 任务后，MCP 工具列表符合 `mcpExposure` 与当前策略。

## 常见问题

- **模块未出现**：确认 DLL 目录层级、程序集内存在启用的 `ModuleInfoBase` 子类，并查看控制台 `module` 警告。
- **指令数为 0**：精准暴露的 `MainClassType` 为空，或入口类没有可托管的公共方法。
- **依赖加载失败**：把非框架依赖放入同一模块槽，避免依赖散落到其他槽。
- **摘要为空**：确认生成 XML 文档，文件名与 DLL 相同并放在同一槽。

# V3.0 OneHistoryStudio 整体模块化迁移

> 日期：2026-08-07
> 状态：研究完成，施工文档待审核；本阶段不修改 OHS 源码、版本号、AppShell 或发布包

## 目标

V3.0 将 OneHistoryStudio 从“自带 UI 与 ServiceHost 的独立 EXE”迁移为 AppShell 的一个完整业务模块。
AppShell 成为唯一桌面宿主和后台服务宿主；OHS 只交付可被模块注册器装载的业务 DLL，不再交付
`OneHistoryStudio.exe`、第二套 `ServiceHost`、第二套 `ShellWindow`、第二套模块注册器或第二套 MCP/Web 网关。

公开命令名、端口、数据目录、Git 行为、LAN 配对协议、MCP/Web 协议和用户工作流保持不变。
本迁移不是重写业务，也不是把 OHS 代码复制到 AppShell 仓库。

## 当前事实

### OHS 2.9.1

- `b-Code-Studio/Studio.csproj` 当前是 `WinExe`，业务、WPF 页面、连接/LAN、Git、命令注册和服务组合均在一个产品工程内。
- `Program.cs` 同时承载 UI、`--service-host`、`--generate-manual` 和 LAN 安装入口；`App.xaml.cs` 负责客户端连接、窗口表和前端命令代理。
- `Service/StudioServiceCompositionFactory.cs` 创建 `CommandRegistry`、`ProjectService`、Git 规则、分支历史、工具同步、MCP、WebGateway、LAN 发现和模块宿主。
- 服务端当前注册约 81 条 OHS 命令，命令处理器主要使用 `CommandDescriptor`、复杂 DTO、确认服务、设置、日志和数据目录，不是无状态的简单反射方法。
- 当前正式 `z-Package` 是包含 EXE、AppShell 运行库、帮助文档和 manifest/checksum 的 2.9.1 产品包。

### AppShell 当前能力

AppShell 源码工作线当前为 3.1.2，3.0.3 仍是已冻结消费基线。3.1.2 工作树正在开发，未提交的源码不作为
OHS 施工依赖；V3.0 必须只消费 AppShell 自己正式发布的 Z 级快照。

当前宿主已经具备以下模块能力：

- `AppShell.Services.Modules.ModuleHost` 从数据目录 `Modules` 扫描根 DLL 和一级模块槽目录。
- 每个槽使用可回收 `AssemblyLoadContext`；文件变化 800ms 防抖后整体换血，旧 UI、命令、快捷键和 ALC 会被回收。
- 通过公共 `BaseVariable.ModuleInfoBase` 的全名进行模块元信息识别，支持精准暴露 `MainClassType` 或全量公共方法暴露。
- 通过 `IUiModule`、`IShellUiAware` 和 `IShellUiRegistrar` 注册/销毁嵌入式工具窗口；`ToolWindowDescriptor` 已包含稳定窗口 ID、默认停靠侧和比例。
- 服务宿主可关闭 UI 模块，只加载命令模块；前端 Shell 可启用 UI 模块。模块命令来源投影为 `module:<name>`，宿主拒绝与保留命令域冲突。
- `module.list`、`module.reload` 和 `module.dir` 已有宿主管理入口；XML 注释可生成模块命令帮助。

这些能力足以承载轻量示例模块，但还不足以直接承载 OHS 当前服务组合。

## 目标边界

| 责任 | AppShell 宿主 | OneHistoryStudio 模块 |
|---|---|---|
| 进程与窗口 | `AppShell.exe`、单实例、ShellWindow、停靠布局、控制台、模块管理 | 注册 OHS 业务工具窗口及其内容工厂 |
| 后台服务 | `AppShell.exe --service-host`、ServiceHost 生命周期、单实例、事件循环 | 注册 OHS 服务组合、业务命令和延迟启动任务 |
| 命令 | CommandRegistry、总线、确认路由、来源和冲突门禁 | OHS 81 条业务命令及其数据反序列化 |
| MCP/Web | 网关、回环监听、认证/确认/审计和前后端转发 | OHS 命令的模块暴露策略、LAN 发现扩展和业务响应 |
| 数据 | 宿主基础目录与模块目录发现 | 继续使用 `%APPDATA%\OneHistoryStudio` 下的设置、数据库、Git 状态、日志和 token |
| 更新 | 模块扫描、热重载、模块版本/manifest 校验 | 只交付当前 OHS 模块 DLL 及必要旁车文件 |
| AppShell 代码 | 由 023 单独维护 | OHS 不复制、不修改 AppShell 源码 |

## 必须先补齐的宿主合同

### 1. 服务模块组合接口

现有 `ModuleInfoBase` 反射路径没有依赖注入，也没有服务生命周期；OHS 无法通过它安全创建
`ProjectService`、`HistoryRecorder`、`WebGateway` 和 LAN 发现器。AppShell 需要在正式版本中提供稳定的服务模块合同，建议形态为：

- `IServiceModule`：由 ServiceHost 在注册表、设置、日志、数据根和网关准备后调用 `Configure`，在退出或热重载时调用 `Dispose`。
- `IModuleContext`：至少提供 `CommandRegistry`、`ISettingsService`、`IShellLog`、模块专属数据根、确认服务、模块来源名和取消令牌。
- `IModuleWebRegistration` 或等价窄接口：允许模块挂载业务健康检查、LAN 发现/配对所需的宿主扩展；模块不得直接持有宿主私有 `WebGateway` 实例。
- 模块注册的命令统一带 `module:OneHistoryStudio` 来源，MCP 策略从 manifest/模块声明读取，不允许模块绕过宿主网关直接开放端口。

具体接口名可由 AppShell 决定，但能力必须稳定、可测试、可在服务宿主和前端 UI 两侧复用。

### 2. UI 模块生命周期

OHS 模块实现 `IUiModule + IShellUiAware`。`CreateUi` 中仅通过 `IShellUiRegistrar` 注册窗口，
不直接访问 AvalonDock；`DestroyUi` 必须释放事件、计时器、服务客户端和窗口所有权。模块窗口 ID 保持现有合同：

`overview`、`tree`、`meta`、`projops`、`history`、`connection.settings`，以及需要保留的稳定布局关系。

模块管理、控制台、命令详情、MCP 和资源窗口由 AppShell 提供，OHS 不再重复注册这些窗口。

### 3. 模块数据根

AppShell 的默认 `AppPaths` 以宿主身份建立目录；OHS 不能因为换宿主而把用户数据迁移到 `%APPDATA%\AppShell`。
宿主合同必须允许模块声明稳定数据键 `OneHistoryStudio`，或者向模块上下文注入等价的产品数据根。

V3.0 保留以下路径及内容：

- `%APPDATA%\OneHistoryStudio\data\main.db`
- `%APPDATA%\OneHistoryStudio\settings.json`
- `%APPDATA%\OneHistoryStudio\Modules` 与 `panels`
- LAN 设备、配对 token、证书指纹和日志目录

首次启动不得重建数据库、清空 token、修改项目 bare repo 或改变默认服务器/客户端角色。

### 4. 命令与复杂结果

AppShell 当前反射绑定只覆盖字符串、整数、浮点数、布尔值和 JSON 返回；OHS 现有命令还包含复杂 DTO、枚举、
批量规则、Git 目标、服务响应和确认边界。因此迁移采用两层策略：

1. OHS 业务服务继续保留现有强类型实现和序列化映射。
2. 模块组合接口负责把现有 `CommandDescriptor` 原样注册到宿主 Registry，而不是把 81 条命令机械改写成反射方法。

命令名称、参数名、只读/确认属性、MCP 投影和错误消息保持现状；宿主只负责总线执行和来源标记。

## OHS 模块内部结构

施工时将现有 `b-Code-Studio` 重组为一个模块工程（可暂时保留目录名，避免无关路径迁移），建议边界如下：

- `Module/OneHistoryStudioModule.cs`：模块元信息、宿主组合入口、版本和释放合同。
- `Module/OneHistoryStudioServiceModule.cs`：服务侧组合，创建 OHS 数据服务并向宿主注册现有命令。
- `Module/OneHistoryStudioUiModule.cs`：UI 注册和工具窗口生命周期。
- `Git/`、`Connection/`、`Service/`：继续按功能内聚，不为满足文件行数机械拆分。
- `Views/`：保留 WPF 页面和当前停靠比例；移除仅属于独立 EXE 的 `Program`、`App` 和二次 `ShellWindow` 装配。

OHS 模块不得再创建 `ServiceHost`、`McpGateway`、`WebGateway`、`ModuleHost` 或 `ShellWindow` 实例；这些对象由
AppShell 创建并通过窄合同提供能力。

## 发布形态

V3.0 的 OHS `z-Package` 改为模块消费区，只保存最新经过验证的 OHS 模块快照。正式产物为：

- `OneHistoryStudio.dll`：唯一业务模块主体；不生成 `OneHistoryStudio.exe`。
- `OneHistoryStudio.xml`：模块命令帮助旁车文件；若宿主最终改为 manifest 内置帮助，才可取消。
- `module.manifest.json`：至少声明 `name=OneHistoryStudio`、`version=3.0.0`、`ui=true` 和模块暴露策略。
- `SHA256SUMS`/正式 manifest：记录上述文件、源码 commit、宿主合同版本和模块版本。

不进入 OHS 模块正式包：AppShell 四个 DLL、runtimeconfig/deps、独立帮助目录、旧 EXE、旧 Service 进程入口、
临时构建目录和测试证据。AppShell 运行包只从 023 的 `z-Package-AppShell` 消费。

`b-Publish` 仍只保存当前候选、旧正式模块包历史和事务目录；`C:\OneHistory\OneHistory-Push` 不再直接消费
OHS 模块包，部署管道负责把 z 级模块快照同步到 AppShell 宿主的模块目录并触发热重载。

## 迁移顺序

1. **AppShell 合同冻结**：完成并发布服务模块上下文、数据根、Web 扩展、生命周期释放和模块 manifest 版本合同；只消费 023 正式快照，不引用 023 工作树。
2. **模块骨架**：将 OHS 工程改为模块类库，建立 `ModuleInfoBase`、`IServiceModule`、`IUiModule` 双侧入口；先装载空模块并验证热重载。
3. **服务迁移**：把 `StudioServiceCompositionFactory` 的业务组合迁入服务模块，删除 OHS 自有 ServiceHost/MCP/Web 创建；逐条核对 81 条命令和 `module:OneHistoryStudio` 来源。
4. **UI 迁移**：把 `App.xaml.cs` 的窗口表迁入 `OneHistoryStudioUiModule`，删除第二套 Shell 装配，确认客户端远程连接和服务器本地 UI 都能工作。
5. **数据兼容**：使用原 `%APPDATA%\OneHistoryStudio` 数据根启动，验证数据库、设置、设备 token、LAN 指纹、布局和 Git 项目均原地复用。
6. **模块候选**：Debug/Release 构建、模块合同、AppShell 宿主 Smoke、OHS 定向 Smoke、热重载和前后端分离全绿；候选只放 `b-Publish/candidate`。
7. **正式提升**：manifest、SHA-256、模块依赖与宿主版本复核后，原子替换 `z-Package`；旧 EXE 进入一个版本周期的回滚区，不再作为正式产物。
8. **切换与清理**：由模块部署管道把 DLL 同步到 AppShell 的 `Modules` 槽，人工验收后停止旧 OHS EXE；保留旧数据库和回滚包，不执行自动数据迁移。

## 测试与门禁

- AppShell 合同：服务模块注册/释放、UI 注册/销毁、模块专属数据根、命令来源、MCP 暴露和 Web 扩展。
- 模块装载：缺 DLL、坏 XML、错误 manifest、重复命令域、依赖冲突、热重载 10 次、旧 ALC 可回收和失败模块隔离。
- OHS 命令：81 条命令名称/参数/确认属性、复杂 DTO 反序列化、命令手册数量与 SHA-256、MCP readonly/operate/admin 投影。
- UI：六个 OHS 业务窗口注册、默认停靠比例、客户端远程连接、服务器本地模式、关闭/重载后无残留窗口。
- 数据与协议：原数据根、数据库、设置、token、LAN 自动发现、HTTPS 指纹、8738/TCP、MCP 回环和前后端分离。
- 发布静态门禁：正式包只有模块 DLL、XML、manifest 和 checksum；不存在 OHS EXE、独立 Service EXE、AppShell 运行库复制品。
- Debug/Release 构建与定向 Smoke 日常执行；完整宿主/模块 Smoke、帮助、正式包、部署和回滚只进入发布候选。
- 不执行开机自启动测试；真实 UAC、防火墙、双机 LAN 和用户数据升级留作发布候选人工验收。

## 不变项与非目标

- 不修改公开命令名称、端口、数据库 schema、Git 提交/推送语义、LAN 配对合同和 MCP/Web 协议。
- 不在 OHS 中保留一层“薄 ServiceHost”兼容入口；V3.0 完成后唯一宿主是 AppShell。
- 不把 AppShell 3.1.2 未提交工作树当作依赖；模块只引用正式 AppShell 包版本。
- 不顺带升级 AppShell 的视觉设计、资源模块或其他消费项目。
- 不在本文件阶段修改 `StudioVersion.props`、代码、正式包或部署；施工完成后再提升 OHS 到 `3.0.0`。

## 验收结论

只有同时满足“AppShell 宿主合同已正式发布”“OHS 模块 DLL 可在服务/前端两侧装载”“原数据和 81 条命令行为不变”
以及“z-Package 不含任何 OHS EXE”四项条件，才允许把 V3.0 标记为正式完成。

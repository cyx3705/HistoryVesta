# V3.0 OneHistoryStudio 整体模块化迁移

> 日期：2026-08-07
> 状态：AppShell 3.1.7 正式宿主已发布；OHS 模块施工尚未开始。本文只定义迁移合同，不修改源码、版本号、正式包或部署。

## 目标

V3.0 将 OneHistoryStudio 从“自带 UI、ServiceHost 和前后端代理的独立 EXE”迁移为 AppShell 的一个完整业务模块。
AppShell 成为唯一桌面宿主和后台服务宿主；OHS 最终只交付可被模块注册器装载的业务 DLL，不再交付
`OneHistoryStudio.exe`、第二套 `ServiceHost`、第二套 `ShellWindow`、第二套模块注册器或第二套 MCP/Web 网关。

公开命令名称、参数、端口、数据目录、Git 行为、LAN 配对协议和 MCP/Web 协议保持不变。本迁移不重写业务，也不复制或修改 AppShell 源码。

## 当前事实

### OHS 2.9.1

- `b-Code-Studio/Studio.csproj` 当前仍是 `WinExe`；业务服务、WPF 页面、LAN、Git、命令注册和旧服务组合仍在同一产品工程内。
- `Program.cs` 仍承载 UI、`--service-host`、`--generate-manual` 和 LAN 安装入口；`App.xaml.cs` 仍承载窗口表、前端连接和远程命令代理。
- `Service/StudioServiceCompositionFactory.cs` 仍是旧 EXE 的兼容宿主适配层；V3 施工分支已经把 OHS 业务组合抽成可注入边界，但尚未删除旧宿主。
- 当前正式 OHS 包仍是 2.9.1 产品包。V3 完成后，OHS 的 `z-Package` 只保存 OHS 模块快照。

### AppShell 3.1.7 正式消费合同

唯一正式宿主快照为：

`C:\OneHistory\OneHistory-Projects\2026-023-AppShell\z-Package-AppShell`

- 正式入口：`host/AppShell.exe`。
- 正式快照身份由 `manifest.json` 与 `SHA256SUMS` 校验。
- manifest 权威字段：`version=3.1.7`、`sourceCommit=d50234589ccd420eb5b26e18b4894c22a347b5e8`、`sourceDirty=false`。
- 3.1.7 正式部署交付完整宿主快照，不提供当前 NuGet feed；兼容嵌入消费方如需四个框架包，必须使用单独批准的同版本包源。
- 3.1.7 已提供 `ModuleHost`、可回收模块槽、模块命令目录、命令来源投影、模块卸载/热重载、`IUiModule`、`IShellUiAware`、`IShellUiRegistrar`、唯一模块管理页和 `module.*` 管理命令。
- 消费方必须显式启用 `EnableModules`；只有需要界面模块时才启用 `EnableUiModules`。模块默认从应用数据目录的 `Modules` 及其一级模块槽加载。

## 责任边界

| 责任 | AppShell 宿主 | OneHistoryStudio 模块 |
|---|---|---|
| 进程与窗口 | `AppShell.exe`、单实例、`ShellWindow`、停靠布局、控制台和标准窗口 | 注册 OHS 业务窗口及内容工厂 |
| 后台服务 | `ServiceComposition`、`ServiceHost` 生命周期、服务事件循环和统一释放 | 提供 OHS 业务组合及命令注册入口 |
| 命令总线 | `CommandRegistry`、`CommandBus`、确认、命令来源和冲突门禁 | 注册 OHS 业务 `CommandDescriptor`，保持现有命令语义 |
| MCP/Web | 网关、监听、鉴权、确认、审计、前后端中继 | 声明 OHS 命令的暴露策略和 Web/LAN 业务扩展需求 |
| 模块运行时 | manifest 解析、依赖/冲突、模块槽、加载、卸载、热重载和管理页 | 提供模块 manifest、DLL、XML 和面板声明 |
| 数据 | 宿主提供应用身份、设置、日志、确认通道和模块上下文 | 继续使用兼容的 OHS 数据目录、Git 状态、历史和 token |
| 项目资料 | 不理解项目仓库语义 | 管理项目 worktree、Git 规则、发布区和项目级资料 |

## 模块元数据责任边界

AppShell 负责模块运行时元数据：模块 manifest 的发现与校验、版本和入口 DLL、命令域冲突、依赖、加载状态、模块槽、生命周期和热重载。
AppShell 3.1.7 不扫描全局 `OneHistory-Projects\\*\\z-*`，也不理解项目中的 `z-Package`。

OHS 继续负责项目库元数据：worktree 下的 `z-*` 元文件夹、Git 文件规则、模板基线、`b-Publish`、`z-Package` 以及项目文档和历史。
发布管道负责把审核通过的 OHS 模块快照从 OHS `z-Package` 同步到 AppShell 应用数据目录的 `Modules` 模块槽；AppShell 只消费已同步的正式模块目录。

因此，OHS 不再复制 `ModuleHost`、模块管理页面或第二套 manifest 运行时；项目层的 `ToolSyncService` 后续只保留项目清单治理，宿主模块安装、加载和热重载归 AppShell 或独立部署管道所有。

## 尚未具备的宿主合同

AppShell 3.1.7 已能承载宿主级 `ServiceComposition` 和 `ServiceHost`，但还没有为 OHS 这类完整业务模块冻结以下公开合同：

- 服务模块注册、配置、释放和热重载生命周期；
- 模块专属数据根，同时保持 `%APPDATA%\\OneHistoryStudio` 数据兼容；
- 外部模块向宿主注册复杂 `CommandDescriptor`、确认通道和命令来源的稳定入口；
- OHS Web/LAN 健康检查、发现、配对和服务扩展的宿主注册接口。

`IServiceModule`、`IModuleContext`、`IModuleWebRegistration` 等名称在本文件中仅作为待设计能力的描述，不是 AppShell 3.1.7 已发布 API。OHS 施工不得提前引用这些假定接口。

## OHS 模块内部结构

OHS 对模块注册器只发布一个模块，源码内部按功能内聚分层：

- `Module/OneHistoryStudioModule.cs`：模块身份、宿主组合入口、版本和释放合同。
- 业务服务层：项目、Git 规则、分支历史、历史记录、格式库存和连接业务。
- 命令适配层：保留现有 `CommandDescriptor`、参数、确认、DTO 和反序列化语义，注册到宿主总线。
- UI 层：概览、继承树、Meta、项目操作、历史和连接页面，通过 `IUiModule`/`IShellUiRegistrar` 注册。

模块不得创建 `ServiceHost`、`McpGateway`、`WebGateway`、`ModuleHost` 或 `ShellWindow` 实例，也不得直接依赖 AppShell 内部 AvalonDock 类型。

## 正式发布形态

V3.0 OHS `z-Package` 改为模块消费区，只保存最新经过验证的 OHS 模块快照。正式产物为：

- `OneHistoryStudio.dll`：唯一业务模块主体；
- `OneHistoryStudio.xml`：模块命令和 API 帮助；
- `module.manifest.json`：至少声明 `name=OneHistoryStudio`、模块版本、UI 能力和 MCP 暴露策略；
- `SHA256SUMS` 及正式 manifest：记录模块文件、来源提交和宿主合同版本。

不进入 OHS 模块正式包：AppShell 宿主 DLL、runtimeconfig/deps、独立帮助目录、旧 OHS EXE、旧 Service 入口、临时构建目录和测试证据。
AppShell 运行包始终从 023 的 `z-Package-AppShell` 消费。

## 迁移顺序

1. **宿主基线确认**：固定消费 AppShell 3.1.7 `z-Package-AppShell`，核对 manifest、文件清单和 SHA-256；不引用 AppShell 工作树。
2. **单模块骨架**：将 OHS 工程迁移为模块程序集，完成模块 manifest、UI 入口和宿主命令注册适配。
3. **UI 迁移**：把现有业务窗口迁入 `IUiModule`，删除第二套 Shell 装配，确认默认停靠和卸载后无残留窗口。
4. **服务合同冻结后迁移**：将现有 OHS 业务组合接入宿主服务模块上下文，删除 OHS 自建 ServiceHost、MCP/Web 生命周期和前端代理。
5. **数据兼容**：使用原 `%APPDATA%\\OneHistoryStudio` 数据根，验证数据库、设置、设备 token、LAN 指纹、布局和 Git 项目均原地复用。
6. **模块候选**：执行模块合同、宿主装载/卸载/热重载、OHS 定向 Smoke 和前后端分离验证；候选只进入 `b-Publish/candidate`。
7. **正式发布**：核对 module manifest、SHA-256、OHS 模块版本和 AppShell 3.1.7 宿主版本后，更新 OHS `z-Package`。
8. **切换与清理**：由部署管道把 OHS 模块同步到 AppShell `Modules` 槽，人工验收后停止旧 OHS EXE；保留旧数据库和回滚包，不执行自动数据迁移。

## 测试与门禁

- AppShell 合同：模块发现、命令来源、UI 注册/销毁、模块槽隔离、热重载、失败模块卸载和生命周期释放。
- OHS 命令：现有命令名称、参数、确认、DTO 反序列化、命令手册数量和 MCP 投影保持不变。
- UI：六个 OHS 业务窗口注册、默认停靠、客户端远程连接、服务器本地模式和卸载后无残留窗口。
- 数据与协议：原数据根、数据库、设置、token、LAN 自动发现、HTTPS 指纹、8738/TCP、MCP 回环和前后端分离行为保持兼容。
- 发布静态门禁：正式 OHS 包只有模块 DLL、XML、manifest 和 checksum，不含 OHS EXE、独立 Service EXE 或 AppShell 运行库复制品。
- 日常开发执行 Debug/Release 构建和定向 Smoke；完整宿主 Smoke、Help、正式包、部署和回滚只进入发布候选阶段。
- 不执行开机自启动测试；真实 UAC、防火墙、双机 LAN 和用户数据升级留作发布候选人工验收。

## 不变项与非目标

- 不修改公开命令名称、参数、数据库 schema、Git 提交/推送语义、LAN 配对协议和 MCP/Web 协议。
- 不在 OHS 中保留一层“薄 ServiceHost”兼容入口；V3 完成后唯一宿主是 AppShell。
- 不把 AppShell 工作树当作依赖；OHS 只消费正式 3.1.7 Z 快照。
- 不顺带升级 AppShell 视觉设计、资源模块或其他消费项目。
- 本文阶段不修改 `StudioVersion.props`、代码、正式包或部署；施工完成后再提升 OHS 到 V3.0。

## 验收结论

只有同时满足“AppShell 3.1.7 正式快照可作为宿主”“OHS 单模块可在宿主服务/UI 两侧装载”“原数据和命令行为不变”以及“OHS `z-Package` 不含任何 OHS EXE”四项条件，才允许将 V3.0 标记为正式完成。

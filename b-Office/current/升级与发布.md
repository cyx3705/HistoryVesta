# AppShell 升级与发布合同

本文件是 AppShell 维护者和消费项目执行升级、候选验证、正式发布与回滚的现行入口。版本历史和
施工过程位于 `../history/`；API、命令和运行时用法位于 `../package/`。

## 消费模型

AppShell 只在 023 维护一份源码和一条版本线。消费方使用固定版本 NuGet 包，不复制源码，不跨
项目 `ProjectReference`，也不修改全局 NuGet 缓存或解压后的包内容。

| 场景 | 直接引用 | 传递依赖 |
| --- | --- | --- |
| WPF 桌面应用 | `OneHistory.AppShell.Shell` | Core、Services |
| 无窗服务宿主 | `OneHistory.AppShell.ServiceHost` | Core、Services |
| 桌面和独立服务并存 | Shell、ServiceHost | Core、Services |
| 只使用契约 | Core | 无 |
| 只使用通用服务 | Services | Core |

四包必须使用同一版本。V3 冻结消费版本为 3.0.3：

```xml
<PackageReference Include="OneHistory.AppShell.Shell" Version="3.0.3" />
<PackageReference Include="OneHistory.AppShell.ServiceHost" Version="3.0.3" />
```

## 包源与资产边界

| 类型 | 位置 | 属性 |
| --- | --- | --- |
| 审核候选 | `b-Publish/current/packages/` | 只保留最近一次，可覆盖、用于候选验证 |
| 正式历史 | `b-Publish/history/<版本>/` | 与当时 Z 快照同构的最小不可变副本 |
| 当前正式快照 | `z-Package-AppShell/` | 一个当前版本，供消费方稳定索引 |
| 消费合同源 | `b-Office/package/` | 唯一可编辑的发布文档源 |
| 发布机器输入 | `b-Code-AppShell/eng/release/` | 文档清单和 Z 级生成模板 |

AppShell 自有包不发布到 NuGet.org。正式消费配置只指向 Z 级 feed；候选验证使用临时配置，完成后
移除 current 候选来源。

## 消费方升级

### 升级前

1. 记录消费项目 HEAD、当前 AppShell 版本、锁文件和关键回归结果。
2. 确认所有 AppShell 包版本一致，没有源码副本、跨项目引用或 current 候选长期配置。
3. 阅读目标版本消费变更、运行时限制以及实际使用能力对应的 API/模块合同。
4. 保留当前锁文件、可回滚包和用户状态备份。

### 候选验证

```powershell
dotnet restore .\YourApp.sln --force-evaluate --source <current-candidate-packages> --source https://api.nuget.org/v3/index.json
dotnet build .\YourApp.sln -c Debug --no-restore
dotnet build .\YourApp.sln -c Release --no-restore
dotnet test .\YourApp.sln -c Release --no-build --no-restore
```

随后执行消费应用自己的 Smoke、GUI、确定性或协议回归。仅编译通过不等于升级完成；窗口布局、
命令目录、模块、MCP/Web、服务生命周期和关闭释放按实际使用能力验证。

### 正式切换

1. 等待候选审核通过并提升到正式 feed。
2. 将消费项目固定为正式版本，从 Z 级 feed 使用全新缓存或 `--force-evaluate` 还原。
3. 审查 `packages.lock.json`，确认 AppShell 四包一致且没有意外依赖漂移。
4. 重跑候选阶段完整回归后，才提交消费方升级。

### 从源码副本迁移

先加入固定包引用并验证，再移除解决方案中的 AppShell 工程和 `ProjectReference`，最后删除消费方
源码副本、重复发布脚本和重复手册。顺序不可颠倒；禁止为了通过编译重新引入副本。

## 框架候选

在 023 根执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\b-Code-AppShell\eng\Publish-AppShell.ps1 -Version 3.0.3
```

候选流水线执行隔离还原、Debug/Release 构建测试、漏洞审计、四包与符号打包、PackageSmoke、
Demo 发布、消费文档复制、manifest 和 SHA-256 生成。它只覆盖 `b-Publish/current/`，不更新正式
归档或 Z 级快照。

## 正式发布

正式发布前必须同时满足：

- 来源代码、消费合同和发布机器输入已经提交且工作树洁净。
- 候选来源提交、版本和 manifest 已审查。
- AppShell 自身门禁和要求的消费方回归全部通过。
- 用户明确批准正式发布。

执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\b-Code-AppShell\eng\Publish-AppShell.ps1 -Version 3.0.3 -Publish
```

正式路径先整体替换 Z 级当前快照，再把同一最小快照写入不可覆盖的 `history/<版本>/`。脚本不执行 Git commit、
tag、push，也不发布 NuGet.org；这些动作需要单独授权。

## 历史链路与虚拟快照

历史发布链验证不重建旧源码：

```powershell
.\b-Code-AppShell\eng\Publish-AppShell.ps1 -Version <历史版本> -VirtualPublish
```

它从 `b-Publish/history/<版本>/feed` 读取已归档四包，写入 `b-Publish/virtual/<版本>/`，并标记
`compatibilityValidated=false`。只有明确测试或回滚指令时才增加 `-DeployToZ`；脚本校验后整体
替换 Z 根内容，不建立版本号外层目录，也不混合新旧文件。

## 回滚

1. 消费方将所有 AppShell 包统一改回上一正式版本。
2. 从对应已验证 feed 强制还原并审查锁文件。
3. 恢复与该版本匹配的消费代码和配置。
4. 重跑与升级时相同的回归矩阵。

布局、设置和模块目录属于用户状态；跨主版本回滚前先备份应用数据目录，不得用删除用户数据
代替迁移。正式历史归档不得覆盖或删除。

## 最低回归矩阵

| 能力 | 最低回归 |
| --- | --- |
| 命令总线 | 注册、解析、校验、确认、执行、取消、异常与帮助 |
| WPF Shell | 启停、四边工具窗、中央文档、拖放、旧布局迁移和保存恢复 |
| Workspace/面板 | 边界、文件操作、JSON 加载、输入绑定、reload |
| 模块 | 好坏模块隔离、命令/UI 注册、owner 回收、热重载 |
| MCP/Web | 目录、调用、策略、确认、审计、鉴权、限流、端口释放 |
| ServiceHost | 单实例、启动、停止、重启、自启和 Dispose |

## 禁止事项

- 不混用不同版本的 AppShell 包。
- 不把 current 候选路径长期写入正式 NuGet 配置。
- 不在消费方维护第二份命令目录、前端代理或 AppShell 手册。
- 不用删除布局或用户数据代替兼容性修复。
- 不直接编辑 `b-Publish/` 正式归档或 `z-Package-AppShell/` 当前快照。
- 不把候选构建、正式提升、Git 推送和部署合并成未经审核的自动动作。

# HistoryJanus 有效决策

## DEC-001 单模块交付

- 状态：已接受
- 日期：2026-08-07
- 决策：Janus 对 HistoryVulcan 只发布一个 `HistoryJanus` 模块；源码内部按功能内聚组织，不拆成相互依赖的多个运行模块。
- 原因：项目、分支历史、Meta 与 Git 规则共享项目选择、设置和数据模型，继续拆分会增加跨模块合同而没有独立生命周期收益。
- 后果：正式产物只有一个业务 DLL；内部仍可继续按职责拆文件。

## DEC-002 HistoryVulcan 独占宿主职责

- 状态：已接受
- 日期：2026-08-07
- 决策：模块注册器、命令总线、Shell、ServiceHost、Web/MCP 网关和模块生命周期全部归 HistoryVulcan；Janus 只注册业务。
- 原因：保持 HistoryVulcan 稳定后，Janus 可装载、卸载、热重载，也能避免进程间重复协议。
- 后果：V3 不再发布 Janus EXE，不保留旧 ServiceHost 兼容入口。

## DEC-003 命令总线是跨模块 API

- 状态：已接受
- 日期：2026-08-07
- 决策：其他模块通过宿主 `CommandBus` 和稳定命令名消费 Janus，不直接引用 Janus 程序集中的内部 DTO 或服务类型。
- 原因：命令合同可由宿主投影来源、确认和权限，且允许 Janus 独立升级。
- 后果：`package/模块API.md` 是唯一人工消费文档，运行时命令目录仍是参数和策略的最终真值。

## DEC-004 两层发布与双槽部署

- 状态：已接受
- 日期：2026-08-07
- 决策：`b-Publish` 是候选与历史区，`z-HistoryJanus`（V3.3.2 前名 `z-Package-HistoryJanus`）是最新正式消费区；部署同步到 HistoryVulcan UI 与 Service 两个模块槽。
- 原因：开发完成与正式发布解耦，同时保证前后端宿主装载同一模块哈希。
- 后果：正式包不含宿主文件；历史只保留被替换的正式包；不把部署目录视为第三层发布区。

## DEC-005 元文档与消费者文档分离

- 状态：已接受
- 日期：2026-08-07
- 决策：现行项目事实只保存在 `current` 四份元文档；`package` 只保留一份模块 API；历史版本文档不作为后续开发输入。
- 原因：减少文档漂移和同一合同多处手工同步。
- 后果：旧综合命令、MCP 和模块开发手册不再维护或随包发布。

## DEC-008 V3.7.0 页面收敛、指令类精简与测试执行效率

- 状态：已接受
- 日期：2026-08-10
- 决策：分四条。
  1. **github 页并入项目操作页**。取消独立的 `github` 单例窗口，GitHub 连接治理成为
     `projops` 底部同级切换的第三项，与「Git 文件规则」「分支历史」同行。
     UI 宿主自此只注册 `overview`、`projops` 两个窗口。
  2. **删除 Git 文件规则面板的标题行**。该行同时重复了两处已有信息——切换按钮已写明
     「Git 文件规则」，当前项目已由上方选中项标题给出——`RuleTitle` 整体移除。
  3. **指令类由 6 类精简为 4 类**：`proj`、`gitrule`、`history`、`github`。
     `debug` 类整体退役（`janus.debug.logflood` 与宿主 `vulcan.log.flood` 完全重复；
     `janus.debug.sleep` 全仓零调用点）；`meta` 类并入 `proj`
     （`janus.meta.list` → `janus.proj.metas`，`janus.meta.open` → `janus.proj.metaopen`）。
  4. **测试以执行效率为首要目标**：互相独立的 Smoke 套件并行执行，
     每套带具名超时，套件耗时随结果打印。
- 原因：
  1. GitHub 页只有三条只读诊断命令和一个连接状态面板，独占一个右侧单例窗口与
     「项目操作」争夺同一停靠位；两者本就同侧并入同一标签组，用户仍需在两个标签间跳。
     并入后一次切换即可在同一上下文里完成「选项目 → 看规则/历史 → 查连接」。
  2. 一行标题重复两处已有信息，在 0.28 宽度的右侧栏里挤占的是内容空间。
  3. 模块不应重复宿主已提供的诊断能力，更不应把零调用点的自动化辅助指令留在
     最终用户的命令集里（对齐 HistoryVulcan DEC-024）。`meta` 只有两条命令，
     且操作对象就是项目根下的文件夹，本属 `proj`。
  4. 8 个 Smoke 套件串行执行 25 秒，而它们各自创建独立临时 git 仓库、互不共享状态。
- 后果：
  - 窗口 ID `github` 退役；已保存布局中的该窗口在装载时被忽略。消费方与脚本若引用
    `vulcan.ui.show name=github` 需改为切换 `projops` 内的分段。
  - 33 条命令减为 31 条，4 条改名（2 条删除、2 条 meta 迁移）。
  - `DebugCommands.cs` 整体删除。需要日志承压时使用宿主 `vulcan.log.flood`
    （宿主侧默认不注册，需 `diagnostics.commands=true`）。
  - Smoke 并行后单套失败不再中断其余套件，输出按套件名排序而非完成顺序，保证可比对。
- 替代条件：页面若再增第四个分段导致分段行拥挤，需重新评估是否恢复独立窗口；
  指令类若再变更需同级决策。

## DEC-007 指令三段式全小写命名

- 状态：已接受
- 日期：2026-08-09
- 决策：模块命令统一采用 `<模块域>.<类>.<方法>` 三段式，域/类/方法全小写；域名短拼不带 History（本模块为 `janus`）；旧名一次硬切不留别名。细则见 `current/指令优化规范.md`。
- 原因：降低命令行与 MCP 输入成本，消除 `HistoryJanus.Status` / `git.rule.batch-set` 等大小写与连字符负担，并为其他模块提供可对齐样板。
- 后果：3.5.0 起旧命令名全部失效；消费方、脚本与其他模块须按映射表切换；设置键与窗口 ID 不套用三段式。

## DEC-006 V3.1.0 项目库与模块身份改名

- 状态：已接受
- 日期：2026-08-08
- 决策：项目库父目录 `C:\OneHistory\OneHistory-Projects` 改名为 `HistoryVesta`，裸仓 `OneHistory-Projects.git` 改名为 `HistoryVesta.git`；模块 `OneHistoryStudio` 全量改名为 `HistoryJanus`，覆盖 AssemblyName、命名空间、manifest、命令前缀 `module:HistoryJanus`、部署槽、`z-Package-HistoryJanus` 与全部 worktree 的 `.gitattributes`/`.gitignore` managed/baseline 标记；本地分支 `2026-020-OneHistoryStudio` 改名为 `HistoryJanus`，远程分支保持原名且不推送。
- 原因：项目库与模块名称语义化对齐，消除编号目录与模块身份之间的硬编码漂移；集中一次完成可避免新旧名称长期混用导致的隐性 bug。
- 后果：裸仓内全部 worktree 指针（`worktrees/*/gitdir`、各 `.git` 文件、`worktree_paths.txt`）随目录改名重写；3.0.x 消费方须按新模块名与命令前缀重新接入；旧部署槽 `OneHistoryStudio`（含 service 槽）退役，由用户确认后手动清理。

# OneHistoryStudio 有效决策

## DEC-001 单模块交付

- 状态：已接受
- 日期：2026-08-07
- 决策：OHS 对 AppShell 只发布一个 `OneHistoryStudio` 模块；源码内部按功能内聚组织，不拆成相互依赖的多个运行模块。
- 原因：项目、分支历史、Meta 与 Git 规则共享项目选择、设置和数据模型，继续拆分会增加跨模块合同而没有独立生命周期收益。
- 后果：正式产物只有一个业务 DLL；内部仍可继续按职责拆文件。

## DEC-002 AppShell 独占宿主职责

- 状态：已接受
- 日期：2026-08-07
- 决策：模块注册器、命令总线、Shell、ServiceHost、Web/MCP 网关和模块生命周期全部归 AppShell；OHS 只注册业务。
- 原因：保持 AppShell 稳定后，OHS 可装载、卸载、热重载，也能避免进程间重复协议。
- 后果：V3 不再发布 OHS EXE，不保留旧 ServiceHost 兼容入口。

## DEC-003 命令总线是跨模块 API

- 状态：已接受
- 日期：2026-08-07
- 决策：其他模块通过宿主 `CommandBus` 和稳定命令名消费 OHS，不直接引用 OHS 程序集中的内部 DTO 或服务类型。
- 原因：命令合同可由宿主投影来源、确认和权限，且允许 OHS 独立升级。
- 后果：`package/模块API.md` 是唯一人工消费文档，运行时命令目录仍是参数和策略的最终真值。

## DEC-004 两层发布与双槽部署

- 状态：已接受
- 日期：2026-08-07
- 决策：`b-Publish` 是候选与历史区，`z-Package-OneHistoryStudio` 是最新正式消费区；部署同步到 AppShell UI 与 Service 两个模块槽。
- 原因：开发完成与正式发布解耦，同时保证前后端宿主装载同一模块哈希。
- 后果：正式包不含宿主文件；历史只保留被替换的正式包；不把部署目录视为第三层发布区。

## DEC-005 元文档与消费者文档分离

- 状态：已接受
- 日期：2026-08-07
- 决策：现行项目事实只保存在 `current` 四份元文档；`package` 只保留一份模块 API；历史版本文档不作为后续开发输入。
- 原因：减少文档漂移和同一合同多处手工同步。
- 后果：旧综合命令、MCP 和模块开发手册不再维护或随包发布。

# AppShell 技术合同

本文件合并当前有效的需求与架构。详细公共 API、命令参数和消费示例以
`../package/` 下的四份消费合同为准；历史设计和冻结施工记录不再作为现行实现依据。

## 现行需求

### REQ-PKG-001 固定版本包消费

- 目的：消除复制 AppShell 源码造成的分叉和隐式耦合。
- 要求：当前候选消费方统一引用 `OneHistory.AppShell.Shell 3.1.3`；服务宿主额外引用
  `OneHistory.AppShell.ServiceHost 3.1.3`，不得直接引用本仓库源码工程。正式 Z 快照仍以其自身 manifest 版本为准。
- 验收：隔离 NuGet 缓存可从候选或正式 Z 级 feed 还原、构建并报告一致版本。
- 关联组件：`b-Code-AppShell/src/`
- 关联验证：`VERIFY-PACKAGE`

### REQ-DOCK-001 单一窗口与中央主工作区

- 目的：在统一停靠模型中保证中央业务区可用，同时允许工具页自由停靠。
- 要求：命令集是默认中央文档；中央区显示自己的页面头和页面选择区。普通工具页可拖入中央
  成为标签，再拖出或停回四边；运行期同侧工具页复用同一标签窗格。
- 验收：真实 WPF 视觉树、拖放、持久化和恢复测试通过；左右或上下侧栏合计不超过对应轴 50%。
- 关联组件：`b-Code-AppShell/src/AppShell.Shell/`
- 关联验证：`VERIFY-FULL`

### REQ-DOCK-002 顶栏手势与页面拖出边界（3.1.3）

- 目的：避免慢速连点或轻微拖动误触窗口切换，并消除页头与页签对“拖出页面”的职责冲突。
- 要求：自定义双击必须是同一目标在 250ms 内、且指针未超出系统双击范围的两次有效点击。嵌入或聚焦
  页面的空白顶栏只控制 AppShell 主窗口；主窗口处于普通状态时越过系统拖动阈值即开始移动，不增加按住延时。
  主窗口最大化状态及独立浮窗仍需按住满 120ms 才允许移动；最大化状态使用两倍系统阈值，并在启动拖动时
  按鼠标横向比例恢复。延时场景的提前位移必须保留至 120ms 到期，任何一次按下只要越过移动阈值，就必须
  立即作废该次双击候选，即使 120ms 尚未到期；释放、失去捕获或双击
  必须取消拖动。主窗口移动不得改变当前聚焦页面。只有真实页签能够拖出页面：普通页签
  使用 AvalonDock 原生流程，聚焦页签执行 `win.restore` 后再执行 `win.float`。拖出尺寸来自恢复后的嵌入窗格
  实际宽高，鼠标维持原页签抓取点；跨显示器定位必须区分物理像素与 WPF DIP，并限制在目标显示器工作区。
- 验收：`ShellTopBarGestureTests` 覆盖普通主窗口无延时、其余宿主 119/120ms、提前位移、释放取消、250/251ms、两倍阈值、DPI、工作区
  裁剪和鼠标锚点；`ShellChromeContractTests` 覆盖普通、聚焦及独立浮窗动作矩阵。
- 关联组件：`b-Code-AppShell/src/AppShell.Shell/`
- 关联验证：`VERIFY-FULL` 与 Windows GUI 冒烟

### REQ-CMD-001 统一命令合同

- 目的：让 UI、脚本、模块、MCP、Web 和服务宿主共享可查询、可治理的命令模型。
- 要求：命令必须经注册表和总线执行，具备来源、参数、安全级别、执行站点和 MCP 允许标记；
  基础命令组由 `AppShell_API与指令手册.md` 固定。
- 验收：命令解析、注册冲突、确认、线程编组、前端代理和目录导出测试通过。
- 关联组件：`AppShell.Core/Commands`、`AppShell.Shell`
- 关联验证：`VERIFY-FULL`

### REQ-CMD-002 业务入口统一走命令管线（3.1.1）

- 目的：消除 UI 按钮直接改服务或窗口状态造成的断头指令。
- 要求：会改变应用状态或执行外部操作的控制台、窗口、复制示例和面板选择入口必须调用
  `CommandBus`；检索与控制台操作使用 `log.level/source/keyword/mute/autoscroll/clear/export/copy/focus`。
  `cls` 仅作为 `log.clear` 兼容别名保留。纯焦点、选择和 Tab 导航不作为业务命令。
- 验收：`断头指令审计表.md`、`ShellChromeContractTests` 和命令注册测试全部通过。

### REQ-CAP-001 默认最小能力

- 目的：框架包不得在消费方未授权时启动监听、扫描模块或建立治理状态。
- 要求：`ShellConfig.EnableMcp` 与 `EnableModules` 默认均为 `false`；本地 `command.*` 和中央
  命令集不依赖 MCP 网关。消费方必须显式开启所需能力。
- 验收：默认配置下不创建 MCP 网关、模块宿主或监听端口，本地命令与主工作区仍可用。
- 关联组件：`AppShell.Shell/ShellConfig`、`AppShell.Services`
- 关联验证：`VERIFY-FULL`

### REQ-SVC-001 双进程后台服务与快捷键（3.1.2，方案源自 3.2 历史设计）

- 目的：让命令、非 UI 模块、日志、MCP/Web 和全局快捷键在用户会话后台持续运行，前端只承载 WPF 与 UI 模块。
- 要求：独立宿主使用同一 EXE 的 `--service` 分支；前端通过 loopback 端点连接，重复启动只激活已有前端；
  关闭默认隐藏，`app.exit` 协调两端退出。快捷键只映射命令文本、不吞键、不保存原始按键，模块卸载释放其 owner 的全部注册。
- 要求：双 `/` 执行 `app.frontend.focus-console` 时，无论控制台原先隐藏或已经显示，都必须将主窗口提升到 Windows
  前台、切换控制台聚焦布局并把键盘焦点落入命令输入框；提升只改变当前 Z 序，不得让窗口永久保持 `Topmost`。
- 验收：服务端点健康检查、前端重连/单实例、`app.frontend.*` 命令、双 `/` 与快捷键冲突测试通过；
  `FrontendFocusConsoleRaisesTheWindowAndRefocusesExistingConsole` 覆盖隐藏唤醒和已显示时再次上浮聚焦。
- 关联组件：`AppShell.ServiceHost`、`AppShell.Services/Input`、`AppShell.Shell`
- 关联验证：`VERIFY-FULL`、双进程烟测

### REQ-MOD-001 模块 UI 生命周期

- 目的：保留模块注册和修改能力，同时避免模块窗口挤压主工作区或重复生成窗格。
- 要求：UI 模块通过 `IShellUiRegistrar.RegisterToolWindow` 注册；默认位置为右侧、默认比例 0.25，
  同侧优先合并为标签。owner 卸载时回收其窗口和命令；模块可显式覆盖有效停靠配置。
- 验收：模块装载、热重载、回收、右侧合并和 SE2SW 真实窗口冒烟通过。
- 关联组件：`AppShell.Services/Modules`、`AppShell.Shell`
- 关联验证：`VERIFY-FULL`

### REQ-MCP-001 MCP 与 Web 安全边界

- 目的：提供可选远程接入而不扩大默认攻击面或泄露敏感信息。
- 要求：端口按应用身份稳定派生并有界顺延；命令只有显式 `AllowMcpExecution=true` 才能暴露；
  鉴权、限流、确认、会话隔离、消息上限、固定时长令牌比较和脱敏审计必须保持。
- 验收：协议、鉴权、坏帧、分片、限流、确认、脱敏和审计测试通过。
- 关联组件：`AppShell.Core/Mcp`、`AppShell.Services/Mcp`、`AppShell.ServiceHost`
- 关联验证：`VERIFY-FULL`

### REQ-REL-001 发布真值与不可变性

- 目的：区分可编辑源、审核候选、历史归档和当前正式快照。
- 要求：消费文档只编辑 `b-Office/package/`；候选覆盖写入 `b-Publish/current/`；正式发布先更新

- 验收：manifest、文件清单、包身份、文档副本和 SHA-256 一致；正式来源提交洁净。
- 关联组件：`b-Code-AppShell/eng/Publish-AppShell.ps1`

### REQ-UI-001 现代化外壳（3.1 起）

- 目的：以层次而非线条表达页面边界，并把常驻横带（菜单行、状态栏）还给工作区。
- 要求：停靠窗格渲染为圆角卡片（间隙 + 投影，窗格之间无 1px 边框）；**不设独立标题栏层**，
  菜单与最小化/最大化/关闭按钮并入最上一排页签所在的那一行，菜单按钮恒在三个窗口按钮左侧；
  页签与卡片同心圆角；页面最大化铺满工作区并保留真实页签及唯一主 ChromeBar，不显示重复页面动作；不设状态栏，原有结果与错误
  计数改由瞬时回执与顶部徽章承载；视图顶部的成组控件合并为「切分圆角矩形」；窗体外缘直角、
  内部统一圆角；工具页不设自身标题栏，页面动作（浮动/停靠为文档/自动隐藏/隐藏）占页签行右端；
  提供浅色/深色两套令牌，主题色统一为暗黄，深色为低饱和墨绿底 + 淡黄正文，经 `app.theme`
  切换并持久化，浮动窗口须逐窗口跟随；表格表头必须显式引用 `Shell.GridHeader`，
  且 `ListBox`/`ListView`/`TabControl` 必须使用 Shell 模板 —— WPF 默认模板会在禁用态和
  内容区刷上系统浅灰，深色模式下直接漏色。
  细则与编号（UI-01…UI-09、R2-1…R2-6、R3-1…R3-4、R4-1…R4-5）见 `V3.1界面现代化方案.md`。
- 验收：`ShellChromeContractTests` 外壳合同 + `DockingContractTests` 全量通过；除 3.1.1 明确删除的资源公开面外，
  其余公开 API 基线不变，四份 Unshipped 仍为空。
- 关联组件：`b-Code-AppShell/src/AppShell.Shell/`（`Themes/`、`ShellWindow`、五个内置视图）
- 关联验证：`VERIFY-FULL`

## 系统架构

### 系统边界

AppShell 管理通用壳层能力和扩展合同，不拥有消费应用的业务模型。Core 不依赖 WPF；Services
实现通用服务；Shell 是唯一直接封装 AvalonDock 的层；ServiceHost 提供无窗 WPF 服务进程。资源浏览/文件
操作不属于 AppShell，未来由独立模块提供。

### 组成

| 组件 | 路径 | 职责 | 主要输出 |
| --- | --- | --- | --- |
| Core | `src/AppShell.Core` | 命令、停靠、日志、MCP、存储等契约 | `OneHistory.AppShell.Core` |
| Services | `src/AppShell.Services` | 设置、文件状态、日志、MCP、模块实现 | `OneHistory.AppShell.Services` |
| Shell | `src/AppShell.Shell` | WPF 主壳、停靠 UI、控制台、面板与模块管理 | `OneHistory.AppShell.Shell` |
| ServiceHost | `src/AppShell.ServiceHost` | 无窗服务宿主和 `svc.*` 生命周期 | `OneHistory.AppShell.ServiceHost` |
| Demo | `src/App` | 独立运行与 GUI 验收宿主 | win-x64 framework-dependent ZIP |
| Tests | `b-Code-Tests/AppShell.Tests` | 公开合同、安全、布局与冻结回归 | TRX 与进程退出码 |

### 关键流程

1. 消费方固定包版本，创建 `ShellConfig`，只显式启用需要的模块或 MCP 能力。
2. Shell 组装命令、日志、布局和窗口；模块通过注册合同增加命令与工具页。
3. 候选流水线隔离还原、构建、测试、审计、打包和 PackageSmoke，人工批准后才提升正式快照。

### 不变量与生成物边界

- Core 保持零 WPF 依赖；AvalonDock 只从 Shell 直接引用。
- 所有命令执行进入同一总线；危险命令进入统一确认边界。
- 正式包和 Z 级快照不直接编辑；权威源是源码、`b-Office/package/` 与发布模板。
- AppShell 只保留 `ModulesView` 这一套模块管理页面；独立 AppShell 可执行宿主显式启用 `EnableModules` 并成为
  模块生命周期所有者。OHS 只提供停靠位置与消费配置，后续业务能力以模块接入，不复制页面或第二个 `ModuleHost`。
- 3.1.1 删除内置资源浏览能力和演示电机页面；`res.*`、`motor.*` 不再注册。
- `b-Publish/current/`、`b-Publish/virtual/`、`bin/`、`obj/`、`artifacts/` 是可重建生成物。
- `b-Publish/` 的版本化正式归档和 `z-Package-AppShell/` 当前快照是发布资产。

# HistoryJanus 技术合同

## 现行需求

### REQ-001 宿主化运行（3.7.0 收敛为两个窗口）

- Janus 必须作为 `HistoryJanus` 模块由 HistoryVulcan 加载，不创建独立应用、后台服务或第二套 Shell。
- UI 宿主只注册 `overview`、`projops` **两个**单例窗口。Meta 文件夹浏览并入 `overview`；
  `projops` 底部以同一行分段切换三个面板：**Git 文件规则 / 分支历史 / GitHub**。
- **默认落位（3.7.1）**：`overview` 占**中央工作区**（`DockSide.Center`），
  `projops` 停靠**左侧**、默认宽度占比 `0.38`。
  `overview` **不得**声明 `DefaultTabTarget`：此前它并入 Mcp 标签组，而那个窗口由
  HistoryMercury 提供，模块装载顺序不保证它先到——先到就并入、没到就回退右侧停靠，
  首次启动落位因此不确定（服务日志中的「标签组目标 mcp 不可用」）。
  中央区不依赖任何别的模块，落位才是确定的。
  3.4.0 引入、3.6.0 仍存在的独立 `github` 窗口在 3.7.0 退役（DEC-008）。
- UI 与无 UI Service 宿主都必须注册同一组 Janus 业务命令，来源统一为 `module:HistoryJanus`。
- 分段面板不得各自显示重复标题：分段按钮已给出面板名，上方选中项标题已给出当前项目，
  面板内不再重复这两项。

### REQ-002 业务能力

- 模块提供项目列举、创建、提交、推送、继承树命令、Meta 文件夹浏览、分支历史、回滚和 Git 文件规则治理；继承树与分支历史不再提供独立页面。
- **指令分类（3.7.0，DEC-008）**：`janus` 域内只有四个业务类——`proj`、`gitrule`、`history`、`github`，
  共 31 条业务命令，一律三段式 `janus.<类>.<方法>`（3.5.0 DEC-007 确立）；模块宿主另投影
  两段式只读命令 `janus.status`，因此运行时总数为 32 条。
  模块不注册诊断或自动化辅助指令：日志承压使用宿主 `vulcan.log.flood`，
  不在业务模块内重复实现。
- 页面通过宿主 `CommandBus` 调用业务命令；跨 HTTP 的结构化结果必须先从 JSON 投影为页面模型。
- 卸载或热重载后不得残留窗口或旧命令注册。

### REQ-003 正式交付

- `b-Publish/current/HistoryJanus` 只保存本次验证候选；旧正式版本只以扁平历史包保存在 `b-Publish/history`。
- `z-HistoryJanus` 只保存最新正式快照。
- 正式快照只允许 `HistoryJanus.dll`、`HistoryJanus.xml`、`module.manifest.json`、`SHA256SUMS` 和 `package/模块API.md`。
- 部署只把正式快照中的运行文件同步到 HistoryVulcan UI 与 Service 两个模块槽；API 文档留在 z 级消费区供开发者读取。

## 系统架构

| 组件 | 路径或位置 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| 模块入口 | `b-Code-Studio/Module` | 接收宿主上下文，注册命令和窗口 | `IModuleContext`、`IShellUiRegistrar` | 命令注册与两个页面 |
| 业务组合 | `b-Code-Studio/StudioBusinessComposition.cs` | 组合项目、Git 规则、历史与 GitHub 命令 | 宿主设置、日志、数据根 | 31 条业务命令（`janus.*`，四类）；宿主另投影 `janus.status` |
| 页面 | `b-Code-Studio/Views` | 展示项目与 Git 工作流 | 宿主 CommandBus 结果 | WPF 页面状态 |
| 验证 | `b-Code-Verify` | 契约、功能和模块生命周期回归 | 源码与候选包 | 通过/失败结果 |
| 正式消费区 | `z-HistoryJanus` | 保存最新模块和 API 合同 | 已验证候选 | 跨项目可消费快照 |

### 关键流程

1. HistoryVulcan 从自身 Modules 目录读取 manifest 并装载 `HistoryJanus.dll`。
2. `IModuleContextAware.Attach` 使用宿主 registry、bus、settings、log 与 data directory 注册业务组合。
3. `IUiModule.CreateUi` 把两个页面登记到宿主布局；项目总览同时消费项目和 Meta 列表，项目操作页以同一行分段内嵌 Git 文件规则、分支历史与 GitHub 连接面板（GitHub 面板直连模块内连接服务，写操作仅限页面），其余交互只通过宿主总线执行业务命令。
4. 发布管道验证源码、模块生命周期和包集合后提升到 z 级正式消费区。
5. 部署管道原子更新 UI/Service 两个模块槽，并保留上一正式部署用于回滚。

### 不变量与生成物边界

- 唯一产品版本源：`b-Code-Studio/JanusVersion.props`，当前开发版本为 `3.7.2`。
  版本沿革：3.4.0 把 GitHubConnection 并入 Janus 成为第三页；3.5.0/3.5.1 指令全量改为
  `janus.<类>.<方法>` 三段式；3.6.0 分支名以 worktree 路径为唯一权威、总览挂入中央区工具页、
  github 页去 Tab、总览显示最近提交描述；3.7.0 收敛页面与指令类并重整测试执行效率。
  （3.4.0–3.6.0 的需求此前未写入本合同，3.7.0 一并补记。）
- 模块 manifest 源：`b-Code-Studio/Module/module.manifest.json`，版本必须与版本源一致。
- HistoryVulcan API 权威源：`2026-023-HistoryVulcan/z-HistoryVulcan`；Janus 不复制其运行库。
- 可重建生成物：`bin/`、`obj/`、`b-Publish/work`、`b-Publish/quarantine`。
- 正式消费快照：`z-HistoryJanus`。

# OneHistoryStudio V2.7.6 · AppShell 质量更新与双缺陷修复

> 文档性质：V2.7.6 联合质量设计、修复立项与验收合同
> 状态：已交付（2026-07-28）
> 范围：AppShell Core/Services/Shell/ServiceHost、包与测试管道，以及 OneHistoryStudio 前端/服务数据契约
> 版本关系：V2.7.5 完成代码管道化；V2.7.6 在其结果上实施 AppShell 框架质量更新并修复两个用户缺陷

本文包含两个已经由用户确认的 V2.7.3 缺陷，以及此前未被独立展开的 AppShell 质量更新。当前代码审查得到的
内容标为“待证根因”，在最小复现和修复测试完成前不得写成已确认事实。V2.7.6 不以增加超时、刷新次数、
手工重启或扩大 Smoke 脚本掩盖架构和数据契约问题。

## 1. 缺陷总览

| 编号 | 用户可见症状 | 影响面 | 目标 |
|---|---|---|---|
| BUG276-01 | 模块管理窗口能显示模块，但选中模块后“注册指令”区域为空或不更新 | AppShell 模块管理窗口、前端/服务分离运行、热重载后的模块观察 | 模块指令明细必须与服务端实际注册表同源，能够显示、刷新和清空 |
| BUG276-02 | 继承树窗口无法正常显示树内容，无法可靠展开、选择或打开项目 | OHS 继承树工具窗口、缓存/重扫、前端/服务分离运行 | `proj.tree` 的服务结果经远端 JSON 往返后仍能构成可交互树 |

正式部署记录已明确把继承树问题留给质量修复：[OHS 2.7.3 部署证据](../evidence/deploy-ohs-2.7.3-20260728-091042.md)
的“尚待人工”段不得被改写成已通过。模块指令问题没有独立的成功证据，V2.7.6 必须补齐。

这两个缺陷不是孤立 UI 补丁：模块管理问题直接暴露 AppShell 管理视图在前端/服务分离后的真值来源错误；
继承树问题暴露远端结构化结果缺少完整往返验收。二者将作为 AppShell 质量更新的首批端到端样本。

## 2. BUG276-01 模块注册指令不显示

### 2.1 当前实现事实

当前模块管理视图在 `RefreshAsync` 中执行 `module.list`，并使用结果中的 `ModuleMeta.CommandCount` 填充模块行；
但在选中行时，`OnModuleSelected` 直接读取当前前端进程的本地 `CommandRegistry.All()`，再按
`<模块名>.` 前缀筛选。

在客户端模式下，AppShell 明确只创建管理视图，不在本进程创建 `ModuleHost`；管理视图的 `module.list` 经过
`CommandBus.RemoteExecutor` 读取服务端结构化结果。因此当前实现存在一个必须先验证的来源分裂：模块行可能来自
服务端，而指令明细查询的是前端本地注册表。若两者不在同一进程，模块数量可以正确但明细必为空。

相关现行源码：

- `../../b-Code-AppShell/src/AppShell.Shell/Views/ModulesView.xaml.cs`
- `../../b-Code-AppShell/src/AppShell.Shell/ShellConfig.cs`
- `../../b-Code-AppShell/src/AppShell.Shell/Mcp/CommandCatalogCommands.cs`
- `../../b-Code-AppShell/src/AppShell.Services/Modules/ModuleHost.cs`

### 2.2 最小复现

必须分别执行本地同进程和前端/服务分离两条路径，并记录以下原始结果：

1. `module.list` 的模块名、`CommandCount`、槽和 UI 状态；
2. `command.list` 中 `Source=module`、`SourceDetail=<模块名>` 的指令集合；
3. 模块管理页选中该模块后显示的指令集合；
4. `module.reload` 前后上述三组集合及顺序；
5. 无模块、模块下线和模块加载失败时的空状态及错误提示。

复现记录不能只截取窗口截图，必须同时保存命令结果摘要和前端/服务端进程身份，确认是否发生本地注册表与
远端注册表混用。

### 2.3 修复要求

- 指令明细必须消费与 `module.list` 同一来源的结构化目录。优先使用远端 `command.list`，按
  `Source=module` 与 `SourceDetail` 筛选；不得在远端管理视图中直接把前端本地注册表当作服务端真值。
- `module.list`、指令目录和模块选择状态必须在同一轮刷新中形成一致快照；刷新失败不得用旧明细伪装成功。
- `module.reload` 完成后，模块行、指令数量和明细同时更新；旧模块的指令必须消失，新模块的指令必须出现，
  不得出现重影或重复行。
- 视图显示字段仍可复用现有 `CommandCatalogRow` 的名称、摘要和示例；不为 UI 另造一套模块指令注册表。
- 同进程模式保留本地路径作为优化，但必须与远端路径共享同一筛选合同，并由同一回归用例覆盖。

### 2.4 验收门禁

| 场景 | 必须证明 |
|---|---|
| 5 个模块、动态指令已装载的正式形态 | 模块行总数、每行 `CommandCount` 与 `command.list` 按来源分组结果一致 |
| 选中每个模块 | 指令明细非空时显示完整，数量与来源筛选结果一致；无指令模块显示明确空状态 |
| 热重载成功 | 旧模块指令全部撤销，新模块指令全部出现，模块管理页不需要重启 |
| 前端/服务分离 | 关闭本地 ModuleHost 后，模块行和指令明细仍来自服务端并正常显示 |
| 服务端失败/断线 | 明细不显示过期数据，窗口给出可诊断状态，恢复连接后可重新加载 |

固定的“13 条模块指令”只能作为本次现场的观察值，不能写成永久断言；测试应从服务端装配集合派生期望值。

## 3. BUG276-02 继承树无法正常显示

### 3.1 当前实现事实与待证根因

`BranchTreeView` 执行 `proj.tree cached=true` 或 `proj.tree refresh=true`，只有在
`result.Data is ProjectService.BranchNode` 成功时才设置 `TreeView.ItemsSource`。展开、选中、右键菜单和打开项目
也全部依赖同一个具体 `BranchNode` 类型。

前端服务客户端已有 `proj.tree -> ProjectService.BranchNode` 的反序列化映射，但现有远端 Smoke 只验证了
`proj.list`、`command.list` 等投影，没有证明完整 `BranchNode.Children` 树经过 JSON 往返后仍可用。以下是待证根因，
必须用实测区分：

1. 远端 `CommandResult.Data` 的 JSON 形状与 `BranchNode` 类型不完全一致，导致类型还原失败；
2. 只读缓存无数据时，视图只更新状态文本，不清理旧 `ItemsSource`，造成空白或旧树残留；
3. `Children`、`IsExpanded` 或 `required BranchName` 在序列化/反序列化后丢失，树根存在但子节点不可渲染；
4. 树算法已经返回数据，但布局加载或工具窗口重建时 `ItemsSource` 被替换/未触发 UI 更新；
5. 实际项目数据存在根分支、编号顺序或缓存格式异常，算法结果为空，和 UI 类型问题混淆。

相关现行源码：

- `../../b-Code-Studio/Views/BranchTreeView.xaml`
- `../../b-Code-Studio/Views/BranchTreeView.xaml.cs`
- `../../b-Code-Studio/Service/StudioCommandDataDeserializer.cs`
- `../../b-Code-Studio/Git/ProjectCommands.cs`
- `../../b-Code-Studio/Git/BranchTreeService.cs`
- `../../b-Code-AppShell/src/AppShell.Shell/ShellConfig.cs`

### 3.2 最小复现与数据分层

使用一个包含根、一级子分支和至少两个二级分支的临时裸仓库，分别记录：

1. 服务进程直接执行 `proj.tree refresh=true` 的 `Success`、消息和 Data 节点数量；
2. HTTP/命令中继返回的原始 JSON（脱敏后）及客户端反序列化后的根、子节点、字段值；
3. 前端执行 `proj.tree cached=true` 时的 `ItemsSource` 类型和节点数量；
4. 重新扫描后 TreeView 的根、一级、二级节点呈现；
5. 选择、展开、折叠、复制分支名、打开项目和跳转分支历史是否仍操作同一节点；
6. 无缓存、损坏缓存、空仓库、服务断线和恢复连接的行为。

任何“窗口存在”或“命令返回成功”都不能替代节点呈现验收。原始 JSON 只进入临时测试产物，不回填 OHS
源码仓库；长期文档只保留结论、哈希和失败阶段。

### 3.3 修复要求

- 为远端数据定义稳定的树投影合同，确保根、`BranchName`、`Description`、`LastPushTime`、`Children` 均可还原；
  不把 WPF `TreeView` 类型或前端布局状态传入服务层。
- 视图加载成功但 Data 为空、类型不符或反序列化失败时，必须清理不可用的旧树并显示可诊断状态；不得静默保留
  空白窗口。
- 只有确认节点集合有效后才启用“全部展开/全部折叠”；上下文菜单和项目选择必须复用当前 ItemsSource 中的
  节点对象。
- 缓存读取、重新扫描和远端中继必须共享同一 `BranchNode` 投影和失败语义；不能为“启动加载”另写一条不完整路径。
- 树算法若返回空树或根分支缺失，错误必须在服务消息中明确指出是仓库数据/缓存问题，而不是让 UI 看起来像渲染失败。

### 3.4 验收门禁

| 场景 | 必须证明 |
|---|---|
| 本地同进程 | 根、一级、二级节点均可见，展开状态和选择同步 |
| 前端/服务分离 | 原始 JSON 还原为完整树，`ItemsSource` 非空且节点数与服务端一致 |
| 缓存命中 | `cached=true` 秒开且内容正确；无缓存时显示明确提示，不伪造空树 |
| 重新扫描 | `refresh=true` 更新树并替换旧缓存，窗口不需要重启 |
| 交互 | 选择节点同步项目状态；右键查看历史、打开项目、复制分支名均作用于选中节点 |
| 异常数据 | 空仓库、损坏缓存、缺根分支和断线均可诊断，恢复后可重试 |

## 4. AppShell 质量更新边界

### 4.1 与 V2.7.5 的分工

V2.7.5 的主目标是把版本、命令元数据、模块清单和发布事实接成可验证管道。它包含 AppShell 相关事项，但
没有为 AppShell 自身建立一份完整的框架质量合同。V2.7.6 不重复版本唯一源、命令指纹和 manifest 生成，
而是在这些管道可用后处理下列更难的问题：

| V2.7.5 前置能力 | V2.7.6 质量责任 |
|---|---|
| AppShell/OHS 版本和命令事实可追溯 | 证明框架在同进程、客户端和服务宿主三种角色下行为一致 |
| 命令目录可从注册表生成 | 管理视图不得绕过目录，直接读取错误进程的本地注册表 |
| 发布入口生成 manifest 与哈希 | staging、隔离包缓存和构建中间目录不得进入源码仓库或污染共享 `obj` |
| Smoke 不再依赖固定总数 | 建立单元、契约、包消费、GUI 四层测试，不再只有控制台跑批 |
| 文档和生成物边界可检查 | AppShell 公共契约、内部实现和 OHS 派生能力必须有明确所有权 |

V2.7.5 未完成的管道门禁不能被 V2.7.6 重新手写绕过；V2.7.6 发现的框架行为缺陷也不能反向塞回 V2.7.5
而失去独立验收记录。

### 4.2 本版必须覆盖的 AppShell 质量域

1. **管理视图跨进程一致性**：模块管理、命令集、指令详情必须使用与当前宿主角色一致的目录来源；
2. **远端结构化合同**：CommandResult Data 经 HTTP/JSON 往返后必须恢复为稳定 DTO，不能依赖某个进程内对象身份；
3. **测试分层**：纯逻辑进入标准测试框架，序列化和宿主角色进入契约测试，PackageSmoke 只验证真实包消费，
   GUI Smoke 只验证 WPF 装配和关键交互；
4. **包体积和 RID**：Windows 框架包与消费冒烟不得复制无关的 Linux、macOS、iOS、Android 原生 SQLite 资产；
5. **构建隔离**：包发布、OHS 构建和模块构建不得共享可被临时 NuGet 缓存污染的 `obj`；
6. **暂存区治理**：发布候选、旧 `b-Publish` 副本、验证 `bin/obj` 和手工检查输出不得提交到 `stage/`；
7. **复杂度控制**：对本版触及的超大类按职责提取可测试组件，但不进行无验收收益的全框架重写；
8. **诊断完整性**：跨进程类型不匹配、目录来源错误、热重载失败和布局恢复必须提供可定位日志，不静默降级为空白 UI。

明确不做：替换 AvalonDock、全面 MVVM 迁移、重写 MCP/Web 协议栈、改变模块公开反射规则，或借质量更新新增
与两个缺陷无关的产品功能。

一致性和上限，而不是要求未来文件数与本表完全相同。

### 5.2 目标分层

```text
AppShell.Core
  公开命令/窗口/模块契约 + 与 UI 无关的目录 DTO
          ↓
AppShell.Services / ServiceHost
  模块宿主、真实注册表、Web/MCP/命令中继、宿主侧目录快照
          ↓ JSON / CommandResult.Data
AppShell.Shell
  角色感知的目录提供者 → 模块管理 / 命令集 / 指令详情
          ↓
OneHistoryStudio
  项目域命令与视图；不复制 AppShell 管理目录逻辑
```

管理窗口不得自行决定“本地 Registry 还是远端命令”。Shell 应提供一个角色感知的目录读取边界：同进程宿主
可以从本地注册表生成快照，客户端必须经命令总线取得服务端快照；两条路径最终返回同一 DTO 集合并执行同一
筛选逻辑。公开接口命名在实施时决定，但不能把 `CommandBus.RemoteExecutor != null` 分支散落到每个 View。

模块指令目录继续以 `command.list` 的 `Source=module`、`SourceDetail=<模块名>` 为真值。`ModuleMeta.CommandCount`
是摘要，不另带一份可能漂移的完整指令副本。命令集、指令详情和模块管理共享同一次或同版本目录快照，避免
热重载过程中出现模块行与明细跨代。

### 5.3 远端 DTO 和错误语义

- DTO 只能包含可序列化数据，不包含 WPF 控件、Dispatcher、事件订阅或进程内服务引用；
- 每个远端投影必须有真实 JSON 往返测试，至少覆盖集合、递归树、空值、未知字段和版本向前兼容；
- 反序列化失败必须记录命令名、预期类型、JSON ValueKind 和相关 ID，不记录 token、密码或完整本机路径；
- UI 收到类型不符的数据时必须清空过期内容并显示诊断摘要，不以成功消息掩盖空白内容；
- 递归树 DTO 与 WPF 展开状态分离，展开状态由前端 ViewModel/节点包装持有，不回写服务缓存。

`ProjectService.BranchNode` 当前同时承担服务数据和 WPF `INotifyPropertyChanged` 展开状态。本版应评估拆为稳定
传输节点与前端展示节点；若暂不拆分，也必须用契约测试证明其 JSON 往返和递归子节点可靠。

### 5.4 测试体系

V2.7.6 建立以下四层，不再继续把所有回归塞进单个 PackageSmoke 或 OHS Smoke：

| 层级 | 责任 | 必须覆盖 |
|---|---|---|
| 单元测试 | Core/Services 的纯逻辑 | 注册冲突、目录来源选择、模块来源筛选、版本/哈希解析、错误映射 |
| 契约测试 | 进程边界和结构化数据 | `module.list`、`command.list`、递归 `proj.tree` JSON 往返；客户端/宿主目录一致 |
| PackageSmoke | 从全新本地 feed 消费四个 AppShell 包 | 包依赖闭包、程序集版本、Demo/ServiceHost 启动、仅包含目标 RID 资产 |
| GUI/集成 Smoke | WPF 和真实宿主组合 | 管理视图、热重载、继承树显示、停靠恢复、前端断线与重连 |

标准测试框架只选一种，所有测试必须可由 `dotnet test` 发现并输出机器可读结果。WPF 测试在独立 STA 线程运行；
不能为了测试方便让 Services 引用 WPF。现有手写 Smoke 可逐步保留为端到端层，但不得继续充当唯一测试入口。

### 5.5 包体积、RID 与发布资产

- PackageSmoke 明确声明 `RuntimeIdentifier=win-x64`、`SelfContained=false`，只允许 Windows x64 的 SQLite 原生资产；
- 包消费输出不得出现 `runtimes/linux-*`、`osx-*`、`ios*`、`android-*` 或非目标 Windows 架构；
- PackageSmoke 完整输出设置 10 MB 软上限，超过时列出前 20 个最大文件并使质量门禁失败；阈值调整必须有依赖证据；
- 包 restore、build、run 使用独立 `ArtifactsPath` 和 NuGet 缓存，不写日常开发的共享 `bin/obj`；
- 发布脚本结束后不得留下指向已删除缓存的 `project.assets.json`；正常解决方案 locked restore/build 必须立即可运行；
- `stage/` 整体退出 Git 并加入忽略规则。正式发布只保留当前 `b-Publish`、外部正式槽/回滚目录，以及
  `b-Office/evidence` 中的简明文本证据；RC、旧副本和验证 `bin/obj` 不入库。

### 5.6 复杂代码演进

本版不以“文件必须低于多少行”为目标。只有当提取能直接支持测试和所有权边界时才拆分：

- 从 `ModulesView` 提取目录读取/筛选状态，视图只绑定快照和选择；
- 从 `ShellWindow` 提取宿主角色与管理目录装配，不让窗口构造继续承载跨进程判断；
- 从 `BuiltinCommands` 提取命令定义与宿主处理器绑定，避免服务端/桌面端重复描述；
- `ModuleHost` 的扫描、注册换代、UI 生命周期分别建立测试边界，但不改变 ALC 卸载顺序；
- `DockingHost` 只有在本版触及停靠回归时才拆，且必须先固定布局序列化与损坏恢复测试。

任何拆分必须保持公共包 API、命令名、窗口 ID 和模块 ABI；需要破坏性契约时必须显式列出消费者迁移并重新
编译 SE2SW 等 UI 模块，不能把二进制不兼容伪装成补丁更新。

## 7. 联合实施顺序

1. 固定 AppShell 与两个用户缺陷的失败前证据：进程角色、命令结果、远端 JSON、视图节点计数、包体积和仓库状态；
2. 建立标准测试项目和最小失败用例，先让 BUG276-01/02 在自动测试中稳定失败；
3. 建立角色感知的管理目录边界，修复模块指令来源分裂，并覆盖热重载快照换代；
4. 固定远端 DTO/JSON 合同，修复继承树投影、空状态和交互，不允许只通过增加刷新解决；
5. 修复 PackageSmoke RID 和隔离输出，建立体积与非目标资产门禁；
6. 清理并忽略仓库 `stage/`，发布脚本改用可删除的外部/忽略暂存区，保留简明证据；
7. 只对本版触及的超大类做职责提取，执行四包、OHS、模块和 GUI 兼容矩阵；
8. 在 Debug/Release 下执行 `dotnet test`、PackageSmoke、功能域 Smoke，再从独立 staging 启动 GUI；
9. 生成发布 manifest、文件哈希和命令契约指纹，确认 V2.7.5 管道化成果没有回归；
10. 完成 AppShell/OHS 正式部署、模块热重载和回滚演练后，才能把本文状态改为已交付并抽干到现行手册。

## 8. 禁止的伪修复

- 不得把模块指令明细重新改成本地注册表专用，以规避前端/服务分离问题；
- 不得把服务端树转成一段文本后在前端重新解析，绕过结构化投影合同；
- 不得用固定模块数量、固定指令总数或固定分支数量作为唯一通过条件；
- 不得只验证 `module.list`/`proj.tree` 命令成功而不验证窗口内容、节点数量和交互；
- 不得把 V2.7.3 的旧 staging 快照或 `stage/` 中的生成物当作当前源码或验收真值。
- 不得只删除本机 PackageSmoke 输出而不修 RID 和体积门禁；下次构建会原样复发；
- 不得新增更多手写 Smoke 来代替标准单元/契约测试；
- 不得用全局 `ExcludeAssets=runtime` 粗暴去掉 SQLite 原生库，导致 Windows 正式运行时缺失；
- 不得为降低行数机械拆分类文件，或在没有兼容测试时重写 DockingHost、ModuleHost、Web/MCP 核心。

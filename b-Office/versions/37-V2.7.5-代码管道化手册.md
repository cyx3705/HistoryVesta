## 0. 结论

OHS 与 AppShell **可继续开发，但当前只达到“局部管道化”，尚未达到“增加一项事实，其余消费者自动形成”**。

已经形成良好管道的部分包括：

- OHS 通过 `ProjectReference` 使用 AppShell 唯一源码，不再维护框架副本；
- `CommandDescriptor` 已能向 Help、命令目录、MCP schema/tools、Web `/api/commands` 和命令手册投影；
- `CommandRegistry` 对重名注册立即失败，模块热装载沿同一注册表增删；
- OHS 产品版本已收口到 `StudioVersion.props`，GUI 与 Service 共用；
- `b-Office/meta` 六份产品文档通过项目发布项进入 `b-Publish/docs`，审查时逐文件 SHA-256 一致；
- AppShell 发布脚本已有锁定还原、双配置构建、漏洞审计、隔离包消费、产物哈希和不可覆盖发布。

主要问题不是“完全没有架构”，而是**管道在进程边界、版本发布边界和安全保留域边界断开**。
当前新增一个前端命令、AppShell 版本或内置命令域，仍要求 AI 记住多处硬编码；漏改时有些测试会失败，
有些则能静默进入运行时。V2.7.5 必须把这些记忆型步骤改为生成、投影或强制校验。

审查判断：

| 维度 | 当前等级 | 结论 |
|---|---:|---|
| 唯一源码 | A | OHS/AppShell 边界清楚，继续保持 |
| 命令元数据投影 | A- | 单进程内成熟，跨前端/服务断链 |
| 模块发现与界面注册 | B+ | 清单和运行时注册较好，保留域仍手写 |
| 产品版本 | A- | OHS 已收口 |
| AppShell 包版本 | D | 同一版本散落在构建、脚本、烟测和说明中 |
| OHS 发布 | C- | 项目发布项可工作，但缺少正式的单入口 staging/验证脚本 |
| 测试抗漂移 | C | 有很多回归，但存在固定数量、固定名单和重复装配 |
| 文档派生 | B | 命令手册与发布文档已有管道，版本事实和状态文字仍会漂移 |

## 1. “代码管道化”的严格定义

### 1.1 四类文件

以后任何事实只能属于以下一类：

| 类别 | 定义 | 能否手改 | 示例 |
|---|---|---:|---|
| 真值源（Source） | 人或 AI 唯一需要修改的位置 | 可以 | `CommandDescriptor`、版本 props、模块 manifest |
| 投影器（Projector） | 从真值源产生另一种运行时表达 | 改机制，不改结果 | MCP exporter、Web catalog、菜单构建器 |
| 生成物（Generated） | 可删除并从真值源重建 | 禁止 | 命令手册、发布 manifest、checksums |
| 人工设计物（Curated） | 无法从事实机械推导的产品决策 | 可以，但须引用真值 | 菜单分组、用户文案、风险审批、迁移策略 |

“两个位置内容相同”不等于管道化。只有下游可以从上游重建，且 CI 能证明一致，才算管道。

### 1.2 一项功能的标准流向

```text
功能定义/命令描述符（唯一真值）
  ├─ 本地 CommandRegistry
  ├─ 前端/服务执行站点与代理目录
  ├─ Help / command.list / command.show
  ├─ MCP tools/list / inputSchema / 暴露状态
  ├─ Web GET /api/commands
  ├─ GUI 命令集与指令详情
  ├─ 生成命令手册
  └─ 契约指纹、回归快照与发布证据
```

开发者只在真值源写一次名称、摘要、参数、只读性、危险性和执行站点。任何消费者再写一次同名数组、
`switch` 或数量常量，均视为管道断点。

### 1.3 不追求“自动生成一切”

以下内容必须保留人工判断：

- 菜单放在哪一组、窗口默认停靠位置、业务页面如何编排；
- MCP 硬排除、安全确认、凭据边界和破坏性操作审批；
- 数据迁移、兼容策略和弃用期限；
- 面向用户的解释文字与版本叙事；
- 有意维护的兼容性 golden snapshot。

但人工设计物只能保存“决策”，不得复制名称、参数、版本号等机器事实。比如菜单可以人工决定显示
“退出”，但其目标必须是经过注册表解析和启动校验的命令引用，不能成为不受校验的字符串孤岛。

## 2. 现场审查证据

### 2.1 已经合格的管道

#### CP-01 · AppShell 唯一源码

`b-Code-Studio/Studio.csproj` 直接引用 `b-Code-AppShell/src/AppShell.Core|Services|Shell|ServiceHost`。
这是正确的伞形仓库内部开发形态。OHS 不得复制 AppShell 类，也不得改为引用 `z-Package-AppShell`
中的旧包来解决本仓库构建问题。

#### CP-02 · 命令描述符向外投影

`CommandRegistry` 是进程内命令目录真值；注册时禁止覆盖，并提供变更事件。`CommandSchemaExporter`
从注册表即时生成 MCP 工具名、描述、参数 JSON Schema 和危险标记；`CommandManualGenerator`、
`command.*`、管理页以及 Web `/api/commands` 均消费注册表。这一方向不应重造第二套 schema。

#### CP-03 · 模块运行时发现

`ModuleHost` 从程序集和 XML 文档形成命令描述符，并按 `module:<name>` 记录来源；UI 模块经
`IShellUiRegistrar` 注册普通工具窗口，owner 卸载时统一回收。这已经是“模块定义一次、命令/UI
随装载形成”的正确基础。

#### CP-04 · OHS 版本源

`b-Code-Studio/StudioVersion.props` 是 OHS 产品版本唯一源；GUI 与 Service 项目都从它读取。
`AppIdentity` 再从程序集身份向标题、日志、MCP serverInfo 等运行时表面投影。后续不得在 C# 中写
OHS 版本常量。

#### CP-05 · 产品文档发布

`Studio.csproj` 把 `b-Office/meta` 六份文档链接为发布目录 `docs/*`。本次审查对源文件和
`b-Publish/docs` 逐文件计算 SHA-256，六对全部一致。该链保留，但要由正式发布脚本验证，不能依靠
“当前碰巧一致”。

### 2.2 高风险断点（V2.7.5 必须清偿）

#### R275-01 · 前端命令在服务端存在第二份名称白名单

证据：`b-Code-Studio/Service/ServiceBuiltinCommands.cs` 的 `FrontendCommands` 手写了 `cls`、
`win.*`、`page.*`、`layout.*`、`panel.*`、`res.*` 等名称；随后为每个名称再造一个
`CommandDescriptor`，并另写一遍只读判定。

后果：

- AppShell 新增前端命令后，必须同时修改真实注册处和 OHS 代理数组；
- 漏改时前端本地有命令，但服务、MCP/Web 目录和远程路由可能看不到；
- 代理使用 `AllowUnspecifiedParameters=true`，服务目录丢失真实参数 schema；
- `Readonly` 又按名称判断，可能与真实描述符安全语义不同；
- AI 很容易根据一次成功构建误判功能已经贯通。

裁决：**禁止保留按名称复制的 `FrontendCommands`。**前端代理必须由真实命令元数据形成。

#### R275-02 · AppShell 内置命令与 OHS ServiceBuiltinCommands 重复描述

`help`、`app.get/set/opendata`、`db.list/tables/schema/query/export/sql` 等能力在 AppShell
`BuiltinCommands` 和 OHS `ServiceBuiltinCommands` 中分别构造描述符。两者摘要、参数、执行站点和
返回结构可以独立漂移。

裁决：把“命令定义”和“宿主处理器绑定”拆开。AppShell 提供可复用定义，桌面宿主和服务宿主只绑定
各自 handler/capability；禁止复制整份描述符。

#### R275-03 · AppShell 版本至少存在四层人工同步

审查快照中 `0.7.1` 同时存在于：

- `Directory.Build.props` 的 `VersionPrefix/Version/AssemblyVersion/FileVersion/InformationalVersion`；
- `Directory.Packages.props` 的两个 OneHistory 包版本；
- `Publish-AppShell.ps1` 的默认值、允许值和演示程序 FileVersion 断言；
- `PackageSmoke/Program.cs` 的程序集版本与 `AppVersion` 期望；
- README、PACKAGE、版本记录和专项文档示例。

发布脚本很严格，但严格地校验了另一份手写常量，仍然需要 AI 多点改值。

裁决：新增 AppShell 单一版本属性源；脚本、包烟测、包引用和发布 manifest 全部读取它。文档中的
机器事实块由发布流程更新/校验，叙事段落仍人工维护。

#### R275-04 · 内置命令域是手写保留表，生产环境没有动态阻断

`ToolManifestLoader.BuiltinDomains` 手写 `app/win/db/...`。新增一级命令域时必须同步改名单，否则模块
可以占用框架新域。`FindUnreservedBuiltinDomains` 虽声明为启动自检，但审查时只在 `WiringSuite`
中被调用，生产装配没有调用。

裁决：模块名冲突判断必须消费已装配 `CommandRegistry` 自动提取的一级域；静态名单只允许保存
“无点号根命令”或尚未装配的永久保留词，并必须与动态集合合并。生产启动在模块装载前发现冲突即拒绝，
不能只依赖测试提醒开发者补名单。

#### R275-05 · OHS 尚无正式、可重复的产品发布入口

AppShell 有 `Publish-AppShell.ps1`，OHS 当前主要依靠项目发布项和人工执行 `dotnet publish` 形成
`b-Publish`。这能复制文件，但没有一个仓库内入口同时负责：干净 staging、双 EXE/未来单 EXE 身份、
版本、文档哈希、运行时依赖、旧文件清除、Smoke、部署 manifest 和原子替换。

裁决：V2.7.3 若已建立单程序发布脚本，V2.7.5 直接加固；若未建立，V2.7.5 必须补齐。正式发布不得
向旧 `b-Publish` 增量覆盖。

### 2.3 中风险断点（同版治理）

#### R275-06 · 测试复制生产装配和固定目录数量

`WiringSuite` 手工复写命令组注册次序；`ServiceWebSuite` 三处写死服务命令数量 `117`。新增一个合法
命令会要求修改测试常量，但测试并不能证明遗漏的消费者都已同步。

裁决：

- 装配测试直接调用正式 composition factory，或 production/test 共用同一 feature collection；
- 数量只作为观测值写入快照，不作为主要契约；
- 主要断言改为集合相等、元数据相等、投影可逆和契约指纹相等；
- 若安全审查确实需要固定名单，保存为显式批准的 golden 文件，不散在 C# 数组中。

#### R275-07 · `expectedReadonly` 重新制造只读性第二真值

`CommandDescriptor.Readonly` 已是只读性真值，`McpExposurePolicy` 也已清空兼容白名单；但
`WiringSuite.expectedReadonly` 又手写完整名单，并用 `SetEquals` 校验。

裁决：普通一致性测试只验证“所有投影读取描述符值”。安全基线变化另走一份可审阅 golden diff，
明确显示新增/删除了哪些 readonly/dangerous/hidden 命令。不能把安全审批和运行时真值混成两套代码。

#### R275-08 · 静态菜单命令字符串缺少统一校验

“视图”菜单已从 Docking descriptor 动态形成，是正确方向；文件/工具/帮助菜单仍含 `app.exit`、
`app.opendata`、`help`、`app.about` 等命令字符串。菜单本身需要人工设计，不要求把全部命令自动变成
菜单，但这些引用必须在启动或测试时解析到真实命令及合法参数。

裁决：引入轻量 `UiActionDescriptor` 或集中菜单定义，并由注册表校验命令引用。未知命令、参数缺失或
执行站点不兼容时，测试立即失败。

#### R275-09 · 标准窗口 Id 仍靠跨文件字符串约定

`console/table/resource/mcp/commanddetail/modules` 同时出现在 OHS 布局声明与 AppShell
`TakeOverDescriptor`。当前机制能保留派生布局并由框架注入内容，设计正确；但 Id 拼写没有类型化契约。

裁决：AppShell 导出标准窗口 Id 常量或强类型 key。OHS 只选择位置和比例，不复制框架窗口身份文字。

#### R275-10 · 说明文档状态会与代码事实漂移

审查时 AppShell README 已按 0.7.1 给出安装与发布示例，但末尾仍写 0.7.0/0.7.1“两者均待实施”，
与版本记录和现场代码状态矛盾。这不是运行时缺陷，却证明版本事实靠手工维护会漂移。

裁决：README/PACKAGE 中版本号、包矩阵、目标框架和交付状态应有受标记的事实区块，由发布预检生成或
校验；正文评价仍人工编写。V2.7.2 完成文档迁移后，以新位置为准实施。

## 3. 目标架构

### 3.1 命令定义与处理器分离

新增一个不依赖 WPF 的命令契约模型，继续以现有 `CommandDescriptor` 为运行时对象，不另造平行总线：

```text
CommandDefinition                 纯元数据，可规范化/序列化/算哈希
  Name / Summary / Example
  Parameters
  Readonly / Dangerous policy
  ExecutionSite / capability

CommandBinding                    宿主绑定
  Definition + Handler

CommandDescriptor                现有总线运行时形态
  由 CommandBinding 形成
```

约束：

1. 名称、参数、只读性、示例和执行站点只存在于 `CommandDefinition`；
2. handler、WPF Dispatcher、数据库实例等宿主对象只存在于 binding；
3. 服务端前端代理由 definition 自动生成，保留完整参数 schema，不再开放任意参数；
4. Help、MCP、Web、GUI 和手册仍消费最终 registry，不直接读取源码文件；
5. 动态模块若不能在编译期共享 definition，则由前端会话握手上报规范化 catalog，服务注册会话级代理；
6. 前端断开时代理可保留目录但明确标为 unavailable，或随会话卸载，具体策略在 M1 固化。

### 3.2 契约指纹

为命令目录定义稳定规范化格式：

- 按命令名 ordinal 排序；
- 参数按声明顺序输出；
- 只包含名称、参数、默认值、允许值、readonly、dangerous、executionSite 等契约字段；
- 不包含对象地址、时间、来源绝对路径和本地化运行时消息；
- UTF-8 无 BOM，LF，SHA-256。

前端连接服务时交换 `catalogVersion + catalogSha256`。不一致时：

- 纯本地 GUI 可以启动；
- 远程/MCP 不得把不一致命令宣称为可用；
- 日志和健康接口明确报告缺失、新增及元数据差异；
- 正式发布 Smoke 必须做到预期集合完全一致。

指纹用于发现漂移，不用于替代逐项差异报告。

### 3.3 版本唯一源

AppShell 新增一个版本源，例如 `AppShellVersion.props`：

```xml
<PropertyGroup>
  <AppShellVersion>0.x.y</AppShellVersion>
</PropertyGroup>
```

由 MSBuild 推导 `Version/VersionPrefix/AssemblyVersion/FileVersion/InformationalVersion`。发布脚本使用
`dotnet msbuild -getProperty:AppShellVersion`（或等价可靠方式）读取，不再接受与源码版本相互独立的默认值。
若保留 `-Version` 参数，它只能作为期望值并与真值比较，不能决定构建版本。

PackageSmoke 从被测程序集/生成的测试属性读取期望；中央包引用使用同一属性。README/PACKAGE 中安装示例
由事实区块生成或由预检验证。

OHS 继续使用 `StudioVersion.props`。V2.7.5 只补齐 FileVersion/InformationalVersion 和发布验证，不新增
第二个 OHS 版本文件。

### 3.4 动态保留域

在模块清单装载前，从已注册内置命令计算：

```text
reservedDomains = registry.All()
  -> name 中第一个点号之前的一级域
  -> OrdinalIgnoreCase 去重
```

`ModuleHost/ToolManifestLoader` 通过参数接收该集合。模块名与任一域冲突即拒绝。永久保留词若没有当前命令，
可以保存在一个小型显式集合中，并写明原因；不允许复制全部已注册域。

### 3.5 发布与文档

OHS/AppShell 分别拥有一个 staging 入口，但共享相同阶段语义：

```text
restore locked
→ Debug/Release build
→ tests/smoke
→ publish/pack 到全新 staging
→ 身份、版本、依赖、文档、契约指纹校验
→ 生成 manifest + SHA-256
→ 可选不可变发布/原子部署
```

`b-Publish` 是正式快照，不是编译缓存。发布必须先形成完整 staging，再整目录替换；禁止 `Copy-Item -Force`
对旧目录增量修补。生成物必须记录源码 commit、dirty 状态、SDK、RID、self-contained、文件列表、哈希、
OHS/AppShell 版本和命令契约指纹。

## 4. AI 开发强制规约

### 4.1 开工前四问

任何 AI 新增或修改功能前必须在工作记录中回答：

1. 这项事实的唯一真值源是哪一个类型/文件？
2. 哪些运行时、UI、协议、文档和发布表面消费它？
3. 消费者是自动投影，还是仍需手工同步？
4. 漏掉一个消费者时，哪条自动测试会阻断？

第 3 或第 4 问答不出来，不得直接施工；先补管道或把缺口写入当版风险裁决。

### 4.2 禁止模式

以下 diff 默认拒绝：

- 为已有命令再加一份命令名数组、readonly 数组、参数字典或 MCP 名称表；
- 在 C#、PowerShell、测试和文档中分别写同一版本号；
- 用固定命令总数证明目录完整；
- 测试手工复写 production composition root；
- UI 菜单直接引用未经注册表校验的命令字符串；
- 新增内置命令域后要求开发者“记得”补模块保留名单；
- 手工编辑命令手册、manifest、checksums 或发布目录文件；
- 发布到已有目录并靠文件覆盖得到“最新版本”；
- 为绕过管道校验而打开 `AllowUnspecifiedParameters`、降低安全档或删除断言。

### 4.3 允许模式

- 在同一个 `RegisterAll` 内写多条不同命令描述符；每条命令本身就是独立真值，不算重复；
- composition root 明确选择启用哪些 feature，但 feature 清单必须可供生产和测试共用；
- 人工设计菜单分组、窗口位置和用户文字，同时通过 key/registry 引用机器事实；
- 维护安全 golden snapshot；其变更必须在 PR/版本文档中逐项解释；
- 为兼容旧版本保留映射表，但必须有来源版本、删除版本和回归测试。

### 4.4 修改完成定义

一项功能只有同时满足以下条件才算完成：

- 真值源只改一处；
- 本地、服务、Web、MCP、GUI 与命令手册投影一致；
- 契约指纹或集合对账通过；
- 不需要再手改固定数量、版本或名称名单；
- Debug/Release 和相关 Smoke 通过；
- staging 可从空目录复现，manifest 可追溯；
- 用户文档只写行为和决策，不复制可生成事实。

## 8. 风险与裁决

| 风险 | 级别 | 裁决 |
|---|---:|---|
| 在 V2.7.3/V2.7.4 在制期间重构命令装配导致合并冲突 | 高 | V2.7.5 只立项，前置交付后 M0 重定位再施工 |

## 10. 后续开发者最短操作手册

### 新增命令

1. 在所属 feature 的唯一 `CommandDefinition` 写名称、参数、执行站点与安全语义；
2. 在实际宿主绑定 handler；
3. 运行 PipelineContractSuite，确认服务代理、Web、MCP、GUI 与手册自动出现；
4. 只有需要产品入口时才人工增加菜单/按钮，并通过 action 引用校验；
5. 不修改命令数量、前端名单、readonly 名单或模块保留域。

### 新增模块能力

1. 修改模块 manifest/程序集定义；
2. 由 ModuleHost 发现命令和 UI；
3. 动态保留域从宿主 registry 自动形成；
4. MCP exposure 只在 manifest 或命令定义的既定真值字段声明；
5. 不在 OHS 另登记模块名、命令名或窗口 Id。

### 升版本

1. OHS 只改 `StudioVersion.props`；AppShell 只改 AppShell 版本属性；
2. 执行 staging，不手改脚本、烟测或 README 中的当前版本；
3. 由预检报告所有程序集、包、manifest 和文档事实区块的一致性；
4. 版本记录正文人工说明行为变化；
5. 同版本正式产物已存在时另升版本，不覆盖。

### 发布

1. 从干净 staging 开始；
2. 跑 locked restore、双配置构建、全套测试和协议探针；
3. 生成并核对 manifest、SHA-256 与 catalog 指纹；
4. 预览发布文件树；
5. 整目录原子替换并保留回滚备份。

## 11. 完成定义

V2.7.5 只有在以下事实同时成立时才可标记交付：

- 开发者新增一个前端命令，不再修改 OHS 服务代理名单；
- 开发者新增一个命令域，不再修改模块保留域名单；
- AppShell/OHS 升版各只修改一个真值文件；
- 生产装配与测试不再各维护一份 feature 次序；
- Help、GUI、Web、MCP、命令手册和发布 manifest 可由真实运行时目录对账；
- 安全变化可见、可审批，但不成为运行时第二真值；
- OHS 与 AppShell 均能从空 staging 重建并验证发布物；
- 任意一处管道断开都会在构建、测试或发布预检中明确失败。

在此之前，“AI 已把代码写完”不能作为完成依据；只要仍需人凭记忆到其他文件补名称、版本、数量或名单，
就应判定该功能尚未完成管道化。

### 12.1 口径与复现

即排除 `obj` / `bin` / 测试 / `b-Code-Samples` / `b-Code-OneHistory-V1`。命令条数按
`Name = "域.名"` 去重计数。**先前口径混入测试夹具导致条数偏差，本节为准。**

### 12.2 “功能 / token 比”实测（本次审计的核心问题）

以 V2.4.0 伞形迁移（`b26e7b81`）为基线，同一口径追踪：

| 采样点 | 产品 LOC | 命令数 |
|---|---:|---:|
| V2.4.0 `b26e7b81` | 20,314 | 98 |
| V2.4.2~4 `bdeba1ae` | 20,355 | 98 |
| V2.4.5 `bed53981` | 20,396 | 98 |
| AppShell 0.7.2 `4b0430b4` = HEAD | 22,422 | 106 |
| 工作树（V2.7.x 在制） | 25,505 | 124 |

- **平均成本**：25,505 ÷ 124 ≈ **206 行 / 命令**
- **边际成本**（V2.4.0 → 工作树）：+5,191 行换 +26 条 ≈ **200 行 / 命令**
- 若只算已提交（V2.4.0 → HEAD）：+2,108 行换 +8 条 ≈ **263 行 / 命令**

**判断：边际成本 ≈ 平均成本，没有超线性爆炸，但也没有平台红利。**

这是本次审计最重要的一条结论，也是对“功能 / token 比变差”实感的正式回应：

> 问题不是代码在腐烂，是**抽象没有产生杠杆**。
> 健康的框架型项目，随着 Core 沉淀，第 100 条命令应当显著便宜于第 10 条。
> OHS 现在每加一条命令付的代价和三个版本前一样。

这恰好是 §3.1「命令定义与处理器分离」要解决的问题。**V2.7.5 是否成功，可以用一个客观指标验收：
实施后，新增命令的边际 LOC 必须显著低于 200 行 / 条。** 建议将该指标并入 §11 完成定义。

参照：`BuiltinCommands.cs` 1,154 行承载 40 条命令；单条 `run` 命令为 22 行元数据 + 25 行逻辑，
即约 **47%** 的命令层代码是声明式元数据。需要说明的是，这部分**是承重的**——
`CommandSchemaExporter`、`CommandManualGenerator`、`help`、`CommandDetailView`、`WebGateway`
五处真实消费它，不是仪式。代价是“一条命令开口价约 30 行”，这是设计换来的定价，
不属于浪费，但也意味着命令数增长会直接线性推高体积。

| 维度 | 等级 | 实测依据 |
|---|---:|---|
| 构建健康度 | **A** | `dotnet build OHS.sln -c Debug` → 0 警告 0 错误，10 秒 |

| 测试 | **D** | 无测试框架，无单元测试，套件按版本号组织（QM275-13 / 14） |

**在 warnings-as-errors + nullable 全开下零警告通过，这个纪律性高于 AI 主导开发的平均线。
骨架是稳的，问题集中在“压舱物”和“防线”两侧。**

### 12.4 文档体量：假基线问题

`b-Office/README.md` 称 `snapshots/` 为“结构重构未改变对外行为的客观对账依据”。实测：

1. **无消费方。** 全仓无任何代码、脚本或测试读取 `snapshots/`。`command.manual`
   （`CommandCatalogCommands.cs`）是纯生成器——从注册表渲染 Markdown 并原子写入，
   **没有 verify / diff / compare 模式**。
2. **它已经算出了 SHA-256，但没人存。** `CommandManualPreview` 携带
   `CommandManualGenerator.Sha256(markdown)`，返回后即丢弃。
3. **相邻快照差异（`diff` 计增删行）：**

   | 对比 | 差异 | 基数 |
   |---|---:|---:|
   | `v244-before` → `v244` | 0 行（MD5 相同） | 1,980 |
   | `v242` → `v243-before` | 0 行（MD5 相同） | 1,876 |
   | `v243-before` → `v243` | 2 行（仅 `> 版本：2.4.2` → `2.4.3`） | 1,876 |
   | `v232` → `v233` | 2 行 | 1,976 |
   | `v220` → `v221` | 79 行（4%） | 1,854 |

`v243-before` / `v243` 这一对，设立目的是“逐条证明代码卫生改写没有改变外部行为”。
它证明的方式是**存两份除版本号字面量外完全相同的 1,876 行文件**——而这个结论用一行
SHA-256 对比即可得到，且更严格：现在这套连“有没有人真的比对过”都无从查证。

**处置方向（QM275-17 / 18）：删除假基线，再建立真基线。** `b-Office` 不再承载运行输出。

`{version, commandCount, catalogSha256}` 和必要协议字段；`command.manual` 增 `verify=true`。
完整命令手册、控制台回显和接口响应只进入临时测试目录或 CI artifacts，不纳入 Git。

# SE2SW V3.6.3 性能与零件级并行

> 日期：2026-08-04
> 基线：V3.6.1（V3.6.2 正在 debug，本版**不依赖也不阻塞**它）
> 范围：转换管线的耗时结构、固定开销回收、SolidWorks 多实例并行
> 状态：设计文档；全部数字来自真机实测，未实施
>
> 与 V3.6.2 的关系见 §6。

## 1. 触发

用户报告"转换管线性能太差，特别是单个零件特征识别和完全定义草图"。

本文档先把耗时结构量清楚，再判断哪里能省、能省多少。**不做任何未经实测的性能断言**——
这一轮此前已经因为凭推断下结论翻过多次车。

## 2. 实测耗时结构

12 个零件的样件（`风滚子.asm` 全套），识别开启：

| 零件 | 识别耗时 | 特征数 | 草图 |
|---|---|---|---|
| gate-part-1 | 10 431 ms | 18 | 17/17 |
| gate-part-2 | 8 067 ms | 6 | 4/4 |
| gate-part-5 | 7 753 ms | 8 | 8/8 |
| gate-part-9 | 6 686 ms | 5 | 4/4 |
| gate-part-4 | 5 951 ms | 4 | 3/3 |
| …（其余略） | 1 771 – 3 643 ms | 1–2 | 1/1 |
| **识别阶段合计** | **53 864 ms** | | |
| **装配阶段** | **52 820 ms** | | |

单件识别 **2.6 – 10.4 s**，与特征数量正相关。但整轮墙钟远超这两段之和，**差额在固定开销上**。

### 2.1 三块固定开销

| 来源 | 单件成本 | 12 件合计 | 出处 |
|---|---|---|---|
| 每件卸载/重载 FeatureWorks | `UnloadAddIn` + 500 ms + `LoadAddIn` + 500 ms | **≈12 s** | V3.5.2 为隔离 COM 故障引入 |
| 每件启一个子 Worker 进程 | 进程创建 + COM 附着 + 事件管道 | 0.5–1 s/件 | 同上 |
| 重试阶梯（全部踩满） | 种子面 5×400 + 文档激活 5×250 + 识别 10×300 = **6.25 s** | 只有失败件付 | `FeatureRecognizer` 常量 |

前两块是 V3.5.2 修 `RPC_E_SERVERFAULT` 时付的保险费；那次修复是必要的，
但**保险费按"每件都买"收取，而故障是偶发的**。

第三块只有失败件付：实测 `测试零件4` 耗掉 6 157 ms 却识别出 0 个特征——
把重试阶梯全额交出去，换回一个空结果。

**结论：固定开销量级 20–30 s，与识别本身的 54 s 同量级。先削这里比优化识别算法划算。**

## 3. 多实例并行：实测可行

### 3.1 先纠正一个错误断言

本文档作者此前断言"SolidWorks 是单实例，同机起不了第二个，零件级并行不可行"。
**这是错的。** 它把本项目的实现细节（全部用 `Activator.CreateInstance(ProgID)` 取实例，
而该调用确实一定附着到已有会话）误当成了平台约束。

### 3.2 `tools/MultiInstanceProbe` 实测结果

| 项 | 实测 |
|---|---|
| 同机并存可自动化实例 | **3 / 3 全部绑定成功** |
| 实例互相独立 | **3 个不同窗口句柄**（1187614 / 793588 / 1384300） |
| **FeatureWorks 每实例独立加载** | **3 / 3 可用** |
| 绑定耗时 | 3.1 – 3.2 s |
| 单实例内存 | 309 – 453 MB |
| 授权拒绝 | 无 |
| 单实例交接（新进程转交后退出） | **不存在**，三个进程各自存活 |
| 探针收尾残留进程 | 0 |

**FeatureWorks 每实例独立可用是决定性的一条**：它意味着占大头的识别环节可以真并行，
而不是只能并行导入、保存这些小头。

### 3.3 正确的多实例获取方式

```
Process.Start("sldworks.exe")                    // 绕开 COM 类工厂
→ 枚举运行对象表（IRunningObjectTable::EnumRunning）
→ 匹配显示名 SolidWorks_PID_<pid>
→ IRunningObjectTable::GetObject() 取实例
```

**三条不要**，每条都是实测踩出来的：

| 不要 | 原因 |
|---|---|
| `Activator.CreateInstance(ProgID)` | 一定附着到已有会话，永远拿不到第二个 |
| `Marshal.BindToMoniker("…")` | 按文件 moniker 解析，取不到 ROT 里的 item moniker |
| 凭记忆写 `!SldWorks.Application:<pid>` | 本机实际注册名是 `SolidWorks_PID_<pid>` |

获取方式必须走**枚举 + 匹配**，不要依赖任何名字格式约定——
本次调查里三次失败全部来自"猜格式"，唯一一次有效动作是把 ROT 里实际有什么列出来。

## 4. 本版方案

按"改动小、风险低、收益确定"排序。前两条不动架构，第三条才引入并行。

### 4.1 按需重载 FeatureWorks（省 ≈12 s / 12 件）

现在每件无条件 `UnloadAddIn → 等 500 ms → LoadAddIn → 等 500 ms`。
改为**只在上一件报告了故障标志时才重置**——`FeatureOutcome.SessionFaulted` 已经是现成信号。

正常件跳过重载，故障后仍然重置。保险还在，只是不再对每件收费。

两个 `PumpAndWait(500)` 也是未经测量的经验值，本版顺带量一次真实需要的等待。

### 4.2 重试阶梯改为指数退避 + 早停

现在是固定次数 × 固定间隔，失败件必然付满 6.25 s。改为：

- 间隔指数退避（如 100 / 200 / 400 / 800 ms），总预算不变但前几次更快返回；
- 识别连续返回 0 且**几何未变化**时提前判定无望，不跑满 10 次。

对成功件无影响（它们只走第一次），对失败件省数秒。

### 4.3 零件级并行（识别阶段 3 路）

V3.5.2 已经把每个零件做成**独立子 Worker 进程**——并行的地基已经铺好，
现在只是串行调度它们。本版改为：

```
实例池（N 个自起的 SolidWorks，按 §3.3 获取）
  ↓
N 路并发调度子 Worker，每路绑定池中一个实例
  ↓
汇聚结果，装配阶段仍串行（它本来就快，且有跨层依赖）
```

**并行度按可用内存定，不拍脑袋**：单实例 309–453 MB，3 路约 1 GB。
建议按 `min(逻辑核数, 可用内存 / 512 MB, 4)` 取值，并允许用户在界面上下调。

**隔离性反而更好**：一路的 FeatureWorks 崩了只影响那一路，
不像现在会污染整批（V3.5.4 / V3.5.5 两次事故都是批内污染）。

### 4.4 收益估算

| 项 | 现状 | 预计 | 依据 |
|---|---|---|---|
| 识别阶段（12 件） | 54 s | 25–30 s | 3 路并行，扣除每实例 3 s 绑定与冷启动 |
| FeatureWorks 重载 | 12 s | ≈1 s | 只在故障后重置 |
| 失败件重试 | 6.25 s/件 | 2–3 s/件 | 指数退避 + 早停 |

**零件阶段合计预计砍掉六成左右。装配阶段不动。**

这些是估算不是承诺；§5 的门禁负责给出真实数字。

## 5. 验收

### 5.1 性能门禁（新增）

现有门禁只判对错，不判快慢。本版新增分段计时并纳入门禁输出：

```
SE 导出 / 子 Worker 启动 / 加载项重载 / 识别 / 草图定义 / 保存 / 装配构建
```

**先埋点、再优化**——没有分段数据的优化就是又一次"拿推断替代测量"。

### 5.2 正确性判据一条都不放宽

性能改动**不得**以任何正确性判据为代价：

| 判据 | 出处 | 本版要求 |
|---|---|---|
| 产物体积与 XT 一致 | 28 号 | 不变 |
| 叶组件世界位置 < 1e-6 m | 20 号 | 不变 |
| 配合落位计数自洽 | 32 号 | 不变 |
| 会话零残留文档 | 32 号 | 不变 |
| 识别 + 配合组合档 | 32 号 | 不变 |

并行引入后**必须复跑全部三档真机门禁**，且 `PartGeometryProbe` 逐件核对体积——
多实例最大的风险正是"产物张冠李戴"，而这恰恰是 28 号文档里已经发生过一次的事故形态。

### 5.3 新增：并行产物身份门禁

多实例下每一路各写各的文件，必须证明没有串台：

- 每个 `.SLDPRT` 的体积与其**对应 XT** 一致（不是与任意 XT 一致）；
- 并行跑与串行跑的产物逐字节或逐几何一致。

## 6. 与 V3.6.2 的关系

V3.6.2（FeatureWorks 识别参数错误）正在 debug，它改的是**识别结果的语义正确性**；
本版改的是**调度与开销**。两者触碰的代码面基本不重叠：

| | V3.6.2 | V3.6.3 |
|---|---|---|
| 关注 | 识别参数、结果校验 | 重载策略、重试节奏、并行调度 |
| 主要文件 | `FeatureRecognizer` 的参数与校验段 | `SolidWorksPartImportIsolation`、实例池 |

**但有一处必须协调**：§4.2 的"识别无望即早停"依赖"什么算识别成功"的判据，
而那正是 V3.6.2 要重新定义的。因此 §4.2 应当在 V3.6.2 落地后再实施，
或者实施时只改节奏、不碰判据。

§4.1 与 §4.3 与 V3.6.2 无耦合，可以先行。

## 7. 实施顺序

1. **分段计时埋点**（§5.1）——不改行为，先拿数据。
2. **按需重载 FeatureWorks**（§4.1）——收益确定、改动最小。
3. **并行产物身份门禁**（§5.3）——**在引入并行之前**先有断言。
4. **实例池与 N 路调度**（§4.3）。
5. **重试节奏**（§4.2）——等 V3.6.2 结论。

第 3 步必须在第 4 步之前。理由是这一轮反复付过学费的那条：
**先有能抓住新失败模式的门禁，再引入会产生该失败模式的能力。**

## 8. 待确认

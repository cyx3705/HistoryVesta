# SE2SW V3.5.2 FeatureWorks 调用隔离修复

> 日期：2026-08-03  
> 基线：V3.5.1  
> 范围：SE2SW Worker、共享 Worker 协议、非交互式真机冒烟  
> 不涉及：AppShell、OHS、窗口界面、装配关系算法

## 1. 问题与结论

装配转换开启特征识别后，前几个零件正常，随后 FeatureWorks 抛出
`0x80010105 RPC_E_SERVERFAULT`。故障发生后，旧管线仍在同一个 Worker、同一个 STA、
同一个 SolidWorks/FeatureWorks 会话中处理剩余零件，最终可能出现：

- 后续零件全部失去特征；
- `LoadFile4` 返回上一件文档，导致不同零件被保存成同一个形状；
- 后续 SolidWorks 装配构建或其他 SW 模块继续使用已故障会话，表现为整体崩溃。

`FeatureWorksBatchSmoke` 对 `测试零件5.par`、`测试零件6.par` 的独立 Worker 实测均成功：
各识别 1 个特征、草图 1/1 完全定义、无降级、无 `SessionFaulted`，源文件哈希未变。
因此零件几何不是根因，根因是**批量调用边界把 FeatureWorks 的有状态 COM 服务跨零件复用**。

## 2. V3.5.2 调用边界

```text
外层 --request / --assembly Worker
  ├─ Solid Edge 批量导出 XT
  ├─ 零件 A -> --import-part 子 Worker -> 重置 FeatureWorks -> 导入/识别/保存 -> 退出
  ├─ 零件 B -> --import-part 子 Worker -> 重置 FeatureWorks -> 导入/识别/保存 -> 退出
  └─ 父 Worker 汇总事件并继续构建 SLDASM
```

规则如下：

1. `RecognizeFeatures=true` 时，一个零件对应一个短生命周期子 Worker/STA。
2. SolidWorks 是单实例；若子 Worker 附着用户已打开的会话，仅换 Worker 不能重启原生服务。
   因此每件开始前使用官方 `UnloadAddIn/LoadAddIn` 重置 FeatureWorks，并保留加载项原始加载状态。
3. 子 Worker 报告 `SessionFaulted` 时，父 Worker 丢弃该次降级 SLDPRT，最多用三个全新子 Worker 重试。
4. 重试仍失败时保留最后一次经过导入身份和几何守卫确认的哑实体；不得串件、不得保存错误几何。
5. `RecognizeFeatures=false` 时仍走原批量导入，不承担额外进程启动成本。
6. 原 `--request`、`--probe-assembly`、`--assembly` 对外协议不变；`--import-part` 只供 Worker 内部使用。

## 3. 协议与生命周期

- 新增 `PartImportRequest`，只允许一个已经存在的 `.x_t` 和一个 `.SLDPRT` 输出。
- `WorkerRequestValidator` 校验源 `.par`、已有 XT、输出目录和覆盖策略。
- `WorkerReporter.Forward` 完整转发 `Feature`、`Assembly`、`Mate`、原生错误、产物和复用类别；
  子事件统一归入父批次。
- 父取消信号会写入子 Worker 的取消文件；15 秒宽限后只终止父 Worker 自己创建的子进程树。
- 临时请求与取消文件位于 `%TEMP%\SE2SW-PartImport`，每次结束尽力清理。
- 不关闭、不强杀转换前已经存在的用户 SolidWorks 进程。

## 4. 自动化覆盖

`SE2SW.Smoke` 新增：

- 内部动词识别与未知动词拒绝；
- `PartImportRequest` JSON 往返和路径校验；
- 只有开启 FeatureWorks 才启用隔离；
- 子 Worker 事件转发不丢 `FeatureOutcome`、`MateOutcome`、错误码和产物类别。

`FeatureWorksBatchSmoke` 新增：

- `--single-batch`：一个外层 Worker 承载多个零件，复现真实模块调用方式；
- `--require-healthy-recognition`：任何降级、几何变化或会话故障都使门禁失败；
- 源文件和副本 SHA-256、XT/SLDPRT 非空、Worker 事件、CAD 进程基线核验。

## 5. 真机结果

### 5.1 调用隔离有效

当前测试前已有用户 SolidWorks：PID `30908`。在不关闭该进程的条件下，单批转换
`测试零件5.par`、`测试零件6.par`：

| 零件 | 特征 | 草图完全定义 | 降级 | SessionFaulted |
|---|---:|---:|---|---|
| 测试零件5 | 1 | 1/1 | 否 | 否 |
| 测试零件6 | 1 | 1/1 | 否 | 否 |

加载项重置实测返回 `UnloadAddIn=0, LoadAddIn=0`。PID 前后均为 `30908`，Edge 进程
前后均为空，源 `.par` 哈希未变。

五件顺序 `测试零件1/2/4/5/6` 中，1、2、5、6 均健康；测试零件4 在已经故障的
PID 30908 中仍可能返回 `RPC_E_SERVERFAULT`，但 5、6 随后的识别恢复正常，SolidWorks
继续响应且进程基线不变。V3.5.1 的“一个故障污染全部后续零件并拖垮 SW 模块”已被切断。

### 5.2 残余边界

`UnloadAddIn/LoadAddIn` 不能保证修复**进入本次转换前已经深度故障**的 SolidWorks 原生状态。
此时 V3.5.2 会安全降级并继续，不会串件或崩溃；要恢复该零件的 FeatureWorks 成功率，必须让用户
正常保存工作并重启 SolidWorks。模块不得擅自关闭用户会话，因此本次不自动执行该动作。

发布前仍需在正常重启后的干净 SolidWorks 会话重跑五件严格门禁；未通过时不得把
“特征识别全部成功”写入发布结论，但调用隔离与崩溃阻断修复可以独立成立。

## 6. 性能与兼容性

开启识别时，每个唯一零件增加一次 Worker 启动和一次 FeatureWorks 加载项重置，转换时间会增加。
这是用吞吐量换取 COM 故障隔离；未开启识别的零件和装配路径不受影响。

版本升至 `3.5.2`，唯一版本源仍为 `build/SE2SW.Version.props`；OHS manifest 只同步版本和模块描述，
本文档与真机附件只留在 SE2SW 项目，不上抛 OHS `b-Office/evidence`。

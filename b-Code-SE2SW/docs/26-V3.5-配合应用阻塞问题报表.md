## 3. 卡住的现象

### 3.1 症状

对三层样件的每一层，每条 Planar / Axial 关系都是同一个结果：

```
测试装配3.SLDASM 配合重建：0/4 条
  #2 PlanarRelation3d：AddMate5 失败，errorStatus=1；
     选择实况：[1] 类型 2/mark 1/有组件 True，[2] 类型 2/mark 1/有组件 True
  #3 同上
  #4 同上
测试装配1.SLDASM 配合重建：0/9 条（Axial 与 Planar 都失败，实况同上）
风滚子.SLDASM     配合重建：0/43 条（同上）
```

### 3.2 选择实况是干净的

`AddMate5` 之前立刻从 `ISelectionMgr` 读回来的实测值：

| 项 | 值 | 说明 |
|---|---|---|
| `GetSelectedObjectCount2(-1)` | **2** | 不多不少 |
| `GetSelectedObjectType3(i, -1)` | **2** | `swSelFACES` |
| `GetSelectedObjectMark(i)` | **1** | 配合要求的 mark |
| `GetSelectedObjectsComponent4(i, -1)` | **非 null** | 面确实带组件上下文 |

**选择看起来完全符合 `AddMate5` 的前置要求，但它就是不认。**

### 3.3 已经试过、没解决的

| 尝试 | 结果 |
|---|---|
| `IEntity::Select2(append, mark)` | 返回 true，`AddMate5` 仍报 1 |
| 改用 `ISelectionMgr::CreateSelectData` + `ISelectData.Mark = 1` + `IEntity::Select4` | 同上 |
| 每次选择前 `ClearSelection` | 已做，选中数确认为 2 |

### 3.4 还没试过的（建议的下一步）

1. **最小复现**：手工建一个两零件装配，用同一套调用建一条重合配合。
   排除"是我们的装配上下文有问题"还是"调用姿势有问题"。
2. **参数逐个变**：`AddMate5` 的 15 个参数里，
   `WidthMateOption`（现传 0）、`ForPositioningOnly`、`LockRotation`、
   三个 distance 与三个 angle 的取值都没有单独验证过。
3. **换 `IAssemblyDoc::AddMate3`** 对比：若旧版能成功，说明是 AddMate5 的参数语义问题。
4. **面来源换一种**：现在用 `IComponent2::GetBodies3` → `IBody2::GetFaces`。
   可换 `IComponent2::GetBody` 或经 `IModelDocExtension::SelectByID2` 取同一个面做对照，
   看是不是这个来源的 `IFace2` 不被配合接受。
5. **活动文档**：确认 `AddMate5` 调用时装配确实是活动文档
   （代码里在插入组件前调过 `ActivateDocument`，之后没有再打开别的文档，但没有二次确认）。

## 4. 第二个未解问题：0 条配合却漂移 0.34 m

顶层 `风滚子.SLDASM` 在**一条配合都没建起来**的情况下，收尾校验报：

```
配合重建后位置退化：平移 0.34 m、旋转 2（风滚子.SLDASM）。已建 0/43 条。
```

旋转元素偏差 2.0 意味着某个元素从 +1 变成 −1，即某个组件被翻转了 180°。

- 两个子装配层（`测试装配3`、`测试装配1`）同样 0 条配合，漂移都是 **0**；
- 只有顶层出现漂移，而顶层是唯一含**子装配组件**的一层；
- 当时 `EditDelete` 还没有加类型守卫，怀疑过是误删组件，
  **加了守卫后漂移依旧 0.34 m**，所以不是误删。

嫌疑集中在 §3.5 的浮动/固定环节：`UnfixComponent` 作用到子装配组件后，
SolidWorks 可能重新求解或改变了该组件的表示。**未验证。**

好消息是这条被 §3.6 的收尾校验当场拦住并抛错，没有产出错误产物——
安全网按设计工作了。

## 6. 途中修掉的三个 COM 生命周期缺陷（已修，供参考）

这三个都表现为 `COM object that has been separated from its underlying RCW cannot be used`，
根因相同：**`Marshal.FinalReleaseComObject` 会把 RCW 清零，而 .NET 对同一个 COM 指针复用同一个 RCW**。
SolidWorks 反复交还同一对象时，第二次拿到的就是已失效的 RCW。

| 位置 | 被误释放的对象 | 为什么之前没暴露 |
|---|---|---|
| `MateCandidateCollector` | `IBody2` / `ISurface` | V3.5 才开始枚举面 |
| `SolidWorksInteropBridge.GetComponentTransform` | `IMathTransform` | V3.3 每个组件只读一次；V3.5 的校验回滚要反复读 |
| `SolidWorksInteropBridge.SelectedObjectHasComponent` | **`IComponent2`** | 这是我加的诊断助手——它释放的正是调用方手里那个组件 |

最后一条最值得记：**诊断代码把被诊断的对象弄死了**。

由此定下一条规矩，已写进相关注释：
**只对"自己创建、自己拥有"的对象（文档等）做 final 释放；
凡是 SolidWorks 反复交还的共享对象（SelectionMgr、Body、Face、Surface、MathTransform、Component）一律不释放。**

## 8. 结案（2026-08-03）

### 8.1 根因：一行枚举误读

`tools/MateApplyProbe` 用强类型 interop 重放 §3.3 的五种姿势，第一轮就露馅：
每个"失败"的 AddMate5 都返回了**非空 Feature**（Coincident1/2/3/4 连续编号）——配合一直在被成功创建。
随即从官方 swconst 程序集实测枚举：

```
swAddMateError_ErrorUknown        = 0
swAddMateError_NoError            = 1   ← 成功是 1，不是 0
swAddMateError_IncorrectSelections = 4   ← 真正的"选择错误"是 4
```

生产代码写的是 `errorStatus != 0 即失败`：**每一条配合都建成了，然后被我们自己删掉。**
选择方式、AddMate 版本、对齐取值五种姿势"全部失败"的假象由同一行判断制造——
V1（生产原姿势）在修正判定后本来就是对的。

§4 的"0 条配合却漂移 0.34 m"同根：配合创建成功时求解器已按 Aligned/AntiAligned
翻转过组件，随后配合被删——**删配合只删约束，不还原位置**。

### 8.2 三处修复

| 修复 | 位置 |
|---|---|
| 成功判定改为 `mate != null && errorStatus == swAddMateError_NoError(1)` | `SolidWorksMateRebuilder` |
| 回滚补上另一半：删配合后把**全部组件写回基线变换**再重建 | 同上 |
| 对齐一律 `swAlignCLOSEST`：组件已精确位于源位置，这条关系在当前摆放下本来就成立，最近解 = 不动。按 `NormalsAligned` 强指方向会让求解器翻转组件（180°，旋转偏差恒为 2） | `MateTypeMapper` |

顺带：`GroundApplied` 计数（接地关系的去向）、多层合并求和、门禁"全固定"断言在
`--rebuild-mates` 档放宽为统计（位置判据不放宽——它才是真验收）。

### 8.3 终局门禁（三层真实样件，独立重开核验）

| 项 | 结果 |
|---|---|
| 关系落位 | **56/56**：53 条配合重建 + 3 条接地固定，失败 0，计数自洽 |
| 逐层明细 | 测试装配3 3+1、测试装配1 8+1、风滚子 42+1 |
| 22 个叶组件世界位置 | 最大平移偏差 **2.43e-09 m**（阈值 1e-6），旋转 4.0e-15 |
| 固定/浮动 | 每层仅基准件 + 1 个未被关系约束的组件（动量轮，如实报告）保持固定，其余全部由配合约束 |
| 源哈希 / 模板 / 回归 | 未变 / 已恢复 / `RebuildMates=false` 门禁与 Smoke 全绿 |

§3.4 的五条"下一步"实际只用到第 1 条（最小复现）就破案；
§4 的浮动/固定隔离实验同场跑过：漂移 0，该嫌疑排除。

### 8.4 留给后续的教训

**"errorStatus 非零即失败"是从 V1.1 沿用的惯性假设，但每个 COM API 的错误枚举都得单独查表。**
本项目此前的 `errors != 0` 判定（LoadFile4 / SaveAs3 / OpenDoc6）恰好都是 0 = 成功，
养成的直觉在 AddMate5 上翻了车。探针半小时就能给出的答案，推理给不出。

## 0. 一句话定义

AppShell 是一个**通用桌面程序骨架模板**：内置工业软件风格的多窗口停靠系统，与"一切操作皆指令"的统一指令架构，预置五类标准窗口（主窗口 / 表窗口 / 控制台窗口 / 控制窗口群 / 资源窗口）。此后所有小工具、游戏、工业软件、上位机软件，均从该模板派生开发。

---

## 1. 背景与目标

### 1.1 背景

- 后续会持续开发多类桌面程序（小工具、游戏、工业软件、上位机），每次从零搭窗口、日志、数据查看等基础设施是重复浪费。
- 工业软件中被长期验证的"多窗口自由停靠"交互范式，覆盖了绝大多数桌面程序的窗口设计需求。
- 需要一个统一底座：新程序在第一天就拥有完整的窗口体系、指令体系、日志体系、数据查看体系。

### 1.2 设计目标

| 编号 | 目标 |
|---|---|
| G1 | **复用**：任何新程序基于模板半天内跑出可用骨架 |
| G2 | **一致**：所有派生程序共享同一套交互语言（停靠布局 + 指令集），学会一个等于学会全部 |
| G3 | **可追溯**：任何人为操作都以指令形式留痕于控制台与日志，可查、可复现 |
| G4 | **可退化**：即使关闭其他一切窗口，仅靠控制台 + 指令仍可完成程序全部核心操作（"控制台完备性"） |
| G5 | **可扩展**：派生应用只做少数几件事——填主窗口内容、注册指令、声明面板、注册数据库、指定资源目录 |

### 1.3 非目标（模板明确不做的事）

- 不内置任何具体业务逻辑。
- 不内置设备通讯协议（串口 / TCP / Modbus 等由派生的上位机程序自行实现，模板只提供指令入口、日志出口、面板承载能力）。
- 不内置图表 / 报表控件库。
- 不做权限与多用户系统（在指令总线上预留拦截器扩展点，将来可加）。
- 不做 Web 端 / 移动端。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| Shell / 框架层 | 模板本身提供的窗口框架、指令核心与基础服务 |
| **主程序窗体（Main Frame）** | 整个应用的外层窗口（含菜单栏、状态栏），是停靠系统的容器 |
| **主窗口 / 设计器区（中央区）** | 主程序窗体的中央内容区。模板中留白，由派生应用注入真实内容。用户口中的"主窗口就是设计器"即指此区 |
| 工具窗口 | 表窗口、控制台窗口、控制面板窗口、资源窗口的统称，均可停靠 / 浮动 / 隐藏 |
| 停靠（Dock） | 工具窗口吸附在主窗体的上 / 下 / 左 / 右或并入某个标签组 |
| 标签组（Tab Group） | 多个工具窗口叠放于同一区域，通过组**顶部**标签条切换 |
| 浮动（Float） | 工具窗口脱离主窗体成为独立顶层窗口 |
| 指令（Command） | 程序中一切人为操作的统一表达形式，文本语法见 §5.1 |
| 指令总线 | 指令的唯一执行通道：解析 → 校验 → 执行 → 回显 → 落日志 |
| 派生应用 | 基于本模板开发的具体程序 |
| 工作区（Workspace） | 资源窗口所管理的根目录 |

> 注：本文档中"主窗口"若不加说明，指中央设计器区；涉及整个应用外框时写"主程序窗体"。停靠比例均相对**主程序窗体**计算。

## 3. 总体架构

### 3.1 分层

```
┌───────────────────────────────────────────────────────┐
│ 应用扩展层（各派生应用：小工具 / 游戏 / 工业软件 / 上位机）  │
│   · 主窗口内容   · 自定义指令   · 控制面板声明   · 业务数据  │
├───────────────────────────────────────────────────────┤
│ 标准窗口模块层                                           │
│   表窗口 │ 控制台窗口 │ 控制窗口群 │ 资源窗口              │
├───────────────────────────────────────────────────────┤
│ 指令核心层（一切操作的唯一入口）                            │
│   解析器 · 指令注册表 · 分发执行 · 历史 · 撤销(预留) · 脚本  │
├───────────────────────────────────────────────────────┤
│ 服务层                                                  │
│   日志服务 · 数据服务 · 文件服务 · 配置服务                 │
├───────────────────────────────────────────────────────┤
│ Shell 窗口框架层                                         │
│   停靠系统 · 布局持久化 · 菜单栏/状态栏 · 主题              │
└───────────────────────────────────────────────────────┘
```

### 3.2 架构不变量（三条铁律）

1. **一切操作皆指令**：任何改变程序状态或触发动作的人为操作（点按钮、改表格数据、开关/停靠窗口、菜单项……）必须最终经由指令总线执行。UI 控件只是指令的"可视化外壳"。
2. **控制台完备性**：凡是 UI 能完成的操作，必须存在等价指令可在控制台手动完成；反之不要求（允许有指令没有对应 UI）。
3. **窗口皆可弃**：除主窗口（中央区）外，任何工具窗口都可隐藏 / 浮动 / 重排，程序功能不因此受损。

## 4. 窗口系统需求

优先级标注：**P0** 必须（首版交付）｜ **P1** 应该（首版尽量）｜ **P2** 可选（后续版本）

### 4.1 停靠框架（通用行为）

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| W-01 | 每个工具窗口拥有标题栏，可被鼠标拖拽独立移动 | P0 |
| W-02 | 「视图」菜单列出全部窗口，支持对每个窗口执行：显示 / 隐藏 / 浮动 / 复位到默认位置 | P0 |
| W-03 | 拖拽窗口时显示停靠引导（中心十字 + 四边指示器 + 半透明落点预览），支持五种落点：上 / 下 / 左 / 右 / 中心（并入目标标签组） | P0 |
| W-04 | 多个窗口叠放为标签组，**标签条位于组顶部**，点击标签切换当前显示的窗口 | P0 |
| W-05 | 相邻停靠区之间有分隔条，可拖动调整比例；比例按"占主程序窗体的百分比"记录，主窗体缩放时各区按比例重算 | P0 |
| W-06 | 工具窗口可拖出为独立顶层浮动窗口，支持多显示器摆放，可再拖回停靠 | P0 |
| W-07 | 布局持久化：退出时自动保存、启动时自动恢复；提供「视图 → 重置默认布局」 | P0 |
| W-08 | 命名布局方案：可保存 / 加载多套布局（layout.save / layout.load / layout.list） | P1 |
| W-09 | 自动隐藏：工具窗口可"取消图钉"收起到主窗体边缘，鼠标悬停标签滑出 | P1 |
| W-10 | 窗口与布局操作本身也走指令（win.* / layout.*）。拖拽类连续手势在**动作结束时**生成一条等价指令，避免拖动过程刷屏 | P0 |
| W-11 | 同一类工具窗口允许多实例（主要服务于控制面板；表 / 控制台 / 资源窗口默认单例，预留多实例开关） | P1 |

补充规则：

- 主窗口（中央区）是停靠树的根：不可关闭、不可浮动、不可隐藏。
- 工具窗口标题栏上的"关闭"按钮语义为**隐藏**（状态保留），不销毁。
- 布局类指令在控制台归入独立来源类别 `layout`，默认显示、可一键过滤（见 §4.4 C-04）。
- 布局文件损坏时自动回退默认布局并在控制台告警（见 §10 N-06）。

**定位**：中央内容承载区。模板交付时为**留白占位页**，派生应用将其替换为真实内容（游戏画布、组态监视画面、工具主界面等）。

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| M-01 | 提供内容注入点：派生应用以一个"主内容组件"填充中央区（注入点以接口约定职责，本文档不定义代码签名） | P0 |
| M-02 | 模板默认占位页：显示程序名、版本、以及"输入 help 查看指令"等入门提示 | P0 |
| M-03 | 中央区可选多文档标签模式（一个内容 = 一个标签页），默认关闭、接口预留（Q5 已定） | P1 |
| M-04 | 中央区尺寸变化事件对内容组件开放（游戏画布 / 绘图区需要据此重建渲染表面） | P0 |
| M-05 | 中央区需能承载自绘 / 实时渲染表面（游戏帧循环由派生应用驱动，模板保证宿主能力） | P0（WPF 承载方案见 §14.3） |

**定位**：程序**所有数据库**的统一查看与修改入口。它本质上是 `db.*` 指令组的图形外壳——在表窗口做的每一次查询与修改，其等价指令都会回显到控制台。

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| T-01 | 顶部提供数据库连接选择 + 表选择（下拉框或左侧树，允许多个命名连接） | P0 |
| T-02 | 主体为数据网格：列排序、列宽调整、单元格选择复制 | P0 |
| T-03 | 分页浏览（默认每页 500 行，可配置）；虚拟滚动 | P0 / 虚拟滚动 P1 |
| T-04 | 可视化条件筛选（列 + 运算符 + 值，可多条 AND），等价生成 db.query 的 where 参数 | P0 |
| T-05 | 编辑能力：单元格改值、新增行、删除行；提交时逐条生成 db.update / db.insert / db.delete 指令并经总线执行 | P0 |
| T-06 | 编辑提交模式定为**即时逐条提交**（Q7 已定）；暂存-批量提交降为后续增强 | P2（增强部分） |
| T-07 | 表结构查看（字段名、类型、主键、非空），只读 | P0 |
| T-08 | 危险操作保护：不带 where 的整表 update / delete 必须二次确认——UI 路径与手输指令路径**各自都拦截** | P0 |
| T-09 | 导出当前查询结果为 CSV（对应 db.export 指令） | P1 |
| T-10 | SQL 直通（db.sql "..."）：高级用户使用，执行前显著风险提示 | P2 |

**定位**：程序的"素颜"，即程序最基础的样貌。所有指令回显、执行结果、运行日志汇聚于此，并且**必须支持手动输入指令**。关闭其他一切窗口，仅靠控制台即可驱动整个程序（架构不变量 2 的落点）。

**输出区**：

| 编号 | 需求描述 | 优先级 |

| C-01 | 回显每一条被执行的指令，带时间戳与来源标签：`[UI]` `[手动]` `[脚本:文件名]` `[layout]` | P0 |
| C-02 | 显示指令执行结果 / 返回摘要 / 错误信息，错误红色高亮 | P0 |
| C-03 | 汇聚运行日志：Trace / Debug / Info / Warn / Error / Fatal 六级，按级别着色 | P0 |
| C-04 | 过滤器：按日志级别、按来源类别（UI / 手动 / 脚本 / layout / 各指令域）、按关键字；layout 类可一键屏蔽 | P0 |
| C-05 | 滚动缓冲上限（默认 5 万行，超出丢弃最旧），列表 UI 虚拟化保证性能 | P0 |
| C-06 | 右键菜单：复制所选、清屏（等价 cls 指令）、导出当前可见内容到文本文件 | P1 |

| P-02 | 首版支持控件类型：按钮、文本框、数字框（含范围/步进）、下拉框、开关/复选、滑条、文件/目录选择、只读标签 | P0 |

| P-05 | 面板可多实例、各自独立停靠、随布局一起持久化 | P0 |

## 5. 指令系统（核心）

### 5.1 语法（默认方案 v0）

```
域.动作 [位置参数 ...] [键=值 ...]
```

规则：

- **域** = 模块名：框架内置 win / layout / db / res / panel / log / app 等，派生应用可注册自己的域（如 motor、game）。
- 指令名大小写不敏感；参数值保留原始大小写。
- 含空格的值用双引号包裹，内部引号以 `\"` 转义。
- `#` 开头整行为注释（用于脚本文件）；空行忽略。
- 一行一条指令。

示例：

```
db.query table=users where="age>30 and city='北京'" limit=100
win.dock name=console pos=bottom ratio=0.25
motor.jog axis=X speed=200
res.rename path="配方/旧.json" to="配方/新.json"
```

> ✅ 本语法已定稿（Q12 已确认），自此成为**所有派生程序的通用语言**；后续如需变更，须按 §14.4 守则 4 的破坏性变更流程执行。

### 5.2 指令生命周期

```
文本输入 / UI事件
   → 解析（词法+参数）
   → 查指令注册表
   → 参数校验（类型/必填/范围）
   → 拦截器链（二次确认、将来的权限控制，预留扩展点）
   → 执行（同步 或 异步）
   → 结果对象
   → 控制台回显 + 日志落盘
```

约束：

- **长任务必须异步**执行，向控制台上报进度（如 `motor.home ... 45%`），全程不阻塞 UI。（P0）
- 任何指令抛出的异常都被总线捕获：**程序不崩溃**，错误进控制台与日志文件。（P0）
- 未知指令 / 参数拼写错误时，提示最接近的候选指令（"你是不是想输入…"）。（P1）

### 5.3 指令注册

- 框架内置指令组：help / cls / history / run / app.* / log.* / win.* / layout.* / db.* / res.* / panel.*（清单见附录 B）。
- 派生应用注册自定义指令时需提供：指令名、参数定义（名 / 类型 / 是否必填 / 默认值 / 说明）、执行体、帮助文本、是否需要二次确认、是否支持撤销。
- 指令名冲突在启动时检测并报错，禁止静默覆盖。（P0）

### 5.4 历史与撤销

- `history` 查看本次会话指令历史；历史持久化条数可配置。（P1）
- 撤销 / 重做（Q6 已定）：首版**只预留接口**——指令接口带撤销能力位、总线维护可撤销栈，不强制任何内置指令实现；整体功能列 P2。

### 5.5 脚本

- `run file=<路径>`：逐行执行指令脚本（纯文本，一行一条，支持 # 注释与空行）。（P1）
- 出错策略：默认中断并报告行号；`run file=x.txt continue=true` 时跳过错误继续。（P1）
- 意义：这是"操作可复现"的最终落地——控制台历史稍作整理即可保存为脚本，重放一次昨天的全部操作。

## 11. 验收标准（模板首版，逐条可勾选）

1. 将表窗口拖到主窗体左侧停靠，比例调至 30%，**重启后布局原样恢复**。
2. 将表窗口与控制台拖成一个标签组，标签条位于组顶部，点击可切换。
3. 任一工具窗口可拖出为浮动窗置于第二显示器，重启后位置恢复。
4. 在表窗口修改一个单元格 → 控制台出现等价 db.update 回显；在控制台**手输同一条指令** → 表窗口数据同步变化。
5. 关闭除主窗口与控制台外的全部窗口，仅用手输指令完成：查询一张表、修改一条数据、新建一个文件夹、显示并停靠一个控制面板。（控制台完备性验收）
6. 在面板 JSON 中定义"数字框 + 按钮"，点击按钮后控制台回显的指令中包含数字框**当前值**。
7. `help` 与 `help db.update` 输出完整、可读、含示例。
8. 以 1000 条/秒注入日志持续 30 秒：UI 不冻结，滚动缓冲上限生效。
9. 不带 where 的 db.delete，在 UI 路径与手输路径**都**触发二次确认。
10. 手动破坏布局文件后启动：自动回退默认布局，控制台出现告警。

## 14. 技术选型与工程结构（v1.0 定稿）

### 14.1 UI 框架：WPF，及 .NET 基线的新决策点（Q13）

**已定（v1.1 改判）**：WPF，目标框架 **net8.0-windows**——开发环境不支持 VS2026，暂无法使用 .NET 10 工具链（Q13）；仅 Windows 10/11 x64；应用清单启用 Per-Monitor V2 DPI。

**架构模式**：MVVM（建议 CommunityToolkit.Mvvm 处理属性与命令样板）。桥接铁律：**View → ViewModel → 组装指令文本 → 指令总线**。ViewModel 不得绕过总线直接调用服务，否则破坏架构不变量 1（一切操作皆指令）。

**⚠️ 选型调研发现的新事实（引出 Q13）**：

- .NET 8（LTS）官方支持至 **2026-11**，距今约 4 个月；.NET 9（STS）已于 2026-05 结束支持；当前 LTS 为 .NET 10（支持至 2028-11）。
- AvalonDock（Dirkster 分支）现状（2026-07 查证）：稳定版 **4.72.x** 可在 .NET 8 上使用；开发中的 **v5**（仍为 preview）目标框架为 net9.0-windows / net10.0-windows / net48，**不支持 net8**。v5 新能力与本需求高度相关：JSON 布局序列化（F-01）、官方 MVVM / 依赖注入配套包、Arc 深/浅色主题（S-04）、内置侧边栏 ToggleDockingManager（W-09 自动隐藏）。

| 路线 | .NET 基线 | 停靠库 | 说明 |
|---|---|---|---|
| **A ✅ 现行（v1.1）** | .NET 8 | AvalonDock 4.72.1 稳定版 | 受开发环境约束采用；注意基线 LTS 支持至 2026-11 |
| B（迁移目标） | .NET 10 LTS | v5 正式版后切换 | 待开发环境支持 VS2026（或改用 dotnet CLI ＋ VS Code / Rider 工具链）后执行；届时获得深色主题 / JSON 布局 / 自动隐藏；封装层保证迁移成本近乎为零 |

封装层（§14.2）保证：无论 4.x 还是 v5，业务代码零感知。

**迁移预案（v1.1 新增）**：
- 触发条件（满足其一即启动评估）：开发环境可用 VS2026 或等效 .NET 10 工具链；.NET 8 支持终止日（2026-11-10）临近。
- 迁移动作：各项目 TargetFramework 改为 net10.0-windows → 视 v5 正式版发布情况决定是否同步升级停靠库 → 全量回归 §11 十条验收。
- 风险留痕：.NET 8 于 2026-11 停止官方支持，此后模板及全部派生程序将运行在无安全补丁的基线上；迁移窗口建议不晚于 2026 年 Q4。

### 14.2 停靠库二次封装

**选定**：AvalonDock（Dirkster 维护分支，NuGet：Dirkster.AvalonDock）＋ 官方主题包（4.x 用 VS2013 系；v5 可用 Arc 系）。
**兜底备选**：Syncfusion DockingManager（商业，有社区免费许可，条件需核实）→ 再兜底为自研。

**封装原则**：Shell 对外只暴露自己的"窗口注册与布局模型"；四类标准窗口与派生应用代码**禁止**直接引用 AvalonDock 类型——这是将来换库或升 v5 的保险。AppShell.Shell 是解决方案中唯一引用 AvalonDock 的项目。

**封装工作清单（M1 范围）**：

1. 窗口注册模型：ID、标题、图标、默认停靠位与比例、单例/多例、"关闭 = 隐藏"语义（对应 W-11 与 §4.1 补充规则）。
2. 标签条置顶：AvalonDock 工具窗格（Anchorable）标签默认位于组底部，需样式改造移至**组顶部**（W-04）。
3. 比例语义换算：库内 DockWidth / DockHeight ↔ "占主程序窗体百分比"，窗体缩放时按比例重算（W-05）。
4. 布局事件 → 指令：监听停靠 / 浮动 / 隐藏 / 调比例的**完成**事件，生成等价 win.* / layout.* 指令进总线（W-10）。
   ⚠️ **防再入循环**：指令驱动布局变化 → 触发布局事件 → 又生成指令。封装层必须带"变更来源标记 ＋ 抑制期"，由指令引发的布局变更不再回声成新指令。
5. 布局序列化对接：库序列化器（4.x 为 XmlLayoutSerializer）↔ 配置服务；文件损坏回退默认布局并告警（N-06）。
6. 浮动窗验证：多显示器、混合 DPI 下的位置保存 / 恢复（W-06、N-01）。
7. 主题挂钩：库主题与应用主题统一切换，为深色主题（S-04）预留。
8. 自动隐藏（W-09，P1）：优先验证库内建能力（v5 的 ToggleDockingManager 天然覆盖），4.x 下不达标则后置。

**M1 首周 spike**：用裸 AvalonDock 快速验证清单中 2 / 3 / 4 / 6 四个高风险点；任何一点被证明不可行，立即触发换库或自研评估，避免封装做到一半才发现地基不稳。

### 14.3 游戏画布在 WPF 中的承载（派生游戏项目选用）

| 方案 | 适用 | 注意事项 |
|---|---|---|
| SkiaSharp（SKElement / SKGLElement） | 2D 游戏、关卡编辑器 | 首选；与 WPF 合成器兼容性好 |
| D3DImage ＋ Vortice / SharpDX | 3D、高性能渲染 | 集成成本较高 |

### 14.4 工程结构与"拷贝式"升级守则

解决方案结构（模板即按此结构交付）：

```
AppShell.sln
├─ src/
│  ├─ AppShell.Core/        # 指令核心、服务接口、窗口注册模型（不依赖 WPF）
│  ├─ AppShell.Services/    # 日志 / 数据(SQLite) / 文件 / 配置服务实现
│  ├─ AppShell.Shell/       # WPF 外壳：停靠封装、四类标准窗口、菜单/状态栏
│  │                        #（解决方案中唯一引用 AvalonDock 的项目）
│  └─ App/                  # ★ 派生应用唯一要改的项目：
│                           #   主窗口内容、自定义指令、面板 JSON、启动装配
├─ workspace/               # 默认工作区（资源窗口根目录，可配置）
├─ docs/                    # 本需求文档、指令手册、升级记录
└─ TEMPLATE_VERSION.md      # Shell 基线版本号与变更记录
```

守则（随模板放入 docs，作为开发纪律）：

1. **只读区**：src/AppShell.Core｜Services｜Shell 三个项目在派生应用中视为只读，App 只通过其公开接口交互。
2. **升级方式**：模板出新版 → 整体替换三个 AppShell.* 目录 → 编译 → 跑 §11 十条验收。TEMPLATE_VERSION.md 记录该应用当前基线版本。
3. **允许分叉**：确需深改 Shell（例如某游戏的深度定制）→ 在 TEMPLATE_VERSION.md 标注"已分叉于 vX.Y"，该应用自此放弃跟随模板升级，责任自负。
4. **接口稳定承诺**：Shell 公开接口的破坏性变更，必须在模板版本说明中给出逐条迁移步骤。

已知代价（选择拷贝式交付的自觉）：各派生程序可能出现版本漂移，靠 TEMPLATE_VERSION.md 与替换纪律控制。若将来程序数量多到难以维护，可平滑演进为"三个 AppShell.* 项目打成内部 NuGet 包"——工程结构不变，只是引用方式改变。

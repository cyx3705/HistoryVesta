# V1.0.0 活动坞独立模块

> 日期：2026-08-02  
> 状态：源码、构建与 Smoke 完成；实机部署与运行验收待执行

## 由来

活动坞原本是 `StudioTools 1.1.0` 聚合程序集里的 `dock` 逻辑模块。聚合期它是该程序集中唯一的
`IUiModule`，界面由 OneHistoryStudio 桌面 Shell 进程承载，因此关闭主窗口活动坞就消失。

活动坞是自持顶层窗口、不依赖主窗口的界面，归属应当是无窗服务宿主而不是桌面 Shell。把它继续留在聚合程序集
里，会让同一个物理模块同时含有"服务侧命令 + 桌面侧界面"两种互相矛盾的归属。因此本次将其整体迁出为独立
物理模块 `ActiveDock`。

## 模块合同

- 物理模块名 `ActiveDock`，版本 `1.0.0`，命令域仍为 `dock`，六条命令签名不变；
- 消费 `OneHistory.AppShell.Core 3.0.3`，不引用 OHS 源码或 AppShell 源码；
- 实现 `IUiModule + IShellUiAware`，但**不使用**注册器，仅用其注入行为判定宿主；
- manifest `ui=true`、`mcpExposure=standard`，正式产物由 `z-ActiveDock` 自包含提供；
- 数据根沿用 `%AppData%\OneHistoryStudio\ActiveDock`，固定项、位置与隐藏偏好跨版本继承。

命令域保持 `dock` 是为了不破坏既有调用和 MCP 投影。代价是部署顺序有硬约束，见下节。

## 宿主判据

模块宿主只在 `ShellUi` 非空时给 `IShellUiAware` 实例注入注册器，且注入发生在实例化阶段、早于
`CreateUi()`。桌面 Shell 恒注入，无窗服务宿主恒不注入，因此 setter 是否被调用可以确定性地区分两侧，
不依赖启动顺序，也不需要跨进程互斥。

`ActiveDockUiModule` 据此在被注入时弃权不建窗，只在服务宿主建窗。两个宿主进程仍都会加载本程序集并实例化
UI 类型，这是当前模块槽模型的固有行为；弃权侧不产生窗口、不占用界面资源。

## 连带修复

`ActiveDockState` 是进程内静态状态，变更经进程内事件通知窗口。迁出前命令注册在服务进程、窗口在桌面进程，
两侧是两份互不相干的静态状态，`dock.hide`、`dock.show`、`dock.pin` 和 `dock.refresh` 因此改不动正在显示的
活动坞，只写入偏好文件，重启桌面进程才生效。

该结论由源码推导得出，**尚未实机复现**。迁出后命令与窗口同处服务进程，该缺陷在设计上不再成立，但同样需要
实机确认。

## 部署顺序

`StudioTools 1.1.0` 仍然注册 `dock` 命令域。若先同步 `ActiveDock`，两个模块会争抢同一命令域导致注册失败。
正确顺序：

1. 先同步 `StudioTools 1.2.0`（已移除 dock），确认 `command.list` 中 `dock.*` 消失；
2. 再同步 `ActiveDock 1.0.0`，确认 `dock.*` 来源变为 `module:ActiveDock`。

该约束与 OHS 2.8.3 迁出 `github` 域时的教训一致。
